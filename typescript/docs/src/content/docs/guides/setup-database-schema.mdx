The schema is not applied by the control plane. It is a set of declarative `.surql` files in the
repository, applied with [surrealkit](https://github.com/surrealdb/surrealkit) — before the first
master starts, and again around every upgrade that changes it. Both deployment guides
([Docker](/guides/deploy-with-docker/), [native](/guides/deploy-natively/)) point here, and so does
every later schema change.

What is in the repository:

| Path | Contents |
|---|---|
| `database/setup.surql` | The two bookkeeping tables surrealkit itself needs: `__entity` and `__rollout` |
| `database/schema/{auth,base,orchestration}.surql` | One file per module — tables, fields, indexes, functions |
| `database/seed/seed.surql` | Optional seed data |
| `database/rollouts/*.toml` | Generated rollout manifests (one per change) |
| `database/snapshots/*.json` | Generated catalog/schema snapshots the next `plan` diffs against |

Prerequisites: `surrealkit` installed and a reachable SurrealDB ≥ 3.2 with root credentials — both
from [Prerequisites](/guides/prerequisites/).

## 1. Point surrealkit at the right database

Run every command from the repository root: surrealkit resolves `./database` relative to the
working directory (`--folder` overrides it).

:::caution[Always pass the connection explicitly]
surrealkit resolves **CLI flags > environment > `.env`**, and a `.env` in the working directory is
inherited by every process started there. On a machine that also holds credentials for another
environment, a forgotten flag is how a "local" command ends up rewriting production. `surrealkit.toml`
in this repository sets no connection defaults on purpose.
:::

Wrap the connection in a shell function so the flags stay short and the password survives whatever
characters it contains — a `SK="… --pass $pw"` string variable would be re-tokenized on spaces:

<Tabs syncKey="deployment">
<TabItem label="Native deployment">

The checkout's own `.env` holds the connection (`SURREALDB_HOST`, `SURREALDB_USER`,
`SURREALDB_PASSWORD`, `SURREALDB_NAMESPACE`, `SURREALDB_NAME`), so source it:

```sh
cd /path/to/proxy-guru
set -a; . ./.env; set +a

sk() {
  surrealkit --host "$SURREALDB_HOST" --ns "$SURREALDB_NAMESPACE" --db "$SURREALDB_NAME" \
    --user "$SURREALDB_USER" --pass "$SURREALDB_PASSWORD" "$@"
}
```

</TabItem>
<TabItem label="Image deployment">

The deployment `.env` lives next to the Compose file, not in the checkout, and names the root
credentials `SURREAL_ROOT_USER`/`SURREAL_ROOT_PASSWORD` with `GURU_NS`/`GURU_DB`. Schema commands
run from the checkout, so pass the password in by hand rather than sourcing a file from another
directory:

```sh
cd /path/to/proxy-guru
read -rs SURREAL_ROOT_PASSWORD    # paste it; not echoed
export SURREAL_ROOT_PASSWORD

sk() {
  surrealkit --host ws://127.0.0.1:8000 --ns guru --db guru \
    --user root --pass "$SURREAL_ROOT_PASSWORD" "$@"
}
```

</TabItem>
</Tabs>

If the database only listens on loopback on a remote host, tunnel to it first:
`ssh -N -L 8000:127.0.0.1:8000 guru-host`.

## 2. Apply the schema

<Steps>

1. **Bookkeeping tables.** Once per database, before anything else:

   ```sh
   sk setup
   ```

2. **Plan.** `plan` diffs the schema files against the live database and writes a reviewable
   manifest; `lint` validates it without touching the database. Read the manifest before applying
   it.

   ```sh
   sk rollout plan --name initial_schema
   # Generated rollout manifest ./database/rollouts/20260913083052__initial_schema.toml
   # Updated ./database/snapshots/catalog_snapshot.json

   sk rollout lint 20260913083052__initial_schema
   ```

3. **Expand.** `start` applies the non-destructive half — new tables, fields, indexes, functions.
   It is safe to run while an older control plane is still serving:

   ```sh
   sk rollout start 20260913083052__initial_schema
   # Rollout ... is ready to complete.
   ```

4. **Contract.** `complete` drops what the new code no longer uses, so it must never run before the
   matching binaries do. On a first install there is no old version to keep alive, so it follows
   immediately:

   ```sh
   sk rollout complete 20260913083052__initial_schema
   ```

5. **Confirm.**

   ```sh
   sk status
   # __rollout:20260913083052__initial_schema [completed] initial_schema
   ```

</Steps>

## 3. Seed the module configuration

Operator-tunable settings — health thresholds and retention, the default ACME directory, the
renewal window, how often each periodic job runs — live in the database, one `app_config` row per
key, not in the environment. Write the defaults once the schema is in place, with `manage-tool` —
built from the same checkout (`cargo build --release -p manage-tool`), or downloaded from a
`master-v*` release, which attaches it as `manage-tool-<version>-x86_64-unknown-linux-gnu`. Its
database flags have the same names as `guru-master`'s, and they also read `SURREALDB_*` from the
environment, so pass them explicitly unless you have just sourced the right file:

<Tabs syncKey="deployment">
<TabItem label="Native deployment">

```sh
(set -a; . ./.env; set +a; ./target/release/manage-tool config seed)
# seeded auth
# seeded orchestration
```

</TabItem>
<TabItem label="Image deployment">

```sh
./target/release/manage-tool \
  --address ws://127.0.0.1:8000 --username root --password "$SURREAL_ROOT_PASSWORD" \
  --namespace guru --database guru \
  config seed
```

</TabItem>
</Tabs>

It is idempotent and never overwrites a value you have edited, so re-run it after every schema
change. `config list`, `config get <key>` and `config set <key> <json>` inspect and change those
values; the masters read them once at startup, so a change needs a restart, not a redeploy. See
[Configuration → Module configuration](/reference/configuration#module-configuration).

Skipping the seed is safe — an unseeded installation runs the defaults — but a stored document that
does not match its type fails master startup naming the key, which is deliberate: silently falling
back to defaults could move ACME from staging to the production directory.

## 4. Later schema changes

An upgrade is the same four commands with the deploy wedged between the two halves, which is the
entire point of the split:

<Steps>

1. `sk rollout plan --name <change>` and read the manifest.

2. `sk rollout start <target>` — expand. The running masters keep working: nothing they use has been
   removed yet.

3. Deploy the binaries that match the new schema (bump the image tags, or rebuild and restart the
   units), then verify.

4. `sk rollout complete <target>` — contract. Only now do the objects the new code dropped go away.

</Steps>

If step 3 or 4 goes wrong, `sk rollout rollback <target>` reverts the rollout and the previous
version's tags/binaries go back. A rollout killed mid-flight leaves `__rollout.status` on
`running_*`; heal the metadata with `sk rollout repair <target>` before planning anything else.

| Command | When |
|---|---|
| `sk rollout baseline` | First rollout against a database that already carries the schema — adopts the current state instead of diffing it from empty |
| `sk rollout rollback <target>` | Revert an in-flight rollout |
| `sk rollout repair <target>` | `start`/`complete` was killed mid-flight and `__rollout.status` is stuck on `running_*`; reconciles metadata only |
| `sk status` | What the database thinks is applied |

:::caution[`surrealkit sync` is for disposable databases]
`sync` reconciles immediately and prunes deleted objects — no manifest, no review step, no rollback.
It is the right tool in [Local Development](/guides/local-development/) and wrong on anything whose
data you would miss.
:::

## 5. Keeping the manifests

`database/rollouts/*.toml` and `database/snapshots/*.json` are how the next `plan` knows what the
live database already has, so they must survive — but they are **not** committed. `.gitignore`
excludes both directories on purpose: they are per-environment state, regenerated by `rollout plan`
against one specific database, and a manifest from another environment is worse than none.

So: keep them on the machine that runs the schema commands, and back that directory up together
with the deployment's `.env`. If several operators maintain the same database, share them the way
you share the credentials — one host or one secret store that owns the schema workflow — not
through the repository.

Losing them does not lose the database, but the next `plan` will diff from an empty catalog; use
`sk rollout baseline` to re-adopt the live state instead.
