The schema is a set of SQL migrations in the repository, embedded into the binaries at compile
time. `guru-master` applies whatever is pending when it starts, so a fresh installation needs
nothing here beyond an empty database — this page is for applying them deliberately instead:
before the first master starts, ahead of a deploy, or against a database no master runs against
yet. Both deployment guides ([Docker](/guides/deploy-with-docker/),
[native](/guides/deploy-natively/)) point here, and so does every later schema change.

What is in the repository:

| Path | Contents |
|---|---|
| `database/migrations/*.sql` | The migrations, applied in filename order and never edited once applied |

Prerequisites: a reachable PostgreSQL ≥ 16 and the connection URL for it — both from
[Prerequisites](/guides/prerequisites/).

## 1. Point the tool at the right database

Both binaries take the connection as one URL: `--database-url`, or `GURU_DATABASE_URL` in the
environment.

```
postgres://guru:<password>@127.0.0.1:15432/guru
```

:::caution[Pass the connection explicitly]
`GURU_DATABASE_URL` is inherited by every process started in a shell that exported it, and a `.env`
in the working directory is inherited the same way. On a machine that also holds credentials for
another environment, a forgotten flag is how a "local" command ends up rewriting production.
:::

`manage-tool` is built from the same checkout (`cargo build --release -p manage-tool`), or
downloaded from a `master-v*` release, which attaches it as
`manage-tool-<version>-x86_64-unknown-linux-gnu`.

<Tabs syncKey="deployment">
<TabItem label="Native deployment">

The checkout's own `.env` holds the connection, so source it:

```sh
cd /path/to/proxy-guru
set -a; . ./.env; set +a
```

</TabItem>
<TabItem label="Image deployment">

The deployment `.env` lives next to the Compose file, not in the checkout, so pass the URL in by
hand rather than sourcing a file from another directory:

```sh
cd /path/to/proxy-guru
read -rs GURU_DATABASE_URL    # paste it; not echoed
export GURU_DATABASE_URL
```

</TabItem>
</Tabs>

If the database only listens on loopback on a remote host, tunnel to it first:
`ssh -N -L 15432:127.0.0.1:5432 guru-host`.

## 2. Apply the schema

```sh
./target/release/manage-tool db migrate
# schema is up to date
```

That is the whole step. It is idempotent: every migration that has already run is recorded in the
`_sqlx_migrations` table and skipped. Several processes may run it at once — the migrator takes a
PostgreSQL advisory lock, so a fleet of masters starting together applies each migration exactly
once.

## 3. Seed the module configuration

Operator-tunable settings — health thresholds and retention, the default ACME directory, the
renewal window, how often each periodic job runs — live in the database, one `app_config` row per
key, not in the environment. Write the defaults once the schema is in place:

```sh
./target/release/manage-tool config seed
# seeded auth
# seeded orchestration
```

It is idempotent and never overwrites a value you have edited, so re-run it after every schema
change. `config list`, `config get <key>` and `config set <key> <json>` inspect and change those
values; the masters read them once at startup, so a change needs a restart, not a redeploy. See
[Configuration → Module configuration](/reference/configuration#module-configuration).

Skipping the seed is safe — an unseeded installation runs the defaults — but a stored document that
does not match its type fails master startup naming the key, which is deliberate: silently falling
back to defaults could move ACME from staging to the production directory.

## 4. Later schema changes

A schema change is a new file in `database/migrations/`; an applied migration is never edited,
because the database records which ones it has run, not what they said.

<Steps>

1. Apply the new migrations, either by deploying the new binaries (each master migrates at startup)
   or, to front-load it, with `manage-tool db migrate` from the new checkout.

2. Deploy the binaries that match, then verify.

</Steps>

:::caution[A rolling upgrade sees both schemas at once]
While the new binaries roll out, the old ones are still serving against the migrated database. A
migration that only adds things is safe for them; one that drops or renames a column the old binary
still reads is not. Split such a change in two — one release that adds and stops using the old
shape, a later one that drops it — or accept a short stop of every master between the two.
:::

There is nothing to keep outside the repository: the migrations are committed, and what a database
has applied is recorded in that database.
