Both deployment guides, [Deploy with Docker](/guides/deploy-with-docker/) and
[Deploy Natively](/guides/deploy-natively/), start here. This page sets up the external
dependencies and the operator tooling; the deployment guide you follow afterwards only wires the
control plane to them.

What each method actually needs:

|                              | Deploy with Docker                                                                                                                        | Deploy Natively                                                            |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| PostgreSQL ≥ 16              | yes                                                                                                                                       | yes                                                                        |
| Apache Iggy server 0.9.x     | yes                                                                                                                                       | yes                                                                        |
| Redis 7.x                    | yes                                                                                                                                       | yes                                                                        |
| Docker Engine + Compose      | yes (runs the published application images; optional for the datastores)                                                                  | no                                                                         |
| Rust toolchain + `protoc`    | only if you build `manage-tool` yourself — it is also attached to every `master-v*` release                                                | yes — it builds every binary                                               |
| C toolchain, `make`, `cmake` | same — only if you build `manage-tool`, which pulls in the certificate stack (`instant-acme`/`rcgen` on aws-lc), whose vendored C sources need a compiler and cmake | yes, same reason                                                           |
| `perl`                       | no                                                                                                                                        | yes — `guru-worker` compiles vendored OpenSSL, configured by a perl script |
| Bun                          | no                                                                                                                                        | yes (builds and runs the dashboard)                                        |
| Hostname + TLS certificate   | yes                                                                                                                                       | yes                                                                        |

## 1. Docker Engine and Compose (image deployment only)

Install Docker only if you are following the image deployment. Native deployment does not require
Docker: install PostgreSQL, Iggy and Redis directly, use managed services, or run them by
another method. Pick your distro once; every tab on this page follows.

<Tabs syncKey="distro">
<TabItem label="Debian">

```sh
# See https://docs.docker.com/engine/install/debian/
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/debian/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/debian
Suites: $(. /etc/os-release && echo "$VERSION_CODENAME")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

Remove any conflicting distro packages first: `docker.io`, `docker-compose`, `docker-doc`,
`docker-buildx`, `podman-docker`, `containerd`, `runc`. The service is enabled on boot by the
package here.

</TabItem>
<TabItem label="Ubuntu">

```sh
# See https://docs.docker.com/engine/install/ubuntu/
# Both the repository path and the suite expression differ from Debian's.
# Ubuntu derivatives report their own codename in `VERSION_CODENAME`.
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

Remove any conflicting distro packages first: `docker.io`, `docker-compose`, `docker-compose-v2`,
`docker-doc`, `docker-buildx`, `podman-docker`, `containerd`, `runc`. The service is enabled on
boot by the package here.

</TabItem>
<TabItem label="Fedora / RHEL">

```sh
# On Fedora: https://docs.docker.com/engine/install/fedora/
sudo dnf config-manager addrepo --from-repofile https://download.docker.com/linux/fedora/docker-ce.repo
sudo dnf install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

```

```sh
# On RHEL: https://docs.docker.com/engine/install/rhel/
sudo dnf -y install dnf-plugins-core
sudo dnf config-manager --add-repo https://download.docker.com/linux/rhel/docker-ce.repo
sudo dnf install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

```

</TabItem>
<TabItem label="Arch">

```sh
# See https://wiki.archlinux.org/title/Docker
sudo pacman -S --needed docker docker-compose
sudo systemctl enable --now docker.service
```

</TabItem>

Confirm the engine, and keep Compose an operator action. You can either use `sudo docker compose` or add your own account to the `docker` group, which is root-equivalent on the host
and should therefore never be granted to a service account:

```sh
sudo docker run --rm hello-world
```

None of these are decoration — each is a real dependency of this workspace:

| Package                                            | Needed because                                                                                                                                                                                                                                                       |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `protoc` (`protobuf-compiler`, on Arch `protobuf`) | `lib/rpguru_sdk`'s build script compiles `proto/` with `tonic-prost-build`, which shells out to `protoc`. Every binary depends on that crate, `manage-tool` included, so a missing `protoc` fails the build. Set `PROTOC=/path/to/protoc` if yours is not on `PATH`. |
| C compiler, `make`                                 | Needed wherever `manage-tool` is built (not if you download it): it reaches the certificate stack through the `orchestration` module, and several of its crates (`aws-lc-sys`, `ring`, `zstd-sys`) compile vendored C sources.                                       |
| `cmake`                                            | `aws-lc-sys` builds its vendored sources with cmake, so it is needed wherever `manage-tool` is built.                                                                                                                                                                |
| `perl`                                             | `guru-worker` links OpenSSL with the `vendored` feature: OpenSSL is compiled from the bundled source tree, and its `Configure` is a perl script. Native deployment only.                                                                                             |
| `pkgconf` / `pkg-config`                           | Build-dependency of the `*-sys` crates above.                                                                                                                                                                                                                        |
| `openssl`                                          | The deployment guides generate passwords and keys with `openssl rand -hex 32`.                                                                                                                                                                                       |
| `unzip`                                            | Required by the Bun installer on Linux.                                                                                                                                                                                                                              |
| `nginx`                                            | Terminates TLS for the dashboard, and for the worker API in the native guide. Any current build has `http_ssl_module` and `http_v2_module`, which is what `grpc_pass` (nginx ≥ 1.13.10) needs.                                                                       |

No `libssl-dev`/`openssl-devel` and no `libprotobuf` development packages: what the Rust build needs
of those, it vendors.

## 3. Rust and Bun

Everything above needed root; everything in this section belongs to the account that will **own the
checkout**, and that account differs per deployment method:

<Tabs syncKey="deployment">
<TabItem label="Native deployment">

The control plane, the dashboard and everything you build run as one unprivileged service user.
Create it with `sudo useradd --create-home --shell /bin/bash guru`, then enter its shell with
`sudo -iu guru`; the rest of this section runs as `guru`. Installing the toolchains from that shell
keeps them in the service user's home, where systemd can find them.

The native guide uses `guru` and `/home/guru` throughout (including `User=`/`Group=` and the Bun
path in its units); substitute your own name consistently. Do **not** give the service user Docker
or other host-administration privileges, even if you choose containers for the datastores.

</TabItem>
<TabItem label="Image deployment">

Nothing runs from the checkout permanently — it holds the Compose file, and builds `manage-tool`
only if you would rather not download it from a `master-v*` release — so your own operator account
is the right place. Bun is not needed at all.

</TabItem>
</Tabs>

<Steps>

1. **Rust**, via [rustup](https://rustup.rs/). The workspace pins the toolchain in
   `rust-toolchain.toml` (channel `1.98`) and rustup installs that pin on the first `cargo`
   invocation. Do not substitute a distro `rust` package: an older compiler cannot build edition 2024.

   ```sh wrap frame="none"
   curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
   . "$HOME/.cargo/env"
   ```

2. **The checkout.** `manage-tool` is the flexible part: build it here, or
   download it from a `master-v*` GitHub release, which carries it next to the `guru-master` binary
   (`x86_64-unknown-linux-gnu`). The image guide also uses the Compose file; native deployment only
   uses that file if you choose the optional container path.

   ```sh wrap frame="none"
   git clone \
     https://github.com/haruki-nikaidou/proxy-guru.git /path/to/proxy-guru
   ```

4. **Bun** — native deployment only, to build and run the dashboard. Node is not used anywhere;
   SvelteKit's post-build step needs `Promise.withResolvers`, which Node 20 lacks.

   ```sh wrap frame="none"
   curl -fsSL https://bun.com/install | bash
   export BUN_INSTALL="$HOME/.bun"; export PATH="$BUN_INSTALL/bin:$PATH"
   ```

   The installer takes a version pin (`bash -s "bun-v1.3.3"`) to match the `oven/bun:1.3` image the
   published dashboard is built with. Arch ships a `bun` package too, but installing it needs root
   and puts the binary outside the service account's home.

</Steps>

## 4. PostgreSQL, Iggy and Redis

### What the control plane needs from them

|           | Requirement                                                                                                                                                                                                                                                     |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PostgreSQL | **16 or newer.** One database, reached through one URL. The control plane owns its schema: it applies the migrations it ships with, so the role it connects as needs ordinary `CREATE`/`ALTER` rights on that database — nothing cluster-wide. |
|           | **Durable storage** on a volume you back up. This is the only irreplaceable state in the system. `pg_dump` of the one database is a complete backup.                                                                                                             |
|           | **Room for the pool.** Every master mode holds up to `GURU_DB_POOL_SIZE` connections (10 by default) and there are five of them, so leave `max_connections` comfortably above fifty.                                                                          |
| Iggy      | **Apache Iggy server 0.9.x** — the release paired with the Rust SDK 0.11 that the control plane builds against. Linux only: in a container it needs `SYS_NICE`, `seccomp=unconfined` and an unlimited `memlock` (io_uring). The control plane creates its stream (`guru`) and topics at startup, idempotently, so nothing has to be pre-created — the root user the server creates is enough. |
|           | URL form: `iggy://user:password@host:8090`, passed as `IGGY_URL`.                                                                                                                                                                                             |
|           | Iggy is **mandatory in all five master modes**. It carries canvas-change hints, health facts and notices, and stores them durably (plus retry topics), so it is state to keep on a volume — but the periodic jobs run in-process in `cron` and do not depend on it. |
| Redis     | **7.x or newer.** Pub/sub only — the control plane stores nothing in it, declares nothing and needs no persistence, so any reachable server works, including a managed one. One instance shared by the whole fleet: replicas find each other through it. |
|           | URL form: `redis://127.0.0.1:6379/`, passed as `REDIS_URL`. Required in every mode except `notifier`, which never touches it.                                                                                                                                  |
|           | It carries the operator API's `Watch*` streams: every mutation publishes one event on the channel `guru:orchestration:live`, and each `dashboard_grpc` replica subscribes once and fans it out to the streams it serves. An outage costs open streams their deliveries and nothing else — edits still apply and still derive, and the subscriber reconnects with backoff and then asks every watcher to re-read the database. The dashboard's canvas editor and health page follow these streams, so an open page stops updating meanwhile and catches up on its own; `live bus connected` in a master's log is still the direct check. |

Neither containers nor Docker Compose are required for the datastores. Follow the official
[PostgreSQL download page](https://www.postgresql.org/download/),
[Apache Iggy site](https://iggy.apache.org) and
[Redis installation guide](https://redis.io/docs/latest/operate/oss_and_stack/install/), use
managed services, or use the Compose examples below. Whichever method you choose must satisfy the
requirements above.

### Credentials

Generate the passwords **URL-safe** — both are interpolated into a URL (`GURU_DATABASE_URL` and
`IGGY_URL`), where `@`, `:`, `/` and `%` change the meaning of the URL:

```sh
openssl rand -hex 32          # once for PostgreSQL, once for Iggy
```

Hex avoids every quoting and percent-encoding question. If you insist on punctuation, percent-encode
it in both URIs (`@` → `%40`, `:` → `%3A`, `/` → `%2F`, `%` → `%25`).

Two passwords, not three: Redis takes no credentials at all. Its listener is the access control —
bind it to loopback, or leave it on the private Compose network. The other two guard state that a
stray client could read or destroy, which is why they get a password and it does not.

Record the connection credentials in the file the control plane will read. The image-deployment
Compose example also reads its datastore credentials from this file:

<Tabs syncKey="deployment">
<TabItem label="Native deployment">

```sh
# /path/to/proxy-guru/.env   (chmod 600; gitignored)
GURU_DATABASE_URL=postgres://guru:<first hex string>@127.0.0.1:5432/guru
IGGY_USER=guru
IGGY_PASSWORD=<second hex string>
IGGY_URL=iggy://guru:<second hex string>@127.0.0.1:8090
REDIS_URL=redis://127.0.0.1:6379/
```

systemd later reads this file verbatim through `EnvironmentFile=`. Keep `GURU_DATABASE_URL` and
`IGGY_URL` written out in full; systemd does **not** expand `${…}`.

</TabItem>
<TabItem label="Image deployment">

```sh
# /srv/guru/.env   (chmod 600)
POSTGRES_USER=guru
POSTGRES_PASSWORD=<first hex string>
POSTGRES_DB=guru

IGGY_USER=guru
IGGY_PASSWORD=<second hex string>
```

Create `/srv/guru` first (`sudo mkdir -p /srv/guru`); the Compose file below lives next to this
`.env`, and the image guide adds `MASTER_VERSION`, `FRONTEND_VERSION` and `GURU_MASTER_KEY` to it.
`GURU_DATABASE_URL` and `IGGY_URL` never appear in it either: Compose builds both from the variables
above, the way it spells Redis out itself (`redis://redis:6379/`) because Redis needs no credentials.

</TabItem>
</Tabs>

### Start them

<Tabs>
<TabItem label="Native deployment">

Install the three services with the official
[PostgreSQL download page](https://www.postgresql.org/download/),
[Apache Iggy site](https://iggy.apache.org) (server 0.9.x binaries or packages) and
[Redis installation guide](https://redis.io/docs/latest/operate/oss_and_stack/install/). Create a
`guru` role and a `guru` database owned by it, with a loopback listener on port `5432`; configure
the Iggy server with `IGGY_ROOT_USERNAME`/`IGGY_ROOT_PASSWORD` set to the user and password from
`.env`, durable storage and a TCP listener on `127.0.0.1:8090`; configure Redis with a loopback
listener on port `6379` and persistence
turned off (`save ""` and `appendonly no`), because nothing in it is worth restoring. Use your
operating system's service manager to start all three services and enable them at boot.

Docker Compose is an optional alternative, not a deployment requirement. If you choose it, the
repository's `docker-compose.yml` provides the same loopback-only layout with persistent data under
`./data/`.

</TabItem>
<TabItem label="Image deployment">

Create the deployment directory (`/srv/guru` in the image guide) and put the three datastores in its
Compose file, next to the `.env` that holds their credentials:

```yaml
# /srv/guru/docker-compose.yml
name: guru

services:
  postgres:
    image: postgres:18.6-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    volumes:
      # The 18-series image mounts the whole cluster here, not at /…/data.
      - postgres-data:/var/lib/postgresql
    # Loopback only: the operator machine reaches it through an SSH tunnel.
    ports:
      - "127.0.0.1:5432:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 20

  iggy:
    image: apache/iggy:0.9.0
    restart: unless-stopped
    # io_uring: the server needs these on Linux.
    cap_add: [SYS_NICE]
    security_opt: ["seccomp=unconfined"]
    ulimits:
      memlock:
        soft: -1
        hard: -1
    environment:
      IGGY_ROOT_USERNAME: ${IGGY_USER}
      IGGY_ROOT_PASSWORD: ${IGGY_PASSWORD}
      IGGY_TCP_ADDRESS: 0.0.0.0:8090
      IGGY_NODE_ADVERTISED_ADDRESS: localhost
      IGGY_QUIC_ENABLED: "false"
      IGGY_WEBSOCKET_ENABLED: "false"
    volumes:
      - iggy-data:/app/local_data
    healthcheck:
      test: ["CMD-SHELL", "iggy -u \"$$IGGY_ROOT_USERNAME\" -p \"$$IGGY_ROOT_PASSWORD\" stream list"]
      interval: 10s
      timeout: 10s
      retries: 12

  redis:
    image: redis:7-alpine
    restart: unless-stopped
    # Pub/sub only: nothing is persisted.
    command: ["redis-server", "--save", "", "--appendonly", "no"]

volumes:
  postgres-data:
  iggy-data:
```

```sh
cd /srv/guru
sudo docker compose up -d postgres iggy redis
```

The masters are added to this same file later, in the image guide — the datastores have to exist
first, because a master applies the schema to the database as it starts.

</TabItem>
</Tabs>

The Compose example needs one detail explained. The Iggy server uses io_uring, which is why the
service adds `SYS_NICE`, drops the default seccomp profile and lifts the `memlock` limit. Its data
lives in the `iggy-data` volume, which keeps undelivered events across a container recreation.
Redis is the odd one out on purpose: no volume, no
published port and no healthcheck — the masters reach it over the Compose network, and a fresh empty
server is exactly as useful as the one it replaces.

The Iggy topology is created for you by every master as it starts: one stream `guru` with the
topics `orchestration_canvas_dirty`, `orchestration_health_changed` and `notify_health_notice`, one
partition (id `0`) each, plus a `retry_<topic>` for each once its consumer has started.

## 5. A hostname and a certificate

One DNS name pointing at the host, plus a TLS certificate for it (`certbot`, your CA, anything).
Both guides terminate the dashboard on it; the native guide terminates the worker API on the same
name.

:::danger[HTTPS is not optional]
The dashboard's session cookie (`guru_session`) is issued with `Secure`, so browsers drop it over
plain HTTP on anything but `localhost`. The app also reconstructs its own origin per request and
rejects a login POST whose browser `Origin` does not match, which is why the proxy has to forward
`X-Forwarded-Proto` and `X-Forwarded-Host`.
:::

:::caution[Behind Cloudflare's proxy]
The hostname may sit behind the orange cloud once gRPC is turned on in Cloudflare's Network
settings. Cloudflare cuts a streaming response that carries no data for about 100 s, so the worker
streams never go quiet: `WatchConfig` carries a keep-alive every `stream_keepalive_secs` (15 s) and
`ReportHealth` answers every report — keep that setting well under the limit. Workers built before
0.5.0-beta ask for no keep-alives and reconnect every couple of minutes until they are updated. nginx
should also take the client address from Cloudflare, or every worker is recorded at a Cloudflare
address: see [Deploy Natively → Behind Cloudflare](/guides/deploy-natively/#behind-cloudflare).
:::
