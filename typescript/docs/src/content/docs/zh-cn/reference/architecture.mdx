## Crate 一览

| Crate | 职责 |
|---|---|
| `bin/guru-master` | 控制平面。单个二进制，五种模式（`--mode`）：`dashboard_grpc`（运维 API）、`workers_grpc`（Worker API + 配置视图轮询器）、`consumer`（Iggy 事件处理器 —— `CanvasDirty` 配置派生与 `HealthChanged` 通知扇出）、`notifier`（通知投递，恰好一个实例）、`cron`（在进程内运行全部六个周期任务）。各模式通过 wakuwaku 的 `ServiceBuilder` 装配：`grpc_service`（gRPC 服务端）、`iggy_consumer`（事件处理器）、`cron_job`（周期任务）。 |
| `bin/guru-worker` | 数据平面。终结监听器并转发流量。既可以基于 TOML 文件独立运行（收到 `SIGHUP` 时重新加载），也可以以 agent 模式运行，从 master 流式获取配置。 |
| `bin/manage-tool` | 管理 CLI：`create-admin` 初始化引导、`orchestration export-config`。 |
| `lib/guru_topology` | 以 Pod 为点的转发拓扑图：检查图，并把它编译成每台服务器的转发配置。纯计算，无 I/O。 |
| `lib/guru_worker_config` | Worker 配置模型，由两个平面共享。 |
| `lib/rpguru_sdk` | 由 `proto/` 生成的 gRPC/protobuf 类型（Rust）。 |
| `lib/db_types` | `table_record!` 与 `text_enum!`：带类型的行 id 和以文本存储的枚举。 |
| `modules/auth` | 账号、会话、API key、RBAC。 |
| `modules/orchestration` | 画布、服务器和 Pod 图；图的检查、配置派生、Worker 发布。 |
| `modules/notify` | 通知模块 —— 已按 `base` 搭好骨架，尚未实现。 |
| `modules/base` | 共享基础设施，以及所有模块共同遵循的目录布局。 |

## 一切皆 Processor

`kanau::processor::Processor` 就是**状态加上一个异步函数**：

```text
Processor = State + async fn(Input) -> Result<Output, Error>
```

`Processor` 是一个可 `Clone` 的结构体，它持有自己的依赖，并为每个操作实现一次
`Processor<Input>`。业务操作和周期任务（`Processor<CronTick>`）都被建模为「一个输入结构体
加一个 `Processor` 实现」；数据库查询采用同样的「输入结构体」形态，但实现的是 wakuwaku-entity 的
`Query` 与 `Execute<PgSource>`（见下方分层规则）。

## 模块结构

每个模块 crate 都与 `modules/base` 保持一致：

<FileTree>

- src/
  - lib.rs 声明下面各个模块；设置 crate 级别的 lint
  - config.rs 带类型的配置（对应一行 `app_config`，JSON 文档）
  - utils/ 小巧、几乎无依赖的辅助函数
  - entities/ 持久化层
    - db/ PostgreSQL 行类型 + sqlx 查询
    - redis/ Redis 键值类型（rkyv 编码）
  - services/ 业务逻辑（有状态的 Processor）
  - events/ Iggy 事件载荷 + topic
  - hooks/ 后台反应器（Iggy 事件处理器、周期任务、日志记录器）
  - rpc/ gRPC 服务实现（传输边界）

</FileTree>

| 你正在写…… | 就放到…… |
|---|---|
| 一条 PostgreSQL 查询或一个表行类型 | `entities/db` |
| 一个 Redis 缓存值或临时令牌 | `entities/redis` |
| 一个组合了查询与规则的用例 | `services` |
| 一条其他模块会响应的消息 | `events` |
| 对某个事件的响应 / 一个周期任务 / 一条审计日志 | `hooks` |
| 一个 gRPC 端点实现 | `rpc` |
| 一项运维人员可以修改的带类型设置 | `config` |
| 一个不依赖运行时的纯辅助函数 | `utils` |

## 分层规则

- **依赖方向：** `rpc → services → entities/events/config`。功能模块可以依赖 `base`，但 `base`
  不得依赖任何功能模块；模块之间也不得直接触碰彼此的内部实现 —— 它们通过 gRPC 或 Iggy 事件通信。
- **`entities/db`：** 每个表或聚合对应一个子模块；定义行结构体；id 由
  `table_record!(NameId, "table")` 包装，以文本存储的枚举由 `text_enum!` 统一写一次。每条查询是一个输入结构体，
  实现 wakuwaku-entity 的 `Query`（其 `Effect` 为 `Read<tables::X>` / `Write<tables::X>`，作用于各 crate 在
  `entities/db/tables.rs` 中定义的表标记）与 `Execute<PgSource>`；由 `base::db::Db`（即
  `wakuwaku::entity::Db<PgSource, ReadWrite>`）执行；`Execute` 返回 `base::db::Error`。每个多语句事务都是一个
  公开的 `TxFlow` 状态机（`XFlow::new(input)`），其步骤按顺序以 `tx.run` 执行普通查询或辅助查询，并以
  `base::db::commit` 或 `base::db::rollback`（栅栏失败：`Error::Conflict`）结束；条件写入什么都没匹配到时，提交其空结果。
  事务流不是查询：调用方执行 `db.process(Transaction(XFlow::new(..)))`，自行处理 `TxOutput::Committed` / `RolledBack`；
  丢失的 `COMMIT` 应答变成 `OrchestrationError::CommitUnknown`（gRPC `UNKNOWN`）。快照读取是 `RepeatableRead` 隔离级别的只读事务流。所有语句都走 sqlx 的 `query!` 宏族，因此 SQL 在编译期就会按真实 schema 校验；行为
  仍然由针对真实数据库的集成测试覆盖（`#[sqlx::test]`）。
- **`services`：** 持有自身依赖的 `Clone` 结构体，每个操作一个 `Processor` 实现，返回领域类型 ——
  绝不返回 protobuf 类型。
- **`events`：** Iggy 事件载荷。一个事件派生 rkyv 与 `RkyvMessageSer/De`，实现 `EventBody` 和 `Event`
  （`TYPE_TAG`、`Key: PartitionKey`——其 `SUPER_PARTITION_NAME` 就是 topic、`Algebra`、`atomic_ordering`）。
  契约文档写明发布方、消费方、topic 和 tag。共享的 stream 与拓扑（`STREAM`、`PARTITIONS`、`ensure_topology`）
  位于 `base::events`。这是模块之间唯一被认可的异步通道。
- **`hooks`：** 对事件的响应是 Iggy `EventHandler<E>` 实现（外加 `ServiceCreation`）；周期性工作是 `CronJob`
  实现——一个带固定 `INTERVAL` 的 `Processor<CronTick>`，在开始工作前用 `ClaimJobRun` 抢占这次运行（写入一行
  `orchestration_job_run`，采用 compare-and-set），因此多个 `cron` 进程同时运行时，同一轮处理也不会被执行两次。
  处理失败时：数据库不可用 → 原地重试；其他数据库错误或冲突 → 该键进入 `retry_<topic>`（间隔 2、4、8、16 s 重试）；
  其余错误被丢弃并记录日志。offset 在处理之后才提交（至少一次）。
- **`rpc`：** 只做薄适配 —— 解码请求、调用服务、编码回复。不含业务逻辑。
- **错误：** 不再有 `wakuwaku::Error`；每个模块有自己的错误枚举（`AuthError`、`OrchestrationError`、
  `NotifyError`），可转换为 `tonic::Status`，也可转换为事件处理器所用的 Iggy `HandleError` 类别。
- **Lint：** crate 级别 `deny(clippy::unwrap_used)`、`expect_used` 与 `panic`。请求路径上不允许
  panic。
- **Tracing：** 只使用 `tracing` + `tracing-subscriber`（没有 OpenTelemetry）。使用 `#[tracing::instrument(skip_all, err)]` 并显式指定 span `name` —— entities 用
  `Query:<Input>`（事务流的 `step` 用 `Transaction:<Input>`），services 用 `Service:<Input>`，hook processor 用
  `Hook:<Input>`。gRPC handler 不需要指定；trait 方法名本身就标识了 span。

## PostgreSQL 注意事项

- 比较可空列请用 `IS DISTINCT FROM`，而不是 `<>`：`<>` 与 `NULL` 比较的结果是 `NULL`，而不是
  `true`，所以用它写出来的围栏条件会悄无声息地永不匹配。
- `jsonb` 文档里的 JSON `null` 不是 SQL 的 `NULL`；用 `jsonb_typeof` 区分两者。
- 语句在编译期校验：列要逐个写出（不用 `SELECT *`）；Rust 侧类型是 `table_record!` id、`text_enum!`
  或 `Json<T>` 的列要带上类型别名（`id AS "id: CanvasId"`），同类型的参数则以 `input.id as _` 传入；
  超过五行的 SQL 放在 `<crate>/sql/*.sql` 里，由 `query_file!` 调用。没有任何地方在运行时拼 SQL。
- 离线查询数据提交在 `.sqlx/`，因此构建不需要数据库（镜像构建使用 `SQLX_OFFLINE=true`）。语句或
  schema 变更后，对一个已迁移的数据库运行 `cargo sqlx prepare --workspace -- --all-targets` 重新生成
  并提交（`-- --all-targets` 用来把测试自身的语句也收进去）。
- Schema 只做 migration，绝不做原地修改：`guru-master` 在启动时持有一把 advisory lock 应用所有尚未
  应用的 migration，因此一批同时启动的 master 只会把每个 migration 恰好应用一次。
