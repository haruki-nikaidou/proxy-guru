一棵画布树持有一张 **Pod 图**：一张有向无环图，顶点是服务器上的监听，终点是转发网络之外的目的地。每次编辑时，
控制平面都会检查整张图，并由它为每台服务器派生一份配置（见[发布模型](/zh-cn/reference/rollout/)）。画布上
显示的其他东西 —— 分流器、聚合器、总线 —— 都是这张图的*画法*，是从图上实时计算出来的。

![main 画布：杭州的服务器上两个客户端 Pod 进入同一个分流器，分散到香港的五台服务器，再由一个聚合器把它们的总线汇合到两个出口](/img/canvas/canvas-overview.avif)

## 模型

| 概念 | 是什么 |
|---|---|
| **服务器** | 一台运行 `guru-worker` 的机器，也是在它上面运行的 Pod 的集合。服务器本身不转发任何东西。 |
| **Pod** | 某台服务器上的一个监听：一个端口、可选的绑定地址、可选的对外地址，以及它的**接入方式**。每个 Pod 都是一个独立的顶点。 |
| **接入方式** | 流量到达 Pod 的方式。*客户端* Pod 直接接受客户端连接 —— 裸 TCP，或用 ACME 证书终结 TLS —— 并可以接收 PROXY 头。*中继* Pod 接受其他 Pod 经由 TCP、TLS 或 QUIC 中继过来的流量。 |
| **出口** | 转发网络之外、流量离开的 `host:port`，可以附带 PROXY 头。任意多个 Pod 都可以连到同一个出口。 |
| **边** | Pod 流量的一条去向：去往某个中继 Pod，或某个出口。两个 Pod 之间可以有多条边（比如拨不同的地址）。 |
| **路由** | 每个 Pod 自己的一棵树，叶子恰好是它自己的出边。**负载均衡**按权重把连接分给成员，**故障转移**使用第一个存活的成员。两者可以任意层数互相嵌套。 |

由这个模型可以得出几条规则：

- **一跳的协议由目标的接入方式决定。** 连向 `relay_quic` Pod 的边就是一跳 QUIC；改变 Pod 的接入方式，所有连向
  它的 Pod 都会按新的方式拨号。
- **一跳的地址**依次取边上的覆盖地址、目标 Pod 的对外地址、目标服务器的有效地址（从 Worker 学到的：固定、上报
  或观测）。端口依次取边上的覆盖端口、目标 Pod 的端口。
- **客户端 Pod 不能被连入**，流量也永远不会回到它已经经过的 Pod：图始终无环。
- **端口可以自动分配。** 保存时不填端口的 Pod 会得到所在服务器 40000–59999 之间的一个空闲端口；同一台服务器的
  两个 Pod 不能占用同一个套接字（通配绑定与该端口、该传输层上的所有地址重叠）。
- **按客户端 IP 固定的负载均衡**需要知道客户端地址的 Pod：中继 Pod，或接收 PROXY 的客户端 Pod。
- **画了一半也是合法的。** 没有去向的 Pod、没有被连入的中继 Pod、没有边到达的出口都只是警告；这样的 Pod 只是
  不会部署，不影响其他任何东西。

## 读懂画布

### 服务器

![杭州移动 的服务器卡片：中国国旗、绿色的 Online 徽标、IPv4 和 IPv6 地址、最后一次上报，以及两个客户端 Pod m_hk7_145 和 tutusgak 及其监听地址](/img/canvas/card-server-client.avif)

服务器卡片显示健康徽标、其他服务器拨它时用的地址、最后一次健康上报的时间和 Worker 版本，然后是画在这个画布上的
每个 Pod 各一行：经过它的规则的颜色、名字、接入方式（客户端 Pod 带一个进入方框的箭头）和监听地址。

![gcore-hk-1 的服务器卡片：两个 QUIC 中继 Pod，每个左右各有一个把手](/img/canvas/card-server-relay.avif)

每个 Pod 行的**右侧**都有一个把手 —— 从这里拖出，就给这个 Pod 加一个新的去向。中继 Pod 的行在**左侧**还有一个，
去向可以落在这里。卡片标题上的两个把手属于卡片本身：左边的把去向落成这台服务器上的一个新中继 Pod，总线则连在两边。
其他画布的服务器、但它的 Pod 画在这个画布上时，会以虚线边框显示。

服务器的面板里有它的设置（名称、图标、日志级别、IPv6 策略、QUIC 速率、固定地址和额外地址）、它的 Pod 列表和添加
Pod 的一行、在它上面运行的 agent，以及它在发布中的状态。

### 出口

![出口卡片：exit-8443，目的地 localhost:8443，有 5 条连入](/img/canvas/card-exit.avif)

出口卡片显示目的地、到达它的规则，以及有多少条边连到这里。

### 分流器

![分流器卡片：负载均衡，2 个路由，gcore-hk-1 到 gcore-hk-5 五个成员各 ×1，以及 + 成员 把手](/img/canvas/card-splitter.avif)

分流器是路由中的一个分组 —— 负载均衡或故障转移。在相同的卡片之间以相同方式选择的分组，不论属于多少个 Pod，都画成
**一个**分流器：两条规则分散到同样的五台服务器上，就是一个代表两个路由的分流器。每一行是一个成员，带着它的权重
（`×2`）或档位（`#1`）以及去向；成员本身是分组时，会连向一个嵌套的分流器。淡色的 **+ 成员** 把手会给这个分流器
代表的每个路由都加一个成员。它的面板可以一次性修改所有这些路由的策略、固定方式、权重和顺序。

### 聚合器

![聚合器卡片：5 台服务器，两个去向，到 exit-8443 和 出口 黑色的海豚](/img/canvas/card-aggregator.avif)

当来自两台及以上服务器的总线在同一个分流器或出口前汇合时，聚合器把它们收拢，并为每张交出去的卡片各设一个出口。
它只是画法：不保存任何东西，也不能编辑或删除。

### 总线与规则

**总线**是在两张卡片之间走同一条路的所有边，画成一根线缆，里面每条**规则**各有一根该规则颜色的细线，代表多条边时
还会标出数量。规则就是客户端 Pod —— 流量进入转发网络的地方 —— 它会给这些流量可能经过的一切上色。右上角的图例
列出画布上的规则；点击其中一条，不承载它的东西都会变淡。

### 子画布与传送门

子画布是画在另一个画布里的画布，双击即可进入。嵌套只用来组织画面：边可以自由跨越画布边界。把连线拖到子画布卡片上，
会询问指的是其中哪个中继 Pod、出口或服务器；**传送门**卡片代表树中另一个画布，这个画布的边连进去或从那里连过来。

### 问题

左下角列出控制平面在这棵树的图上发现的问题 —— 先是与这个画布有关的，再是树中其他地方的。点击一条就打开它所涉及
的东西，如果在别处，会先打开那个画布。错误会阻止下一次编辑；警告从不阻止。

## 编辑

每次编辑都是**一个批次** —— 要写入和删除的行 —— 控制平面会针对它所导致的图整体检查，要么全部写入，要么全部不写。
如果批次是基于一棵在画布读取之后已经改变的树计算出来的，就会被拒绝；画布会重新加载，你再试一次即可。

### 添加

菜单栏的**添加**会在视图中央附近、不与其他卡片重叠的地方创建服务器、出口（会询问目的地）或子画布。Pod 在服务器的
面板里添加：名字、接入方式和端口 —— 留空就自动分配。

### 连接

从 Pod 行右侧的把手拖出，放到：

| 放到 | 结果 |
|---|---|
| 某个中继 Pod 左侧的把手 | 一条连向该 Pod 的边 |
| 某个出口 | 一条连向该出口的边 |
| 某张服务器卡片 | 那台服务器上一个新的中继 Pod，按你选的协议监听 |
| 某个分流器 | 这个 Pod 加入它：它的路由多出一份该分流器分组的副本，落在同样那些服务器上属于它自己的中继 Pod 上 |
| 某个子画布或传送门 | 由你选择其中的中继 Pod、出口，或某台服务器上的新中继 Pod |

新的去向会加入 Pod 的路由：第一个就是整个路由，第二个会把两者变成负载均衡，分组则多一个成员。从分流器的 **+ 成员**
把手拖出，会对它代表的每个路由做同样的事。

### 编辑 Pod

![m_hk7_145 的 Pod 面板：端口、绑定和对外地址，以及显示在 gcore-hk-1 和 gcore-hk-2 的中继 Pod 之间负载均衡的路由编辑器](/img/canvas/panel-route.avif)

点击 Pod 行打开它的面板：名字和备注、接入方式、是否接收 PROXY、TLS 客户端 Pod 的 TLS 证书（SNI、DNS 提供商、
zone 或域名 id、ACME 目录）、端口、绑定地址和对外地址。下面是树形的路由：

- 每个分组有一个策略（负载均衡或故障转移），负载均衡可以按客户端地址固定；
- 负载均衡的每个成员有权重，故障转移的每个成员有档位；
- 箭头用来调整成员顺序；勾选一个分组中的两个或更多成员，可以把它们**编组**成自己的负载均衡或故障转移，
  **解散编组**把嵌套的分组放回父分组；
- **添加去向**给这个分组加一个成员（与*连接*相同的目标对话框）；
- 去向的菜单可以编辑这条边的**拨号地址** —— 覆盖地址或端口 —— 或删除这个去向。

路由的结构在保存之前都是草稿。添加或删除去向会改变边、立即写入，所以要等草稿保存或还原之后才能做。中继 Pod 的面板
还会列出连向它的 Pod。

### 删除

选中卡片或总线后按 **Delete**，或使用面板里的删除按钮。要删除的内容会在删除之前连同控制平面对结果图的判定一起显示：

![确认对话框：删除 2 个 Pod、删除 4 条连线、改写 2 个 Pod，一个“同时删除不再有入边的中继 Pod”的开关，以及控制面接受这次修改](/img/canvas/dialog-review.avif)

删除 Pod 会删除进出它的所有边，并改写引用这些边的路由。**同时删除不再有入边的中继 Pod** 会把不再有任何连入的中继
Pod 连同它们的去向一起删掉 —— 也就是为某条规则落在中转服务器上的那些。删除服务器会先删除它的 Pod；删除子画布会
删除其中的一切，但只要还有外面的 Pod 连进去，或运行在里面的服务器上，就会被拒绝。

### 移动

拖动卡片来移动，松开时位置会被保存。服务器、出口和子画布的位置保存在它们自己的行上。分流器、聚合器、传送门以及
其他画布的服务器记在画布的布局里；编辑会让每张卡片保持原位：被编辑改变了形状的分流器留在原处，新卡片会放在
不与其他卡片重叠的地方。

## 编辑如何被检查

下面这些会拒绝整个批次：

| 问题 | 原因 |
|---|---|
| `cycle` | 流量可能回到它已经经过的 Pod |
| `route_missing_edge`、`route_duplicate_edge`、`route_unknown_edge`、`route_foreign_edge`、`missing_route` | 路由没有恰好各引用一次该 Pod 的每条出边 |
| `empty_group`、`zero_weight`、`route_too_deep` | 没有成员的分组、权重为 0、嵌套超过 32 层 |
| `client_pod_dialed` | 连向客户端 Pod 的边 |
| `listener_conflict` | 同一台服务器的两个 Pod 在同一端口、同一传输层上绑定地址重叠 |
| `listener_in_use` | 某台服务器仍在以另一种协议拨这个端口：改给 Pod 换一个新端口 |
| `sticky_without_client_ip` | 在不知道客户端地址的 Pod 上使用按客户端固定的负载均衡 |
| `invalid_bind_ip`、`invalid_advertise_ip`、`invalid_override_address`、`invalid_exit_destination`、`invalid_sni` | 无法解析的地址、目的地和名字 |
| `unknown_dns_provider`、`certificate_issued_elsewhere` | TLS Pod 引用了不存在的 DNS 提供商，或在 SNI 的签发方式上与另一个 Pod 不一致 |
| `no_free_port` | 该服务器上 40000–59999 的端口全被占用 |
| `edge_ends_changed` | 边的两端就是它的身份：删掉它，再加一条 |

下面这些只是警告：`single_tier_failover`、`pod_without_edges`、`relay_pod_not_dialed`、`exit_not_reached`。

## Worker 运行的是什么

每个 Pod 在其服务器的配置里变成一个 `[[forwarding]]`，tag 是 Pod 的 id。报告了 `route_table` 能力的 Worker 以
分组和上游组成的表来接收路由，并按存活情况在成员之间选择；连向这类 Worker 的中继跳会要求中继确认它自己的下一跳
已经应答，所以存活中继背后失效的出口也会让拨号端转向下一个选择。旧版 Worker 以树形接收路由。两种形式都见
[配置参考](/zh-cn/reference/configuration/#forwardingto)。
