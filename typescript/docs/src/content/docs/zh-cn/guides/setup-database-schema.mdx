Schema 是仓库中一组 SQL migration，在编译期被嵌入到二进制文件里。`guru-master` 启动时会应用所有尚未
应用的 migration，所以全新安装只需要一个空数据库，本页之外无需任何操作 —— 本页讲的是如何主动地应用它们：
在第一个 master 启动之前、部署之前，或者针对一个还没有任何 master 连接的数据库。两篇部署指南
（[Docker](/zh-cn/guides/deploy-with-docker/)、[原生部署](/zh-cn/guides/deploy-natively/)）都指向本页，
后续每一次 Schema 变更同样如此。

仓库中都有什么：

| 路径 | 内容 |
|---|---|
| `migrations/*.sql` | 各个 migration，按文件名顺序应用，一旦应用过就不再修改 |

前置条件：一个可访问的 PostgreSQL ≥ 16，以及它的连接 URL —— 两者都来自
[前置条件](/zh-cn/guides/prerequisites/)。

## 1. 让工具指向正确的数据库

两个二进制文件都用一个 URL 来表示连接：`--database-url`，或环境变量 `GURU_DATABASE_URL`。

```
postgres://guru:<password>@127.0.0.1:15432/guru
```

:::caution[显式传入连接参数]
`GURU_DATABASE_URL` 会被在导出过它的 shell 中启动的每个进程继承，工作目录下的 `.env` 也会以同样的方式被
继承。如果这台机器上同时存放着另一套环境的凭据，那么一个被遗漏的参数，就是"本地"命令最终改写生产库的原因。
:::

`manage-tool` 由同一个检出目录构建（`cargo build --release -p manage-tool`），也可以直接从某个
`master-v*` release 下载它的二进制（`manage-tool-<version>-x86_64-unknown-linux-gnu`）。

<Tabs syncKey="deployment">
<TabItem label="原生部署">

仓库检出目录自带的 `.env` 保存着连接信息，直接 source 它：

```sh
cd /path/to/proxy-guru
set -a; . ./.env; set +a
```

</TabItem>
<TabItem label="镜像部署">

部署用的 `.env` 与 Compose 文件放在一起，而不在仓库检出目录中，所以请手动传入 URL，而不要去 source
另一个目录下的文件：

```sh
cd /path/to/proxy-guru
read -rs GURU_DATABASE_URL    # paste it; not echoed
export GURU_DATABASE_URL
```

</TabItem>
</Tabs>

如果数据库在远端主机上只监听 loopback，请先建立隧道：
`ssh -N -L 15432:127.0.0.1:5432 guru-host`。

## 2. 应用 Schema

```sh
./target/release/manage-tool db migrate
# schema is up to date
```

这一步就这么多。它是幂等的：每个已经运行过的 migration 都记录在 `_sqlx_migrations` 表中并会被跳过。
多个进程可以同时运行它 —— migrator 会取得一把 PostgreSQL advisory lock，所以一批同时启动的 master
只会把每个 migration 恰好应用一次。

## 3. 初始化模块配置

由运维人员调优的设置 —— 健康阈值与保留期、默认的 ACME 目录、续期窗口、各个周期任务的运行频率 ——
都存放在数据库里，每个键对应一行 `app_config`，而不是放在环境变量中。Schema 就绪后写入一次默认值：

```sh
./target/release/manage-tool config seed
# seeded auth
# seeded orchestration
```

它是幂等的，绝不会覆盖你已经改过的值，所以每次 Schema 变更后都可以重新运行。`config list`、
`config get <key>` 和 `config set <key> <json>` 用于查看和修改这些值；master 只在启动时读取一次，
因此改动需要重启，而不是重新部署。参见
[配置 → 模块配置](/zh-cn/reference/configuration#模块配置)。

跳过初始化是安全的 —— 未初始化的安装会使用默认值 —— 但如果某个已存储的文档与它的类型不匹配，master 启动
会失败并指出对应的键，这是故意的设计：静默回退到默认值可能会把 ACME 从 staging 切到生产目录。

## 4. 后续的 Schema 变更

一次 Schema 变更就是在 `migrations/` 下新增一个文件；已经应用过的 migration 绝不再修改，
因为数据库记录的是它运行过哪些 migration，而不是这些 migration 的内容。

<Steps>

1. 应用新的 migration：既可以直接部署新的二进制文件（每个 master 会在启动时完成 migration），也可以提前
   动手，用新检出目录里的 `manage-tool db migrate` 执行。

2. 部署与之匹配的二进制文件，然后做验证。

</Steps>

:::caution[滚动升级会同时面对两套 Schema]
在新二进制文件逐步上线的过程中，旧的那些仍在对着已经迁移过的数据库提供服务。只做新增的 migration 对它们
是安全的；而删除或重命名一个旧二进制仍在读取的列则不然。请把这类变更拆成两次 —— 一个 release 负责新增并
停止使用旧结构，之后的一个 release 再把旧结构删掉 —— 或者接受在两者之间让所有 master 短暂停机。
:::

仓库之外没有任何需要保管的东西：migration 都已提交，而某个数据库应用了哪些，记录在那个数据库自己里面。
