两种部署方式各自的实际需求：

| | 使用 Docker 部署 | 原生部署 |
|---|---|---|
| PostgreSQL ≥ 16 | 需要 | 需要 |
| RabbitMQ 3.13/4.x | 需要 | 需要 |
| Redis ≥ 7 | 需要 | 需要 |
| Docker Engine + Compose | 需要（用于运行已发布的应用镜像；数据存储是否使用它可自行选择） | 不需要 |
| Rust 工具链 + `protoc` | 仅在你选择自行构建 `manage-tool` 时需要——它也可以从 `master-v*` release 下载 | 需要——它要构建全部二进制 |
| C 工具链、`make`、`cmake` | 同上：仅在自行构建 `manage-tool` 时需要（它会引入证书相关依赖栈——基于 aws-lc 的 `instant-acme`/`rcgen`，其内置的 C 源码需要编译器和 cmake） | 需要，原因相同 |
| `perl` | 不需要 | 需要——`guru-worker` 会编译内置的 OpenSSL，而它由一个 perl 脚本完成配置 |
| Bun | 不需要 | 需要（构建并运行控制台） |
| 主机名 + TLS 证书 | 需要 | 需要 |

## 1. Docker Engine 与 Compose（仅镜像部署）

只有选择镜像部署时才需要安装 Docker。原生部署不要求 Docker：你可以直接安装 PostgreSQL 和
RabbitMQ，也可以使用托管服务或其他运行方式。先选定你的发行版；本页所有标签页都会随之联动。

<Tabs syncKey="distro">
<TabItem label="Debian">

```sh
# See https://docs.docker.com/engine/install/debian/
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/debian/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/debian
Suites: $(. /etc/os-release && echo "$VERSION_CODENAME")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

这些软件包没有一个是装饰性的——每一个都是本工作区的真实依赖：

| 软件包 | 为什么需要 |
|---|---|
| `protoc`（`protobuf-compiler`，Arch 上为 `protobuf`） | `lib/rpguru_sdk` 的构建脚本用 `tonic-prost-build` 编译 `proto/`，而它会调用 `protoc`。所有二进制都依赖该 crate，`manage-tool` 也不例外，因此缺少 `protoc` 会导致构建失败。如果你的 `protoc` 不在 `PATH` 中，请设置 `PROTOC=/path/to/protoc`。 |
| C 编译器、`make` | 构建 `manage-tool` 需要，它经由 `orchestration` 模块引入证书相关依赖栈；其中若干 crate（`aws-lc-sys`、`ring`、`zstd-sys`）会编译内置的 C 源码。原生部署必定要构建它；镜像部署只有在不从 `master-v*` release 下载它时才需要。 |
| `cmake` | `aws-lc-sys` 用 cmake 构建其内置源码，因此凡是构建 `manage-tool` 的地方都需要它。 |
| `perl` | `guru-worker` 以 `vendored` feature 链接 OpenSSL：OpenSSL 由内附的源码树编译而成，而它的 `Configure` 是一个 perl 脚本。仅原生部署需要。 |
| `pkgconf` / `pkg-config` | 上述 `*-sys` crate 的构建依赖。 |
| `openssl` | 部署指南使用 `openssl rand -hex 32` 生成密码和密钥。 |
| `unzip` | Linux 上的 Bun 安装脚本需要它。 |
| `nginx` | 为控制台终止 TLS，在原生部署指南中还为 Worker API 终止 TLS。任何当前版本的构建都带有 `http_ssl_module` 和 `http_v2_module`，这正是 `grpc_pass`（nginx ≥ 1.13.10）所需要的。 |

不需要 `libssl-dev`/`openssl-devel`，也不需要 `libprotobuf` 的开发包：Rust 构建所需的那部分
都由它自己内置。

## 3. Rust 与 Bun

上面的所有步骤都需要 root；本节的一切都属于将要**持有代码检出目录**的那个账号，而这个账号
因部署方式而异：

<Tabs syncKey="deployment">
<TabItem label="原生部署">

控制平面、控制台以及你构建出来的所有东西都以同一个无特权服务用户运行。使用
`sudo useradd --create-home --shell /bin/bash guru` 创建该用户，再用 `sudo -iu guru` 进入它的
shell；本节余下内容都以 `guru` 运行。从这个 shell 安装工具链可确保它们位于服务用户的 home 中，
从而能被 systemd 找到。

原生部署指南全篇都使用 `guru` 和 `/home/guru`（包括 `User=`/`Group=` 以及各 unit 中的 Bun
路径）；如果换成你自己的名字，请保持一致。即使选择用容器运行数据存储，也不要授予服务用户
Docker 或其他主机管理权限。

</TabItem>
<TabItem label="镜像部署">

检出目录里不会常驻运行任何东西——它存放 Compose 文件，并且可以用来构建
`manage-tool`（也可以改为从某个 `master-v*` release 下载那个二进制）——所以放在你自己的运维账号下
就是合适的。完全不需要 Bun。

</TabItem>
</Tabs>

<Steps>

1. **Rust**，通过 [rustup](https://rustup.rs/) 安装。工作区在 `rust-toolchain.toml` 中固定了
   工具链版本（channel `1.98`），rustup 会在第一次执行 `cargo` 时安装这个固定版本。不要用
   发行版自带的 `rust` 包替代：更旧的编译器无法构建 edition 2024。

   ```sh wrap frame="none"
   curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
   . "$HOME/.cargo/env"
   ```

2. **代码检出。** `manage-tool` 可以从这里构建，也可以从某个 `master-v*` release 下载。镜像部署指南还会
   使用 Compose 文件；原生部署只有在选择可选的容器方案时才使用它。

   ```sh wrap frame="none"
   git clone \
     https://github.com/haruki-nikaidou/proxy-guru.git /path/to/proxy-guru
   ```

4. **Bun**——仅原生部署需要，用于构建和运行控制台。项目任何地方都不使用 Node；
   SvelteKit 的构建后处理步骤需要 `Promise.withResolvers`，而 Node 20 没有它。

   ```sh wrap frame="none"
   curl -fsSL https://bun.com/install | bash
   export BUN_INSTALL="$HOME/.bun"; export PATH="$BUN_INSTALL/bin:$PATH"
   ```

   安装脚本支持指定版本（`bash -s "bun-v1.3.3"`），以便与构建已发布控制台镜像所用的
   `oven/bun:1.3` 保持一致。Arch 也提供 `bun` 软件包，但安装它需要 root，而且会把二进制
   放在服务账号 home 之外。

</Steps>

## 4. PostgreSQL、RabbitMQ 与 Redis

### 控制平面对它们的要求

| | 要求 |
|---|---|
| PostgreSQL | **16 或更高版本。** 一个数据库，通过一个 URL 访问。控制平面自己拥有它的 schema：它会应用随二进制一起发布的 migration，因此它连接时所用的角色只需要对该数据库拥有普通的 `CREATE`/`ALTER` 权限，不需要任何集群级权限。 |
| | **持久化存储**，放在一个你会备份的卷上。这是整个系统中唯一无法重建的状态。对这一个数据库执行 `pg_dump` 就是一份完整备份。 |
| | **给连接池留出余量。** 每个提供服务的 master 最多持有 `GURU_DB_POOL_SIZE` 个连接（默认 10 个），而这样的 master 有三个，所以请把 `max_connections` 留得明显高于 30。 |
| RabbitMQ | 任意 3.13/4.x 服务端。控制平面会在启动时自行声明所需的 exchange 和持久化队列，因此无需预先创建——默认 vhost 上的一个用户就够了。本项目只测试过 RabbitMQ。 |
| | URI 形式：`amqp://user:password@host:5672/`，其中**结尾的斜杠**表示选择默认 vhost。`/%2f` 这种写法会被解析器拒绝。 |
| | 在**全部四种 master 模式中消息代理都是必需的**。周期性工作本身*就是*消息：它停机期间，没有任何过期画布被清扫，没有任何静默的服务器被标记为 `Offline`，也没有任何证书会被续期。请把它当作依赖，而不是可选的优化。 |
| Redis | **7.x 或更高版本。** 只用到 pub/sub —— 控制平面不在其中存储任何东西，不声明任何东西，也不需要持久化，因此任何可访问的服务端都可以，包括托管服务。整个集群共用一个实例：各副本正是通过它彼此发现的。 |
| | URL 形式：`redis://127.0.0.1:6379/`，通过 `REDIS_URL` 传入。在会打开数据库连接的**那三种 master 模式下必填**（`dashboard_grpc`、`workers_grpc`、`consumer`）；`cron` 从不接触它。 |
| | 它承载运维 API 的 `Watch*` 流：每一次变更都会在频道 `guru:orchestration:live` 上发布一个事件，而每个 `dashboard_grpc` 副本只订阅它一次，再把事件分发给自己提供的那些流。中断只会让已打开的流收不到投递，除此之外别无影响——编辑照样生效、照样派生，订阅端也会带退避地重连，并在之后让每个 watcher 重新读取数据库。控制台的画布编辑器和健康状况页面跟随这些流，因此中断期间已打开的页面会停止更新，并在之后自行追上最新状态；某个 master 日志里的 `live bus connected` 仍然是直接的检查依据。 |

:::caution[非 RabbitMQ 消息代理并非可直接替换的实现]
控制平面使用 AMQP 0-9-1 客户端 `amqprs`，并依赖 RabbitMQ 的 exchange 与 queue 声明语义。
其他消息代理均未经过测试。尤其是 Azure Service Bus 使用 AMQP 1.0，不能假定它与本项目兼容；
控制平面的部分或全部消息传递都可能失败。除非你能端到端验证其他实现，否则请使用 RabbitMQ。
:::

数据存储不要求使用容器或 Docker Compose。你可以按照官方
[PostgreSQL 下载页面](https://www.postgresql.org/download/)、
[RabbitMQ 下载指南](https://www.rabbitmq.com/docs/download)和
[Redis 安装指南](https://redis.io/docs/latest/operate/oss_and_stack/install/)安装，使用托管服务，或采用
下方的 Compose 示例。无论选择哪种方式，都必须满足上表的要求。

### 凭据

生成的密码要**对 URL 安全**——两个密码都会被插入某个 URI（`GURU_DATABASE_URL` 与
`AMQP_URI`），其中 `@`、`:`、`/` 和 `%` 会改变 URI 的含义：

```sh
openssl rand -hex 32          # once for PostgreSQL, once for RabbitMQ
```

十六进制字符串可以规避所有引号和百分号编码的问题。如果你坚持要用标点符号，请在两个 URI
中都对其做百分号编码（`@` → `%40`、`:` → `%3A`、`/` → `%2F`、`%` → `%25`）。

现在就把连接凭据记录到控制平面将要读取的文件中。镜像部署的 Compose 示例也会从该文件读取
数据存储凭据：

<Tabs syncKey="deployment">
<TabItem label="原生部署">

```sh
# /path/to/proxy-guru/.env   (chmod 600; gitignored)
GURU_DATABASE_URL=postgres://guru:<first hex string>@127.0.0.1:5432/guru
RABBIT_USER=guru
RABBIT_PASSWORD=<second hex string>
AMQP_URI=amqp://guru:<second hex string>@127.0.0.1:5672/
REDIS_URL=redis://127.0.0.1:6379/
```

systemd 之后会通过 `EnvironmentFile=` 逐字读取这个文件。请完整写出 `GURU_DATABASE_URL` 和
`AMQP_URI`，因为 systemd **不会**展开 `${…}`。

</TabItem>
<TabItem label="镜像部署">

```sh
# /srv/guru/.env   (chmod 600)
POSTGRES_USER=guru
POSTGRES_PASSWORD=<first hex string>
POSTGRES_DB=guru

RABBIT_USER=guru
RABBIT_PASSWORD=<second hex string>
```

请先创建 `/srv/guru`（`sudo mkdir -p /srv/guru`）；下面的 Compose 文件就放在这个 `.env`
旁边，镜像部署指南之后还会向它追加 `MASTER_VERSION`、`FRONTEND_VERSION` 和
`GURU_MASTER_KEY`。`GURU_DATABASE_URL` 和 `AMQP_URI` 同样不会出现在其中：Compose 会用上面这些
变量把两者拼出来，就像 Redis 不需要凭据、于是它直接把 URL 写死成 `redis://redis:6379/` 一样。

</TabItem>
</Tabs>

### 启动它们

<Tabs>
<TabItem label="原生部署">

按照官方 [PostgreSQL 下载页面](https://www.postgresql.org/download/)、
[RabbitMQ 下载指南](https://www.rabbitmq.com/docs/download)和
[Redis 安装指南](https://redis.io/docs/latest/operate/oss_and_stack/install/)安装这三个服务。创建一个
`guru` 角色以及一个归它所有的 `guru` 数据库，并让它监听 `5432` 端口的回环地址；为 RabbitMQ 配置
`.env` 中的用户和密码、默认 vhost、持久化存储以及监听 `5672` 端口的回环地址；Redis 只需要一个监听 `6379` 端口的回环
地址，并关掉它的持久化（`--save '' --appendonly no`）——控制平面不在其中存放任何状态。使用操作系统的
服务管理器启动这三个服务，并将它们设为开机自启。

Docker Compose 只是可选方案，并非部署要求。若选择它，仓库中的 `docker-compose.yml` 提供同样
只监听回环地址的布局，并将持久化数据存放在 `./data/` 下。

</TabItem>
<TabItem label="镜像部署">

创建部署目录（镜像部署指南中为 `/srv/guru`），把三个数据存储写进它的 Compose 文件，
与保存其凭据的 `.env` 放在一起：

```yaml
# /srv/guru/docker-compose.yml
name: guru

services:
  postgres:
    image: postgres:18.6-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    volumes:
      # The 18-series image mounts the whole cluster here, not at /…/data.
      - postgres-data:/var/lib/postgresql
    # Loopback only: the operator machine reaches it through an SSH tunnel.
    ports:
      - "127.0.0.1:5432:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 20

  rabbitmq:
    image: rabbitmq:4-alpine
    restart: unless-stopped
    environment:
      RABBITMQ_DEFAULT_USER: ${RABBIT_USER}
      RABBITMQ_DEFAULT_PASS: ${RABBIT_PASSWORD}
    volumes:
      - rabbit-data:/var/lib/rabbitmq
    healthcheck:
      test: ["CMD", "rabbitmq-diagnostics", "-q", "check_running"]
      interval: 10s
      timeout: 10s
      retries: 12

  redis:
    image: redis:7-alpine
    restart: unless-stopped
    # Pub/sub only: nothing is persisted.
    command: ["redis-server", "--save", "", "--appendonly", "no"]

volumes:
  postgres-data:
  rabbit-data:
```

```sh
cd /srv/guru
sudo docker compose up -d postgres rabbitmq redis
```

各个 master 会在之后的镜像部署指南中加入同一个文件——数据存储必须先存在，因为 master 启动时
会自己把 schema 应用到数据库上。

</TabItem>
</Tabs>

Compose 示例还有两个关键细节。RabbitMQ 会以节点名 `rabbit@<hostname>` 命名数据目录，
所以仓库的 Compose 文件固定了 `hostname:`；否则每次重新创建容器都会得到一个空的消息代理。Redis
刻意没有卷：它的服务命令关掉了 RDB 与 AOF，因为经过它的一切都只是过路的实时事件。

consumer 绑定的队列会自动为你创建：用于编辑事件的 `guru_orchestration_canvas_dirty`，
以及对应五个周期任务的 `guru_orchestration_derive_stale_canvases`、
`guru_orchestration_sweep_liveness`、`guru_orchestration_trim_health_history`、
`guru_orchestration_renew_certificates` 和
`guru_orchestration_rotate_relay_certificates`。

## 5. 主机名与证书

一个指向该主机的 DNS 名称，以及为它签发的 TLS 证书（`certbot`、你自己的 CA，都可以）。
两篇指南都在它上面终止控制台的 TLS；原生部署指南还会在同一个名称上终止 Worker API 的 TLS。

:::danger[HTTPS 不是可选项]
控制台的会话 Cookie（`guru_session`）带有 `Secure` 标记，因此除 `localhost` 之外，浏览器
在纯 HTTP 下都会丢弃它。应用还会按请求重建自身的 origin，并拒绝浏览器 `Origin` 不匹配的
登录 POST，这就是反向代理必须转发 `X-Forwarded-Proto` 和 `X-Forwarded-Host` 的原因。
:::

:::caution[不要让该主机名走 Cloudflare 代理]
Cloudflare 的代理会在 100 秒没有数据后关闭流式响应。`WatchConfig` 在两个修订版本之间是静默的，
所以在橙色云朵后面，每个 Worker 都会每隔几分钟重连一次。请把该记录设为 DNS-only；
到你自己 nginx 的 TLS 已经足以保护传输中的 API key。
:::
