[使用 Docker 部署](/zh-cn/guides/deploy-with-docker/)指南从镜像运行应用。本指南讲的是另一种常见形态：
**同一台机器既是构建机，也是控制平面**。Rust 二进制由 systemd 直接从 `target/release/` 启动，
控制台运行自己的构建产物。SurrealDB 和 RabbitMQ 可以作为原生服务、托管服务或容器运行，不要求
Docker。改完代码只需 `cargo build` 加上重启 unit，中间不需要应用镜像。

本指南还补上了镜像方案里没有覆盖的一件事：把 Worker API 放在**与控制台相同的公网主机名下、由 TLS 保护**，这样互联网上任意位置的
Worker 都能用 `--master https://guru.example.com` 接入，无需 VPN。

请把全文中的 `guru.example.com` 替换成你自己的主机名，把 `/path/to/proxy-guru` 替换成你的代码检出目录。除此之外没有任何与主机相关的内容。

## 1. 布局

| 组件 | 运行方式 | 监听地址 |
|---|---|---|
| SurrealDB 3.2 | 原生服务、托管服务或容器 | 默认为 `127.0.0.1:8000` |
| RabbitMQ 4 | 原生服务、托管服务或容器 | 默认为 `127.0.0.1:5672` |
| `guru-master` ×4 | systemd 模板 `guru-master@<mode>` | `127.0.0.1:50051`、`127.0.0.1:50052` |
| 控制台 | systemd `guru-frontend` | `127.0.0.1:3100` |
| nginx | 你现有的 nginx，一个 server 块 | `:443` |

除 nginx 之外，所有组件都只绑定回环地址。唯一的公网入口是那个 TLS server 块：它在 `/` 上提供控制台，并把
`/guru.orchestration.agent.WorkerAgent/` 上的 gRPC 转发到 `:50052`。

## 2. 前置条件

先完成 **[前置条件](/zh-cn/guides/prerequisites/)**：主机软件包（C 工具链、`cmake`、`perl`、
`protoc`、`openssl`、nginx）、rustup、surrealkit、Bun、代码检出、可访问的 SurrealDB 与
RabbitMQ，以及一个已配好证书的主机名。原生构建会编译内置（vendored）OpenSSL 与 aws-lc，并用
Bun 运行控制台。Docker 是可选项，只有把某个数据存储放在容器中运行时才需要。

从代码检出目录直接运行会带来两个后果，开始之前值得再强调一遍。

### 部署用户

前置条件会创建一个非特权用户 `guru`（在其工具链章节的 *原生部署* 标签页中），并以该用户安装 rustup、surrealkit、Bun 和代码检出，因为第
5–6 节的 unit 就是以它运行的：二进制文件、`.env`、`data/` 以及 surrealkit 的清单文件都位于它所拥有的检出目录内 —— 这也正是这些 unit
不能使用 `DynamicUser=`/`ProtectHome=` 的原因。

因此本指南涉及两个执行环境，并且会标明每条命令属于哪一个：**`guru`** 用于构建、Schema、
`manage-tool` 以及控制台构建；**你自己具备 sudo 权限的账户**用于 systemd、nginx 和主机级的
数据存储管理。`guru` 不需要 sudo。

### 各组件的监听位置

数据存储已经可以通过前置条件第 4 节写入 `.env` 的地址访问。本地服务应只监听回环地址。在第 7
节添加唯一的 nginx server 块之前，没有任何其他组件对外暴露。

## 3. 构建

```sh
cd /path/to/proxy-guru
cargo build --release --locked -p guru-master -p manage-tool -p guru-worker
```

首次构建会编译内置的 OpenSSL 与 aws-lc，这正是 `perl`、`make` 和 `cmake` 属于前置条件的原因。下面的配置章节需要用到
`manage-tool`，所以请先把它构建出来再继续。

## 4. 配置

### 密钥文件

[前置条件](/zh-cn/guides/prerequisites/)已经创建了 `/path/to/proxy-guru/.env`，其中包含数据存储凭据（`SURREALDB_*`、
`RABBIT_USER`、`RABBIT_PASSWORD`、`AMQP_URI`）。各个 master 通过 `EnvironmentFile=` 读取同一个文件，因此把它们额外需要的内容追加进去：

<Steps>

1. 生成 master key。它会静态加密所有 DNS 提供商令牌、ACME 账户密钥和证书私钥，一旦丢失就无法恢复这些内容：

   ```sh
   ./target/release/manage-tool generate-master-key   # needs no database
   ```

2. 把下面几行追加到已有的 `.env` 中：

   ```sh
   # /path/to/proxy-guru/.env  (append)
   GURU_MASTER_KEY=<manage-tool generate-master-key>
   GURU_DASHBOARD_GRPC_ADDR=127.0.0.1:50051
   GURU_WORKERS_GRPC_ADDR=127.0.0.1:50052
   GURU_LOG_LEVEL=info
   ```

3. 锁好权限：`chmod 600 .env`。

</Steps>

`GURU_WORKERS_GRPC_ADDR` 特意设为回环地址：只有 nginx 才应该访问明文的 Worker API。`GURU_MASTER_KEY` 也特意只能通过环境变量提供
—— 它没有对应的命令行参数，因为 argv 在进程列表中是可见的。

### 建立数据库 Schema

数据存储已经按前置条件启动，但内容是空的，而 master 不允许在空数据库上启动。现在就应用 Schema 并写入模块配置种子数据，参照
**[建立数据库 Schema](/zh-cn/guides/setup-database-schema/)** —— 以 `guru` 身份在检出目录中执行，使用它已经持有的凭据：

```sh
cd /path/to/proxy-guru
set -a; . ./.env; set +a       # the credentials you wrote above

sk() {
  surrealkit --host ws://127.0.0.1:8000 --ns guru --db guru \
    --user root --pass "$SURREALDB_PASSWORD" "$@"
}
sk setup                                            # once per database
sk rollout plan --name initial_schema               # then lint / start / complete
```

那篇文章中有一点在这里的处理方式不同：后续再做 Schema 变更时，`complete` 要等到第 5–6 节中重新构建的 master 已经运行并验证通过之后再执行。它写在
`database/` 下的清单与快照会留在这台主机上（它们是按环境划分、被 gitignore 的状态数据）—— 请和 `.env` 一起备份。

最后执行同一篇文章中的配置种子命令：

```sh
(set -a; . ./.env; set +a; ./target/release/manage-tool config seed)
# seeded auth
# seeded orchestration
```

### 内部 CA 与第一个管理员

系统没有自助注册：第一个账户直接针对数据库创建，这会特意绕过 RBAC，因为此时还不存在任何管理员。使用 TLS 或 QUIC 的中继链路还需要先建立内部
CA，其 Pod 才能派生配置。

```sh
(set -a; . ./.env; set +a; ./target/release/manage-tool orchestration init-ca)
(set -a; . ./.env; set +a; ./target/release/manage-tool create-admin \
    --email admin@example.com --password '<strong password>')
# Created admin account auth_account:uz0ih3b30nrekqzs1h1y
```

`init-ca` 需要 `GURU_MASTER_KEY`（由 `.env` 提供），它会打印 CA 证书，把所有包含 TLS/QUIC
中继的画布标记为需要重新派生，并且拒绝重复执行。

## 5. systemd 下的 master

一个模板 unit，每种模式一个实例，直接从检出目录运行二进制文件并读取仓库中的 `.env`。两个 unit 都以
[部署用户](#部署用户)中的 `guru` 用户运行，该用户拥有这个检出目录 —— 这也是这里不使用
`DynamicUser=`/`ProtectHome=` 的原因：它们会把服务需要的二进制文件、`.env` 和数据目录都屏蔽掉。

```ini
# /etc/systemd/system/guru-master@.service
[Unit]
Description=guru-master (%i)
After=network-online.target docker.service
Wants=network-online.target
# Never rate-limit Restart=always: the datastores may come up later than we do.
StartLimitIntervalSec=0

[Service]
Type=simple
User=guru
Group=guru
WorkingDirectory=/path/to/proxy-guru
EnvironmentFile=/path/to/proxy-guru/.env
Environment=GURU_WORKER_MODE=%i
ExecStart=/path/to/proxy-guru/target/release/guru-master
Restart=always
RestartSec=3s
TimeoutStopSec=30s
NoNewPrivileges=true
PrivateTmp=true
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
```

安装和启动 unit 属于运维操作 —— 请**在你具备 sudo 权限的账户中**执行这一段：

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now guru-master@dashboard_grpc guru-master@workers_grpc \
                            guru-master@consumer guru-master@cron
journalctl -u 'guru-master@*' -n 20
```

当 broker 连接断开时，`consumer` 和 `cron` 会以非零状态退出；负责自愈的正是 `Restart=always`，所以请保留它。

代码变更后的重新部署要用两个 shell：以 `guru` 身份构建，以运维账户重启。

```sh
sudo -iu guru bash -lc 'cd /path/to/proxy-guru && \
  cargo build --release --locked -p guru-master -p manage-tool -p guru-worker'
sudo systemctl restart 'guru-master@*'
```

## 6. systemd 下的控制台

以 `guru` 身份用 Bun 构建，并强制所有子进程都使用 Bun —— SvelteKit 的构建后处理步骤需要
`Promise.withResolvers`，而 Node 20 没有这个 API —— 运行 adapter-node 的产物时同样使用 Bun：

```sh
bun install --frozen-lockfile --filter guru-frontend
cd typescript/guru-frontend && NODE_ENV=production bun --bun run build
```

```ini
# /etc/systemd/system/guru-frontend.service
[Unit]
Description=guru dashboard (SvelteKit adapter-node)
After=network-online.target guru-master@dashboard_grpc.service
Wants=network-online.target
StartLimitIntervalSec=0

[Service]
Type=simple
User=guru
Group=guru
WorkingDirectory=/path/to/proxy-guru/typescript/guru-frontend
# No EnvironmentFile: the dashboard must not inherit the database credentials.
Environment=NODE_ENV=production
Environment=HOST=127.0.0.1
Environment=PORT=3100
Environment=GURU_GRPC_URL=127.0.0.1:50051
Environment=PROTOCOL_HEADER=x-forwarded-proto
Environment=HOST_HEADER=x-forwarded-host
Environment=ADDRESS_HEADER=x-forwarded-for
ExecStart=/home/guru/.bun/bin/bun build/index.js
Restart=always
RestartSec=3s
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

然后再次以运维身份执行：

```sh
sudo systemctl enable --now guru-frontend
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3100/   # 303 → /auth
```

`ExecStart` 必须是*该用户自己的* Bun 的绝对路径（`sudo -iu guru command -v bun`）；systemd 不会做任何 `PATH`
查找。前端有变更时，重新构建并执行 `sudo systemctl restart guru-frontend`。

## 7. nginx：把控制台和 Worker API 放在同一个主机名下

gRPC 没有路径前缀的概念：每次调用都是 `POST /<package>.<Service>/<Method>`，而 Worker 的服务名是
`guru.orchestration.agent.WorkerAgent`。因此 nginx 可以按这个前缀做路由，让控制台和 Worker API 共用一个 server
块。最长前缀优先匹配，所以 gRPC 的 location 永远不会落到控制台那个 location 上。

`grpc_pass` 需要 nginx ≥ 1.13.10 且带 `http_v2_module`，TLS 需要 `http_ssl_module`；第 2 节中 Debian/Ubuntu、Fedora 和
Arch 的软件包都同时编译了这两个模块。另外唯一需要的前置配置，是一个 `http` 层级、用于 WebSocket 升级的 `map`：

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
```

server 块如下，使用你已经为该主机名准备好的证书：

```nginx
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;                 # nginx ≥ 1.25.1; older builds: `listen 443 ssl http2;`
    server_name guru.example.com;

    ssl_certificate     /etc/letsencrypt/live/guru.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/guru.example.com/privkey.pem;

    # ---- worker agent API: TLS terminated here, plaintext h2c to the master.
    location ^~ /guru.orchestration.agent.WorkerAgent/ {
        grpc_pass grpc://127.0.0.1:50052;
        grpc_connect_timeout 5s;
        # WatchConfig is a server stream that may be silent for hours; ReportHealth a
        # client stream carrying one message per 15 s. The grpc_* defaults are 60 s.
        grpc_read_timeout 7d;
        grpc_send_timeout 7d;
        grpc_socket_keepalive on;
        # ReportHealth is one request body that grows for the life of the session;
        # nginx counts it cumulatively, so any limit would eventually 413 the stream.
        client_max_body_size 0;
        # Gap allowed between two ReportHealth frames (4 missed reports). With nginx
        # in the path this is what bounds dead-worker detection.
        client_body_timeout 60s;
        grpc_set_header x-api-key     $http_x_api_key;
        grpc_set_header x-refresh-key $http_x_refresh_key;
        grpc_set_header X-Real-IP     $remote_addr;
    }

    # ---- dashboard. `^~` keeps any regex locations in the same block (static
    # asset caching rules, PHP handlers) from capturing /_app/immutable/*.
    location ^~ / {
        proxy_pass http://127.0.0.1:3100;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Forwarded-Host  $http_host;   # $host drops the port
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header Upgrade           $http_upgrade;
        proxy_set_header Connection        $connection_upgrade;
        proxy_cache off;          # in case a global proxy_cache is configured
        proxy_buffering off;      # SvelteKit streams responses
        proxy_redirect off;
        proxy_connect_timeout 5s;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}
```

nginx 同样属于 root 的范畴 —— 整个第 7 节都在运维账户中执行：

```sh
sudo nginx -t && sudo systemctl reload nginx
```

其中三个配置项各值得说明一句：

- **`grpc_read_timeout 7d`。** 如果用 60 秒的默认值，nginx 每分钟就会结束一次 `WatchConfig`，Worker
  随之重新注册，刷新密钥每分钟轮换一次 —— 这等于自己制造了一场重新注册风暴。
- **`client_max_body_size 0`。** `ReportHealth` 是客户端流式 RPC：一个 HTTP/2
  请求，其请求体在整个会话期间每上报一次就增长一条消息。nginx 是按累计量来限制请求体大小的，所以任何限制都会在几周后重置健康流。
- **`client_body_timeout 60s`。** master 通过自身连接上的 HTTP/2 PING 来检测失联的 Worker。中间加了 nginx 之后，这些 PING 由
  nginx 应答，因此一个没有发 FIN 就消失的 Worker，只能在 nginx 让健康上报的请求体超时之后才被发现 ——
  大约一分钟，而不是二十秒。这是可以接受的；要调整的常量就在这里。

严格来说，只有控制台 location 上的 `Origin`/转发头是正确性所必需的（参见
[控制台警告](/zh-cn/guides/deploy-with-docker/#9-运行控制台)）；其余配置是用来维持长连接流的。

## 8. 验证

按顺序逐项执行——每一项都会独立地明确报错。请使用服务管理器或托管服务商提供的健康检查确认
数据存储。下面前两条命令只是本地原生安装的示例；远程服务应跳过它们。其余检查在一个全新的运维
shell 中执行；属于服务账户的检查用 `sudo -iu guru` 包裹。

```sh
# 1. Local datastore examples only; use provider health checks for remote services
surreal is-ready --endpoint http://127.0.0.1:8000
rabbitmq-diagnostics -q ping

# 2. Schema (guru: it owns the manifests under database/)
sudo -iu guru bash -lc 'cd /path/to/proxy-guru && set -a && . ./.env && set +a && \
  surrealkit --host "$SURREALDB_HOST" --ns "$SURREALDB_NAMESPACE" --db "$SURREALDB_NAME" \
    --user "$SURREALDB_USER" --pass "$SURREALDB_PASSWORD" status'
#   → the rollout you applied, [completed]

# 3. Control plane: one banner per mode, no restart loop
journalctl -u 'guru-master@*' -n 20

# 4. Dashboard behind nginx (303 to /auth)
curl -s -o /dev/null -w '%{http_code}\n' https://guru.example.com/

# 5. gRPC reaches the master through TLS: HTTP/2 200 with a grpc-status header
curl --http2 -sS -D - -o /dev/null -X POST -H 'content-type: application/grpc' \
  --data-binary '' https://guru.example.com/guru.orchestration.agent.WorkerAgent/Register

# 6. A worker with a bogus key must be rejected by the master, not by TLS or nginx
sudo -iu guru bash -lc 'cd /path/to/proxy-guru && GURU_API_KEY=bogus \
  ./target/release/guru-worker --master https://guru.example.com \
    --server probe --state-dir /tmp/gw'
#   ERROR guru_worker::agent: agent session ended error=... "Missing identity"
```

然后用第 4 节创建的账户在 `https://guru.example.com/` 登录 —— 这是唯一能端到端走通控制台 → 运维 API → SurrealDB
的检查。如果其他检查都通过而登录返回 `Forbidden`，说明第 7 节中的转发头配置有误。

最后，在控制台中创建一台服务器和一个 API 密钥，然后用 `--master https://guru.example.com`
启动一个真实的 Worker。观察它超过三分钟 —— 这才能证明 nginx 的 60 秒默认值确实被覆盖了 ——
再推送一次画布变更，看它的日志里出现 `applied config revision`。

`https://` 这种形式要求 Worker 是从包含 Agent TLS 支持的检出构建出来的（`bin/guru-worker` 启用 tonic 的 `tls-ring` +
`tls-native-roots`）；它会用主机的 `ca-certificates` 校验证书，并发送自己的 HTTP/2 keepalive ping。在私有网络中，
`http://host:50052` 仍然像以前一样可用。
