## Crates

| Crate | Role |
|---|---|
| `bin/guru-master` | Control plane. One binary, five modes (`--mode`): `dashboard_grpc` (operator API), `workers_grpc` (worker API + config-view poller), `consumer` (Iggy event handlers — canvas derivation and the notification fan-out), `notifier` (notification delivery, exactly one instance), `cron` (all six periodic jobs, in-process). ## Everything is a Processor

`kanau::processor::Processor` is **state plus an async function**:

```text
Processor = State + async fn(Input) -> Result<Output, Error>
```

A `Processor` is a `Clone`-able struct that owns its dependencies and implements `Processor<Input>`
once per operation. Every business operation, event handler and cron job is modelled as an input
struct plus one `Processor` impl. Database queries are the one variation: a query is an input
struct implementing wakuwaku-entity's `Query` and `Execute`, and the database handle
`base::db::Db` is the `Processor` that runs it — so a service still calls `self.db.process(query)`.

## Module anatomy

Every module crate mirrors `modules/base`:

<FileTree>

- src/
  - lib.rs declares the modules below; sets crate-wide lints
  - config.rs typed configuration (one `app_config` row, JSON document)
  - utils/ small, dependency-light helpers
  - entities/ persistence layer
    - db/ PostgreSQL row types + sqlx queries
    - redis/ Redis key/value types (rkyv-encoded)
  - services/ business logic (stateful Processors)
  - events/ Iggy event payloads + topics
  - hooks/ background reactors (Iggy event handlers, cron jobs, loggers)
  - rpc/ gRPC service implementations (transport edge)

</FileTree>

| You are writing… | Put it in… |
|---|---|
| A PostgreSQL query or a table row type | `entities/db` |
| A Redis-cached value or ephemeral token | `entities/redis` |
| A use case that combines queries and rules | `services` |
| A message other modules react to | `events` |
| A reaction to an event / a periodic job / an audit log | `hooks` |
| A gRPC endpoint implementation | `rpc` |
| A typed setting an operator can change | `config` |
| A pure helper with no runtime deps | `utils` |

## Layer rules

- **Dependency direction:** `rpc → services → entities/events/config`. A feature module may depend
  on `base`, but `base` must not depend on a feature module, and modules must not reach into each
  other's internals — they communicate via gRPC or Iggy events.
- **`entities/db`:** one submodule per table or aggregate; a row struct; the id wrapped by
  `table_record!(NameId, "table")`, an enum stored as text spelled once by `text_enum!`. Each query
  is an input struct implementing wakuwaku-entity's `Query` — its `Effect` names the tables it
  touches, `Read<tables::X>` / `Write<tables::X>` over the per-crate table markers in
  `entities/db/tables.rs` — and `Execute<PgSource>`; `base::db::Db`
  (= `wakuwaku::entity::Db<PgSource, ReadWrite>`) runs it; `Execute` returns `base::db::Error`.
  Every multi-statement transaction is a public `TxFlow` state machine (`XFlow::new(input)`) whose
  steps `tx.run` plain or helper queries in order and end with `base::db::commit` or
  `base::db::rollback` (a lost fence: `Error::Conflict`); a conditional write that matched nothing
  commits its empty result. A flow is not a query: the caller runs
  `db.process(Transaction(XFlow::new(..)))` and folds `TxOutput::Committed` / `RolledBack` itself,
  and a lost `COMMIT` answer becomes `OrchestrationError::CommitUnknown` (gRPC `UNKNOWN`). Snapshot
  reads are read-only flows at `RepeatableRead`. Every statement goes through sqlx's `query!`
  family, so the SQL is checked against the schema at compile time; behaviour is still covered by
  integration tests against a real database (`#[sqlx::test]`).
- **`services`:** `Clone` structs owning their dependencies, one `Processor` impl per operation,
  returning domain types — never protobuf types.
- **`events`:** the payload, rkyv-encoded with `RkyvMessageSer/De`, implementing `EventBody` and
  `Event` (`TYPE_TAG`, a `Key: PartitionKey` whose `SUPER_PARTITION_NAME` is the topic, `Algebra`,
  `atomic_ordering`). Each event's doc names its publisher, consumer, topic and tag. `base::events`
  holds the shared topology: one stream `guru` (`STREAM`), `PARTITIONS` per topic, and
  `ensure_topology`, which every mode runs at startup. Events are the only sanctioned asynchronous
  channel between modules.
- **`hooks`:** Iggy `EventHandler<E>` impls (plus `ServiceCreation`) for reactions to events, and
  `CronJob` impls — a `Processor<CronTick>` with a fixed `INTERVAL` — for periodic work. A cron job
  claims its run (one `orchestration_job_run` row, compare-and-set) with `ClaimJobRun` before
  working, so several `cron` processes run each pass once per configured interval fleet-wide.
  Handlers are at least once: a handler failing on an unavailable database is retried in place,
  other database errors and conflicts send the key to the `retry_<topic>` topic, and anything else
  is dropped and logged.
- **`rpc`:** thin adapters — decode request, call a service, encode reply. No business logic.
- **Errors:** each module has its own error enum (`AuthError`, `OrchestrationError`,
  `NotifyError`) at the service/hook boundary, converting into `tonic::Status` for gRPC and into an
  Iggy `HandleError` class for handlers; `base::db::Error` inside `entities/db`, which converts with
  `?` at the service layer. It separates a database that did not answer (`UNAVAILABLE`) from a
  refusal, and `Error::Conflict` from both: a transaction that definitely did not commit.
- **Lints:** crate-level `deny(clippy::unwrap_used)`, `expect_used` and `panic`. No panics on the
  request path.
- **Tracing:** `#[tracing::instrument(skip_all, err)]` with an explicit span `name` —
  `Query:<Input>` for entities (`Transaction:<Input>` on a flow's `step`), `Service:<Input>` for services,
  `Hook:<Input>` for event handlers and cron jobs. gRPC handlers need none; the trait-method name
  already labels the span. Tracing is plain `tracing` + `tracing-subscriber`.

## PostgreSQL notes

- Compare a nullable column with `IS DISTINCT FROM`, not `<>`: `<>` against `NULL` is `NULL`, which
  is not `true`, so a fence written with it silently never matches.
- A JSON `null` inside a `jsonb` document is not SQL `NULL`; `jsonb_typeof` tells them apart.
- Statements are compile-time checked: columns are spelled out (no `SELECT *`), a column whose Rust
  type is a `table_record!` id, a `text_enum!` or a `Json<T>` is aliased with it
  (`id AS "id: CanvasId"`), a parameter of such a type is passed as `self.id as _`, and SQL longer
  than five lines lives in `<crate>/sql/*.sql` behind `query_file!`. Nothing builds SQL at runtime.
- `.sqlx/` holds the committed offline query data, so a build needs no database
  (`SQLX_OFFLINE=true` in the image build). Regenerate it with
  `cargo sqlx prepare --workspace -- --all-targets` against a migrated database whenever a statement
  or the schema changes; `-- --all-targets` is what puts the tests’ own statements in there too.
- The schema is a migration, never an edit: `guru-master` applies what is pending at startup under
  an advisory lock, so a fleet starting together applies each one exactly once.
