Proxy Guru はマネージド TCP/TLS プロキシファブリックです。オペレーターは**キャンバス**上でトポロジーを
設計し、コントロールプレーンはそのトポロジーからサーバーごとに1つの設定を導出します。データプレーンの
ワーカーは、新しいリビジョンを自動的に取得します。

## 2つのプレーン

**コントロールプレーン** — `bin/guru-master`。`--mode`（`GURU_WORKER_MODE`）で選択する4つのモードを
備えた1つのバイナリです。

| モード | 責務 |
|---|---|
| `dashboard_grpc` | フロントエンドが利用するオペレーター API |
| `workers_grpc` | ワーカー API と config-view ポーラー |
| `consumer` | すべての AMQP フック: 導出フックと5つの定期ジョブすべて |
| `cron` | クロック: 実行時刻を迎えた定期ジョブごとに1つの実行シグナルを発行 |

後者2つは、意図的に1つのジョブを半分に分けたものです。`cron` は設定を読み込まず、データベース接続も
開きません。シグナルを受け取った `consumer` が実行権を獲得して処理を行うため、スイープ、生存確認、
証明書更新は、キャンバスの編集とまったく同じようにスケールしフェイルオーバーします。4つのモードは
いずれもブローカーを必要とします。

**データプレーン** — `bin/guru-worker`。リスナーを終端してトラフィックを転送します。TOML ファイルから
スタンドアロンで動作する（`SIGHUP` でリロード）か、エージェントモードでマスターから設定をストリーミング
します。

ワーカーの設定モデル自体は `lib/guru_worker_config` にあり、両方のプレーンで共有されています。マスターが
それを導出し、ワーカーが消費します。ファイルから駆動されるワーカーは、コントロールプレーンをまったく
必要としません — [独立ワーカーのデプロイ](/ja/guides/independent-worker/) を参照してください。

## トポロジーの用語

各フォワーディングは**リスナー**と**宛先**を持ちます。

- リスナー: `raw`、`tls`、またはインバウンドリレー。
- 宛先: 直接の**エグジット**、TLS-over-TCP または QUIC による他ノードへの**リレー**、あるいは
  **ロードバランス**グループ。

PROXY プロトコル v1 と v2 は両端でサポートされています。

### サーバー、ポッド、アドレス

**サーバー**とは `guru-worker` を実行しているマシンです。**ポッド**とは1つのサーバー上の1つの待ち受け
ポート、つまり1つのルールのソケットです。イングレスのルールは、自分で追加するポッド（たとえば SOCKS
エントリ用の `1080`）です。ポッドはデフォルトでホストのすべてのアドレスにバインドしますが、IPv4 のみに
制限したり、1つのインターフェイスに固定したりできます。

すべてのサーバーには**ユニバーサルポッド**も付属します。これは、ルールごとにポッドを描かなくても他の
サーバーのトラフィックが着地する場所です。イングレスのポッドを**ロードバランス（分配）**ノードの
チャネルハンドルに接続し（すべてに対して1つのストラテジーと1つのリレープロトコル）、それをトランジット
サーバーのユニバーサルポッドへバンドルし、さらにそれらを**ロードバランス（集約）**ノードへバンドル
します。集約ノードはルールごとに色分けされた入力を1つずつ増やしていき、エグジットへ接続できます。各
ルールは経路全体を通じて独自の色を持つ*チャネル*であり、バンドルはすべてのチャネルを運ぶ1本の太い線
です。裏側では、コントロールプレーンが実際のポッド、リレー、ロードバランサー（「レーン」）を生成します
— 各トランジットサーバー上の各ルールの着地ポッドは、そのサーバーのパネルに編集可能なポートとして
表示されます。ルールを決めるのはあなたです: 分配ノードの **メンバー** はそれが分かれる先のバンドルで、
トランジットサーバーごとに 1 つ、名前はあなたが付けます（AWS が 4 台なら 4 メンバー、5 台目は 1 つ
足すだけ）。集約ノードのメンバーは、それが合流させるバンドルです。*内向きに*
バンドルされた分配ノードはすべてを再度ファンアウトします（2段目、あるいはネストしたストラテジー）。
また、1ホップでバランシングが不要なルールであれば、エントリポッドをサーバーのユニバーサルポッドへ直接
描くこともできます。

サーバーの IP を手で入力する人はいません。ワーカーは登録時（および変更があれば以後1分ごとに）自身の
パブリック IPv4/IPv6 とインターフェイスのアドレスを報告し、マスターは登録がどこから来たかを記憶します。
他のサーバーはそこから得られたアドレスにダイヤルします — IPv4 が優先です。学習されたアドレスが自分の
ネットワークにとって正しくない場合（NAT、オーバーレイなど）にのみサーバー側でアドレスを固定し、特定の
ポッドだけ別の経路で到達させたい場合はそのポッド単位で固定してください。

## モジュール

ビジネスロジックは `modules/` にあり、機能ごとに1つのクレートです。

| モジュール | 範囲 |
|---|---|
| `auth` | アカウント、セッション、API キー、RBAC |
| `orchestration` | キャンバス、サーバー、ノード、エッジ。トポロジー検証、設定の導出、ワーカーのロールアウト |
| `notify` | 通知モジュール — `base` からスキャフォールドされたのみで、まだ未実装 |
| `base` | 共有の基盤と、すべてのモジュールが踏襲する構成 |

## スタック

Tokio 上の Rust 2024、[`wakuwaku`](https://crates.io/crates/wakuwaku) +
[`kanau`](https://crates.io/crates/kanau)（すべては `Processor`）、Tonic による gRPC、ストレージには
SurrealDB（スキーマは `database/`、surrealkit で管理）、オペレーター API のライブ `Watch*` ストリームには
Redis の pub/sub、モジュール間イベントには AMQP、トレーシングには OpenTelemetry、そして1つの生成済み API
クライアントを共有する `typescript/` 配下の Bun ワークスペース。
