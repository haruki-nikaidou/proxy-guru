Proxy Guru はマネージド TCP/TLS プロキシファブリックです。オペレーターは**キャンバス**上でトポロジーを
設計し、コントロールプレーンはそのトポロジーからサーバーごとに1つの設定を導出します。データプレーンの
ワーカーは、新しいリビジョンを自動的に取得します。

## 2つのプレーン

**コントロールプレーン** — `bin/guru-master`。`--mode`（`GURU_WORKER_MODE`）で選択する4つのモードを
備えた1つのバイナリです。

| モード | 責務 |
|---|---|
| `dashboard_grpc` | フロントエンドが利用するオペレーター API |
| `workers_grpc` | ワーカー API と config-view ポーラー |
| `consumer` | すべての AMQP フック: 導出フックと6つの定期ジョブすべて |
| `cron` | クロック: 実行時刻を迎えた定期ジョブごとに1つの実行シグナルを発行 |

後者2つは、意図的に1つのジョブを半分に分けたものです。`cron` は設定を読み込まず、データベース接続も
開きません。シグナルを受け取った `consumer` が実行権を獲得して処理を行うため、スイープ、生存確認、
証明書更新は、キャンバスの編集とまったく同じようにスケールしフェイルオーバーします。4つのモードは
いずれもブローカーを必要とします。

**データプレーン** — `bin/guru-worker`。リスナーを終端してトラフィックを転送します。TOML ファイルから
スタンドアロンで動作する（`SIGHUP` でリロード）か、エージェントモードでマスターから設定をストリーミング
します。

ワーカーの設定モデル自体は `lib/guru_worker_config` にあり、両方のプレーンで共有されています。マスターが
それを導出し、ワーカーが消費します。ファイルから駆動されるワーカーは、コントロールプレーンをまったく
必要としません — [独立ワーカーのデプロイ](/ja/guides/independent-worker/) を参照してください。

## トポロジーの用語

キャンバスツリーは 1 つの**ポッドグラフ**を持ちます。

- **サーバー**は `guru-worker` を実行しているマシンであり、その上で動くポッドの集合です。
- **ポッド**は 1 つのサーバー上の 1 つの待ち受けです。*クライアント*ポッドはクライアントからの接続を直接受け
  （生の TCP、または ACME 証明書で TLS を終端。PROXY の受信も可能）、*リレー*ポッドは他のポッドが TCP、TLS、
  QUIC で中継してくるトラフィックを受けます。
- **エグジット**はトラフィックがファブリックを出ていく外部の `host:port` です。
- **エッジ**はポッドのトラフィックの転送先 1 つです — リレーポッドへ（そのポッドの待ち受け方でダイヤル）、
  またはエグジットへ。
- ポッドの**ルート**は自分のエッジの間で、重みによる負荷分散や段ごとのフェイルオーバーを行い、自由に入れ子に
  できます。

たとえば 10 個のルールが 1 台に入ってきて 4 台のトランジットサーバーに分散させたい場合、10 個のクライアント
ポッドがそれぞれ各トランジットサーバー上の自分専用のリレーポッドへ 4 本のエッジを持ち、そのリレーポッドの
エッジがエグジットへ向かいます。キャンバスは同じ選び方をする 4 つの負荷分散を 1 つのスプリッターとして、
40 本のエッジを数本のバスとして描きます。すべてのカードについては[ノード](/ja/reference/nodes/)を、グラフの
描き方と編集の仕方については[キャンバス](/ja/reference/canvas/)を参照してください。

ポッドはデフォルトでホストのすべてのアドレスにバインドしますが、IPv4 のみに制限したり、1つのインターフェイスに
固定したりできます。ポートを指定せずに保存したポッドには、40000〜59999 の空いているポートが割り当てられます。

サーバーの IP を手で入力する人はいません。ワーカーは登録時（および変更があれば以後1分ごとに）自身の
パブリック IPv4/IPv6 とインターフェイスのアドレスを報告し、マスターは登録がどこから来たかを記憶します。
他のサーバーはそこから得られたアドレスにダイヤルします — IPv4 が優先ですが、エッジ自身が IPv4 か IPv6 を
指定することもできます（バスならそのすべてのエッジに一度に設定できます）。学習されたアドレスが自分の
ネットワークにとって正しくない場合（NAT、オーバーレイなど）にのみサーバー側でアドレスを固定し、特定の
ポッドだけ別の経路で到達させたい場合はそのポッド単位で固定してください。

## モジュール

ビジネスロジックは `modules/` にあり、機能ごとに1つのクレートです。

| モジュール | 範囲 |
|---|---|
| `auth` | アカウント、セッション、API キー、RBAC |
| `orchestration` | キャンバス、サーバー、ポッドグラフ。グラフの検査、設定の導出、ワーカーのロールアウト |
| `notify` | ワークスペースごと・アカウントごとの通知設定。ヘルス変化のメールと Telegram での配信（[通知](/ja/features/notifications/)） |
| `base` | 共有の基盤と、すべてのモジュールが踏襲する構成 |

## スタック

Tokio 上の Rust 2024、[`wakuwaku`](https://crates.io/crates/wakuwaku) +
[`kanau`](https://crates.io/crates/kanau)（すべては `Processor`）、Tonic による gRPC、ストレージには
PostgreSQL（sqlx、マイグレーションは `migrations/`）、オペレーター API のライブ `Watch*` ストリームには
Redis の pub/sub、モジュール間イベントには AMQP、トレーシングには OpenTelemetry、そして1つの生成済み API
クライアントを共有する `typescript/` 配下の Bun ワークスペース。
