2 つのデプロイガイド — [Docker でデプロイ](/ja/guides/deploy-with-docker/) と
[ネイティブにデプロイ](/ja/guides/deploy-natively/) — はどちらもこのページから始まります。ここでは外部の
依存コンポーネントとオペレーター用ツールを準備します。この後に読むデプロイガイドは、コントロールプレーンを
それらに接続するだけです。

それぞれの方式が実際に必要とするもの:

| | Docker でデプロイ | ネイティブにデプロイ |
|---|---|---|
| SurrealDB ≥ 3.2 | 必要 | 必要 |
| RabbitMQ 3.13/4.x | 必要 | 必要 |
| Docker Engine + Compose | 必要（公開済みアプリケーションイメージの実行に使用。データストアへの使用は任意） | 不要 |
| `surrealkit` | 必要 | 必要 |
| Rust ツールチェーン + `protoc` | 必要 — `manage-tool` はイメージとして公開されていません | 必要 — すべてのバイナリをビルドします |
| C ツールチェーン、`make`、`cmake` | 必要 — `manage-tool` は証明書関連のクレート群（aws-lc 上の `instant-acme`/`rcgen`）を取り込み、同梱の C ソースのビルドにコンパイラーと cmake が必要です | 必要 — 理由は同じです |
| `perl` | 不要 | 必要 — `guru-worker` は同梱の OpenSSL をビルドし、その構成は perl スクリプトが行います |
| Bun | 不要 | 必要（ダッシュボードのビルドと実行） |
| ホスト名 + TLS 証明書 | 必要 | 必要 |
| Redis | 不要 | 不要 |

Redis はモジュールの雛形に登場しますが、現時点でこれに接続するバイナリはありません。用意する必要はありません。

## 1. Docker Engine と Compose（イメージデプロイのみ）

Docker が必要なのは、イメージデプロイを選ぶ場合だけです。ネイティブデプロイに Docker は不要であり、
SurrealDB と RabbitMQ は直接インストールするか、マネージドサービスまたは別の実行方法を利用できます。
ディストリビューションを一度選べば、このページのすべてのタブが連動します。

<TabItem label="Debian">

```sh

                    openssl nginx curl unzip git
```

</TabItem>
<TabItem label="Ubuntu">

```sh

                    openssl nginx curl unzip git
```

</TabItem>
<TabItem label="Fedora / RHEL">

```sh

                    openssl nginx curl unzip git
```

</TabItem>
<TabItem label="Arch">

```sh
sudo pacman -S --needed base-devel cmake protobuf openssl nginx curl unzip git
```

`base-devel` には `gcc`、`make`、`pkgconf`、`perl` が既に含まれています。

</TabItem>
</Tabs>

いずれも飾りではなく、このワークスペースが実際に依存しているものです:

| パッケージ | 必要な理由 |
|---|---|
| `protoc`（`protobuf-compiler`、Arch では `protobuf`） | `lib/rpguru_sdk` のビルドスクリプトが `tonic-prost-build` で `proto/` をコンパイルし、その内部で `protoc` を呼び出します。`manage-tool` を含むすべてのバイナリがこのクレートに依存するため、`protoc` がないとビルドが失敗します。`PATH` にない場合は `PROTOC=/path/to/protoc` を設定してください。 |
| C コンパイラー、`make` | どちらの方式でも `manage-tool` をビルドし、これは `orchestration` モジュール経由で証明書関連のクレート群に到達します。そのうちいくつか（`aws-lc-sys`、`ring`、`zstd-sys`）は同梱の C ソースをコンパイルします。 |
| `cmake` | `aws-lc-sys` は同梱ソースを cmake でビルドするため、`manage-tool` をビルドする環境では必ず必要です。 |
| `perl` | `guru-worker` は `vendored` フィーチャーで OpenSSL をリンクします。OpenSSL は同梱のソースツリーからコンパイルされ、その `Configure` は perl スクリプトです。ネイティブデプロイのみで必要です。 |
| `pkgconf` / `pkg-config` | 上記の `*-sys` クレート群のビルド依存です。 |
| `openssl` | デプロイガイドでは `openssl rand -hex 32` でパスワードや鍵を生成します。 |
| `unzip` | Linux 上の Bun インストーラーが必要とします。 |
| `nginx` | ダッシュボードの TLS を終端し、ネイティブガイドではワーカー API の TLS も終端します。最近のビルドであれば `http_ssl_module` と `http_v2_module` を備えており、これが `grpc_pass`（nginx 1.13.10 以降）の要件です。 |

`libssl-dev`/`openssl-devel` や `libprotobuf` の開発パッケージは不要です。Rust のビルドがそれらに必要とする分は、
すべて同梱されています。

## 3. Rust、surrealkit、Bun

ここまでの作業には root が必要でした。このセクションの作業はすべて、**チェックアウトを所有する**アカウントに
属します。そしてそのアカウントはデプロイ方式によって異なります:

<Tabs syncKey="deployment">
<TabItem label="ネイティブデプロイ">

コントロールプレーン、ダッシュボード、およびビルドしたものはすべて 1 つの非特権サービスユーザーとして動作します。
`sudo useradd --create-home --shell /bin/bash guru` でユーザーを作成し、`sudo -iu guru` でそのシェルに
入ってください。このセクションの残りは `guru` として実行します。このシェルからツールチェーンをインストールすれば、
systemd から見つけられるサービスユーザーのホームに配置されます。

ネイティブガイドでは全体を通して `guru` と `/home/guru` を使います（ユニットの `User=`/`Group=` と Bun の
パスも同様）。別の名前を使う場合は一貫して置き換えてください。データストアをコンテナで実行する場合でも、
サービスユーザーに Docker やその他のホスト管理権限を与えては**いけません**。

</TabItem>
<TabItem label="イメージデプロイ">

チェックアウトから常駐するものは何もありません。`manage-tool` をビルドし、スキーマファイルを置いておくだけなので、
自分のオペレーターアカウントが適切です。Bun はまったく必要ありません。

</TabItem>
</Tabs>

<Steps>

1. **Rust** は [rustup](https://rustup.rs/) で導入します。ワークスペースは `rust-toolchain.toml` で
   ツールチェーン（チャンネル `1.98`）を固定しており、最初の `cargo` 実行時に rustup がその固定版を
   インストールします。ディストリビューションの `rust` パッケージで代替しないでください。古いコンパイラーでは
   edition 2024 をビルドできません。

   ```sh wrap frame="none"
   curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
   . "$HOME/.cargo/env"
   ```

2. **surrealkit** は
   [データベーススキーマのセットアップ](/ja/guides/setup-database-schema/)で使うスキーマツールです。
   `cargo install surrealkit`（cargo-binstall がある場合は `cargo binstall surrealkit`）で
   インストールしてください。このガイドはバージョン 0.7.0 を対象にしています。インストール済みの
   バージョンを確認します:

   ```sh wrap frame="none"
   surrealkit --version
   ```

3. **チェックアウト。** どちらのガイドでも `database/` 以下のスキーマファイルと `manage-tool` が必要です。
   イメージガイドでは Compose ファイルも使います。ネイティブデプロイでこのファイルを使うのは、任意の
   コンテナ構成を選んだ場合だけです。これらはアプリケーションイメージには含まれていません。

   ```sh wrap frame="none"
   git clone \
     https://github.com/haruki-nikaidou/proxy-guru.git /path/to/proxy-guru
   ```

4. **Bun** はネイティブデプロイのみで、ダッシュボードのビルドと実行に使います。Node はどこでも使いません。
   SvelteKit のビルド後処理は `Promise.withResolvers` を必要とし、Node 20 にはこれがありません。

   ```sh wrap frame="none"
   curl -fsSL https://bun.com/install | bash
   export BUN_INSTALL="$HOME/.bun"; export PATH="$BUN_INSTALL/bin:$PATH"
   ```

   インストーラーはバージョン指定（`bash -s "bun-v1.3.3"`）を受け付けるので、公開版ダッシュボードのビルドに
   使われている `oven/bun:1.3` イメージと揃えられます。Arch には `bun` パッケージもありますが、インストールに
   root が必要で、バイナリがサービスアカウントのホーム外に置かれます。

</Steps>

## 4. SurrealDB と RabbitMQ

### コントロールプレーンが求める条件

| | 要件 |
|---|---|
| SurrealDB | **3.2 以降。** 3.0 系の古いバイナリはワークスペースがリンクしているクライアントと互換性がなく、同一トランザクション内で先に書き込まれた行を読む ASSERT を正しく扱えません。その結果、実際には存在しないはずの "table does not exist" やトランザクション中断のエラーとして現れます。 |
| | **root 認証情報。** `guru-master` は `Root { username, password }` でサインインしてからネームスペースとデータベースを選択します。ネームスペースやデータベースにスコープされたユーザーではこれができません。 |
| | **永続ストレージ。** バックアップ対象のボリューム上に `rocksdb:/data/guru.db` を置きます。これはシステム内で唯一、失うと復元できない状態です。 |
| RabbitMQ | 3.13/4.x のサーバーであれば何でも構いません。コントロールプレーンは起動時に自身の exchange と永続キューを宣言するため、事前に作成しておくものはありません。デフォルト vhost のユーザーが 1 つあれば十分です。このプロジェクトでテスト済みのブローカーは RabbitMQ だけです。 |
| | URI の書式: `amqp://user:password@host:5672/` で、**末尾のスラッシュ**がデフォルト vhost を選択します。`/%2f` 形式はパーサーに拒否されます。 |
| | ブローカーは**4 つのマスターモードすべてで必須**です。定期処理はメッセージそのものであり、ブローカーが停止している間は古いキャンバスのスイープも、応答のないサーバーを `Offline` にする処理も、証明書の更新も行われません。最適化ではなく依存コンポーネントとして扱ってください。 |

:::caution[RabbitMQ 以外のブローカーはそのまま置き換えられません]
コントロールプレーンは AMQP 0-9-1 クライアントの `amqprs` と、RabbitMQ の exchange／queue 宣言の
セマンティクスを使用します。他のブローカーはテストされていません。特に Azure Service Bus は AMQP 1.0 を
使用するため、互換性があると想定してはいけません。コントロールプレーンのメッセージングの一部または全部が
失敗する可能性があります。代替ブローカーをエンドツーエンドで検証できる場合を除き、RabbitMQ を使用してください。
:::

データストアにコンテナや Docker Compose は必須ではありません。公式の
[SurrealDB インストールガイド](https://surrealdb.com/docs/running/installation)と
[RabbitMQ ダウンロードガイド](https://www.rabbitmq.com/docs/download)に従うか、マネージドサービスまたは
以下の Compose 例を使用してください。どの方法でも、上記の要件を満たす必要があります。

### 認証情報

パスワードは**URL セーフ**な形式で生成してください。ブローカーのパスワードは `AMQP_URI` に埋め込まれ、そこでは
`@`、`:`、`/`、`%` が URI の意味を変えてしまいます:

```sh
openssl rand -hex 32          # once for SurrealDB, once for RabbitMQ
```

16 進文字列であれば、クォートやパーセントエンコーディングの問題は一切起きません。どうしても記号を使いたい場合は、
`AMQP_URI` 内でパーセントエンコードしてください（`@` → `%40`、`:` → `%3A`、`/` → `%2F`、`%` → `%25`）。
SurrealDB のパスワードは argv の値として渡されるため、クォートだけで済みます。

接続用の認証情報を、コントロールプレーンが読み込むファイルに記録します。イメージデプロイ用の Compose 例も、
データストアの認証情報をこのファイルから読み込みます:

<Tabs syncKey="deployment">
<TabItem label="ネイティブデプロイ">

```sh
# /path/to/proxy-guru/.env   (chmod 600; gitignored)
SURREALDB_HOST=ws://127.0.0.1:8000
SURREALDB_USER=root
SURREALDB_PASSWORD=<first hex string>
SURREALDB_NAMESPACE=guru
SURREALDB_NAME=guru
RABBIT_USER=guru
RABBIT_PASSWORD=<second hex string>
AMQP_URI=amqp://guru:<second hex string>@127.0.0.1:5672/
```

systemd は後で `EnvironmentFile=` からこのファイルをそのまま読み込みます。systemd は `${…}` を
**展開しない**ため、`AMQP_URI` は完全な形で書き出してください。

</TabItem>
<TabItem label="イメージデプロイ">

```sh
# /srv/guru/.env   (chmod 600)
SURREAL_ROOT_USER=root
SURREAL_ROOT_PASSWORD=<first hex string>

RABBIT_USER=guru
RABBIT_PASSWORD=<second hex string>

GURU_NS=guru
GURU_DB=guru
```

先に `/srv/guru` を作成してください（`sudo mkdir -p /srv/guru`）。以下の Compose ファイルはこの `.env` の
隣に置き、イメージガイドではここに `MASTER_VERSION`、`FRONTEND_VERSION`、`GURU_MASTER_KEY` を追記します。

</TabItem>
</Tabs>

### 起動する

<Tabs>
<TabItem label="ネイティブデプロイ">

公式の [SurrealDB インストールガイド](https://surrealdb.com/docs/running/installation)と
[RabbitMQ ダウンロードガイド](https://www.rabbitmq.com/docs/download)に従って、両方のサービスを
インストールします。SurrealDB は永続ストレージ、root 認証情報、ポート `8000` のループバックリスナーを設定し、
RabbitMQ は `.env` のユーザーとパスワード、デフォルト vhost、永続ストレージ、ポート `5672` の
ループバックリスナーを設定します。オペレーティングシステムのサービスマネージャーを使って両方を起動し、
ブート時に有効化してください。

Docker Compose は任意の代替手段であり、デプロイ要件ではありません。使用する場合、リポジトリの
`docker-compose.yml` が同じループバック限定の構成を提供し、永続データを `./data/` 以下に保存します。

</TabItem>
<TabItem label="イメージデプロイ">

デプロイ用ディレクトリ（イメージガイドでは `/srv/guru`）を作成し、認証情報を持つ `.env` の隣にある Compose
ファイルに 2 つのデータストアを記述します:

```yaml
# /srv/guru/docker-compose.yml
name: guru

services:
  surrealdb:
    image: surrealdb/surrealdb:v3.2.4
    restart: unless-stopped
    command:
      - start
      - --user
      - ${SURREAL_ROOT_USER}
      - --pass
      - ${SURREAL_ROOT_PASSWORD}
      - rocksdb:/data/guru.db
    user: root
    volumes:
      - surreal-data:/data
    # Loopback only: the operator machine reaches it through an SSH tunnel.
    ports:
      - "127.0.0.1:8000:8000"

  rabbitmq:
    image: rabbitmq:4-alpine
    restart: unless-stopped
    environment:
      RABBITMQ_DEFAULT_USER: ${RABBIT_USER}
      RABBITMQ_DEFAULT_PASS: ${RABBIT_PASSWORD}
    volumes:
      - rabbit-data:/var/lib/rabbitmq
    healthcheck:
      test: ["CMD", "rabbitmq-diagnostics", "-q", "check_running"]
      interval: 10s
      timeout: 10s
      retries: 12

volumes:
  surreal-data:
  rabbit-data:
```

```sh
cd /srv/guru
sudo docker compose up -d surrealdb rabbitmq
```

マスターは後でイメージガイドの中で同じファイルに追加します。データストアが先に存在していなければならないのは、
どのマスターを起動する前にもスキーマが適用済みである必要があるからです。

</TabItem>
</Tabs>

Compose 例では、さらに重要な点が 2 つあります。`surrealdb/surrealdb` イメージは非特権ユーザーで動作し、
root 所有のボリュームやバインドマウントには書き込めないため、`user: root` が必要です。RabbitMQ は
データディレクトリをノード名 `rabbit@<hostname>` に基づいて命名するため、リポジトリの Compose ファイルは
`hostname:` を固定しています。これがないと、コンテナを作り直すたびに空のブローカーで起動してしまいます。

consumer がバインドするキューは自動的に作成されます。編集用の `guru_orchestration_canvas_dirty` に加え、
5 つの定期ジョブ用に `guru_orchestration_derive_stale_canvases`、`guru_orchestration_sweep_liveness`、
`guru_orchestration_trim_health_history`、`guru_orchestration_renew_certificates`、
`guru_orchestration_rotate_relay_certificates` が作成されます。

## 5. ホスト名と証明書

ホストを指す DNS 名 1 つと、それに対する TLS 証明書（`certbot`、自前の CA、何でも構いません）が必要です。
どちらのガイドもその名前でダッシュボードを終端し、ネイティブガイドでは同じ名前でワーカー API も終端します。

:::danger[HTTPS は必須です]
ダッシュボードのセッション Cookie（`guru_session`）は `Secure` 付きで発行されるため、`localhost` 以外では
ブラウザーが平文 HTTP 上でこれを破棄します。またアプリはリクエストごとに自身のオリジンを再構成し、ブラウザーの
`Origin` が一致しないログイン POST を拒否します。そのためプロキシは `X-Forwarded-Proto` と
`X-Forwarded-Host` を転送する必要があります。
:::

:::caution[ホスト名を Cloudflare のプロキシ経由にしないこと]
Cloudflare のプロキシは、データが 100 秒流れないストリーミングレスポンスを切断します。`WatchConfig` は
リビジョンの間は無音なので、オレンジクラウド越しではすべてのワーカーが数分おきに再接続することになります。
レコードは DNS のみ（DNS-only）にしてください。自前の nginx への TLS だけで、API キーの通信経路は十分に
保護されます。
:::
