import { Steps, Tabs, TabItem } from '@astrojs/starlight/components';

2 つのデプロイガイド — [Docker でデプロイ](/ja/guides/deploy-with-docker/) と
[ネイティブにデプロイ](/ja/guides/deploy-natively/) — はどちらもこのページから始まります。ここでは外部の
依存コンポーネントとオペレーター用ツールを準備します。この後に読むデプロイガイドは、コントロールプレーンを
それらに接続するだけです。

それぞれの方式が実際に必要とするもの:

| | Docker でデプロイ | ネイティブにデプロイ |
|---|---|---|
| PostgreSQL ≥ 16 | 必要 | 必要 |
| RabbitMQ 3.13/4.x | 必要 | 必要 |
| Redis 7.x | 必要 | 必要 |
| Docker Engine + Compose | 必要（公開済みアプリケーションイメージの実行に使用。データストアへの使用は任意） | 不要 |
| Rust ツールチェーン + `protoc` | `manage-tool` を自分でビルドする場合のみ必要 — バイナリは `master-v*` リリースからダウンロードできます | 必要 — すべてのバイナリをビルドします |
| C ツールチェーン、`make`、`cmake` | 同上 — `manage-tool` は証明書関連のクレート群（aws-lc 上の `instant-acme`/`rcgen`）を取り込み、同梱の C ソースのビルドにコンパイラーと cmake が必要です | 必要 — 理由は同じです |
| `perl` | 不要 | 必要 — `guru-worker` は同梱の OpenSSL をビルドし、その構成は perl スクリプトが行います |
| Bun | 不要 | 必要（ダッシュボードのビルドと実行） |
| ホスト名 + TLS 証明書 | 必要 | 必要 |

イメージデプロイの Rust 行が「場合のみ」なのは、`master-v*` タグが GHCR のイメージに加えて
`guru-master` と `manage-tool` のバイナリ（`x86_64-unknown-linux-gnu`）を GitHub リリースとしても公開する
ようになったからです。それをダウンロードして使うなら、ビルド用のツールチェーンは一切必要ありません。
スキーマはバイナリに埋め込まれて配布されるため、スキーマを適用するためだけにチェックアウトが
必要になることはありません。

## 1. Docker Engine と Compose（イメージデプロイのみ）

Docker が必要なのは、イメージデプロイを選ぶ場合だけです。ネイティブデプロイに Docker は不要であり、
PostgreSQL、RabbitMQ、Redis は直接インストールするか、マネージドサービスまたは別の実行方法を利用できます。
ディストリビューションを一度選べば、このページのすべてのタブが連動します。

<Tabs syncKey="distro">
<TabItem label="Debian">

```sh
# See https://docs.docker.com/engine/install/debian/
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/debian/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/debian
Suites: $(. /etc/os-release && echo "$VERSION_CODENAME")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

`docker-buildx`、`podman-docker`、`containerd`、`runc`。ここではパッケージが起動時の自動実行を有効にします。

</TabItem>

エンジンが動作することを確認します。Compose の実行はオペレーターの操作として扱ってください。`sudo docker compose` を使うか、

サービスアカウントには決して付与しないでください:

```sh
sudo docker run --rm hello-world
```

## 2. ホストのパッケージ

<Tabs syncKey="distro">
<TabItem label="Debian">

```sh
sudo apt update
sudo apt install -y build-essential pkgconf perl cmake protobuf-compiler \
                    openssl nginx curl unzip git
```

</TabItem>
<TabItem label="Ubuntu">

```sh
sudo apt update
sudo apt install -y build-essential pkgconf perl cmake protobuf-compiler \
                    openssl nginx curl unzip git
```

</TabItem>
<TabItem label="Fedora / RHEL">

```sh
sudo dnf install -y gcc gcc-c++ make pkgconf-pkg-config perl cmake protobuf-compiler \
                    openssl nginx curl unzip git
```

</TabItem>
<TabItem label="Arch">

```sh
sudo pacman -S --needed base-devel cmake protobuf openssl nginx curl unzip git
```

`base-devel` には `gcc`、`make`、`pkgconf`、`perl` が既に含まれています。

</TabItem>
</Tabs>

いずれも飾りではなく、このワークスペースが実際に依存しているものです:

| パッケージ | 必要な理由 |
|---|---|
| `protoc`（`protobuf-compiler`、Arch では `protobuf`） | `lib/rpguru_sdk` のビルドスクリプトが `tonic-prost-build` で `proto/` をコンパイルし、その内部で `protoc` を呼び出します。`manage-tool` を含むすべてのバイナリがこのクレートに依存するため、`protoc` がないとビルドが失敗します。`PATH` にない場合は `PROTOC=/path/to/protoc` を設定してください。 |
| C コンパイラー、`make` | `manage-tool` をビルドする場合に必要です。これは `orchestration` モジュール経由で証明書関連のクレート群に到達し、そのうちいくつか（`aws-lc-sys`、`ring`、`zstd-sys`）は同梱の C ソースをコンパイルします。 |
| `cmake` | `aws-lc-sys` は同梱ソースを cmake でビルドするため、`manage-tool` をビルドする環境では必ず必要です。 |
| `perl` | `guru-worker` は `vendored` フィーチャーで OpenSSL をリンクします。OpenSSL は同梱のソースツリーからコンパイルされ、その `Configure` は perl スクリプトです。ネイティブデプロイのみで必要です。 |
| `pkgconf` / `pkg-config` | 上記の `*-sys` クレート群のビルド依存です。 |
| `openssl` | デプロイガイドでは `openssl rand -hex 32` でパスワードや鍵を生成します。 |
| `unzip` | Linux 上の Bun インストーラーが必要とします。 |
| `nginx` | ダッシュボードの TLS を終端し、ネイティブガイドではワーカー API の TLS も終端します。最近のビルドであれば `http_ssl_module` と `http_v2_module` を備えており、これが `grpc_pass`（nginx 1.13.10 以降）の要件です。 |

`libssl-dev`/`openssl-devel` や `libprotobuf` の開発パッケージは不要です。Rust のビルドがそれらに必要とする分は、
すべて同梱されています。

## 3. Rust と Bun

ここまでの作業には root が必要でした。このセクションの作業はすべて、**チェックアウトを所有する**アカウントに
属します。そしてそのアカウントはデプロイ方式によって異なります:

<Tabs syncKey="deployment">
<TabItem label="ネイティブデプロイ">

コントロールプレーン、ダッシュボード、およびビルドしたものはすべて 1 つの非特権サービスユーザーとして動作します。
`sudo useradd --create-home --shell /bin/bash guru` でユーザーを作成し、`sudo -iu guru` でそのシェルに
入ってください。このセクションの残りは `guru` として実行します。このシェルからツールチェーンをインストールすれば、
systemd から見つけられるサービスユーザーのホームに配置されます。

ネイティブガイドでは全体を通して `guru` と `/home/guru` を使います（ユニットの `User=`/`Group=` と Bun の
パスも同様）。別の名前を使う場合は一貫して置き換えてください。データストアをコンテナで実行する場合でも、
サービスユーザーに Docker やその他のホスト管理権限を与えては**いけません**。

</TabItem>
<TabItem label="イメージデプロイ">

チェックアウトから常駐するものは何もありません。Compose ファイルを置き、必要なら `manage-tool` を
ビルドするだけなので、自分のオペレーターアカウントが適切です（`manage-tool` は `master-v*` リリースから
ダウンロードすることもでき、その場合 Rust すら要りません）。Bun はまったく必要ありません。

</TabItem>
</Tabs>

<Steps>

1. **Rust** は [rustup](https://rustup.rs/) で導入します。ワークスペースは `rust-toolchain.toml` で
   ツールチェーン（チャンネル `1.98`）を固定しており、最初の `cargo` 実行時に rustup がその固定版を
   インストールします。ディストリビューションの `rust` パッケージで代替しないでください。古いコンパイラーでは
   edition 2024 をビルドできません。イメージデプロイで `manage-tool` をリリースからダウンロードするなら、
   この手順は省けます。

   ```sh wrap frame="none"
   curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
   . "$HOME/.cargo/env"
   ```

2. **チェックアウト。** 柔軟に選べるのは `manage-tool` です。ここでビルドするか、`guru-master` の
   バイナリと並んで公開されている `master-v*` の GitHub リリース（`x86_64-unknown-linux-gnu`）から
   ダウンロードしてください。イメージガイドでは Compose ファイルも使います。ネイティブデプロイで
   このファイルを使うのは、任意のコンテナ構成を選んだ場合だけです。

   ```sh wrap frame="none"
   git clone \
     https://github.com/haruki-nikaidou/proxy-guru.git /path/to/proxy-guru
   ```

4. **Bun** はネイティブデプロイのみで、ダッシュボードのビルドと実行に使います。Node はどこでも使いません。
   SvelteKit のビルド後処理は `Promise.withResolvers` を必要とし、Node 20 にはこれがありません。

   ```sh wrap frame="none"
   curl -fsSL https://bun.com/install | bash
   export BUN_INSTALL="$HOME/.bun"; export PATH="$BUN_INSTALL/bin:$PATH"
   ```

   インストーラーはバージョン指定（`bash -s "bun-v1.3.3"`）を受け付けるので、公開版ダッシュボードのビルドに
   使われている `oven/bun:1.3` イメージと揃えられます。Arch には `bun` パッケージもありますが、インストールに
   root が必要で、バイナリがサービスアカウントのホーム外に置かれます。

</Steps>

## 4. PostgreSQL、RabbitMQ と Redis

### コントロールプレーンが求める条件

| | 要件 |
|---|---|
| PostgreSQL | **16 以降。** データベースは 1 つ、接続も 1 本の URL だけです。コントロールプレーンは自分のスキーマを自分で所有します — 同梱のマイグレーションを自分で適用するため、接続に使うロールにはそのデータベースに対する通常の `CREATE`/`ALTER` 権限が必要です。クラスター全体の権限は不要です。 |
| | **永続ストレージ。** バックアップ対象のボリューム上に置いてください。これはシステム内で唯一、失うと復元できない状態です。そのデータベース 1 つの `pg_dump` が完全なバックアップになります。 |
| | **コネクションプールの余裕。** サービスを提供する master はそれぞれ最大 `GURU_DB_POOL_SIZE` 本（デフォルトは 10）の接続を保持し、それが 3 つあります。そのため `max_connections` は 30 を十分に上回る値にしておいてください。 |
| RabbitMQ | 3.13/4.x のサーバーであれば何でも構いません。コントロールプレーンは起動時に自身の exchange と永続キューを宣言するため、事前に作成しておくものはありません。デフォルト vhost のユーザーが 1 つあれば十分です。このプロジェクトでテスト済みのブローカーは RabbitMQ だけです。 |
| | URI の書式: `amqp://user:password@host:5672/` で、**末尾のスラッシュ**がデフォルト vhost を選択します。`/%2f` 形式はパーサーに拒否されます。 |
| | ブローカーは**4 つのマスターモードすべてで必須**です。定期処理はメッセージそのものであり、ブローカーが停止している間は古いキャンバスのスイープも、応答のないサーバーを `Offline` にする処理も、証明書の更新も行われません。最適化ではなく依存コンポーネントとして扱ってください。 |
| Redis | **7.x 以降。** pub/sub のみに使います — コントロールプレーンはここに何も保存せず、何も宣言せず、永続化も必要としません。そのため到達できるサーバーであれば何でも、マネージドサービスでも構いません。フリート全体で共有する 1 インスタンスを用意してください。レプリカは互いをこれを通して見つけます。 |
| | URL の書式: `redis://127.0.0.1:6379/`。`REDIS_URL` として渡します。データベース接続を開く 3 つのモード — `dashboard_grpc`、`workers_grpc`、`consumer` — で必須で、`cron` はこれに一切触れません。 |
| | これはオペレーター API の `Watch*` ストリームを運びます。すべての変更はチャンネル `guru:orchestration:live` にイベントを 1 件 publish し、各 `dashboard_grpc` レプリカがそれを一度だけ subscribe して、自分が提供しているストリームへ流します。停止して失われるのは、開いているストリームの配信だけで、それ以外は何も失われません。編集は適用され、導出も走り、subscriber はバックオフしながら再接続して、そのあとすべての watcher にデータベースの再読み込みを求めます。ダッシュボードのキャンバスエディターとヘルスページはこれらのストリームを追従しているため、その間は開いているページの更新が止まり、復旧後は自動的に追いつきます。マスターのログに出る `live bus connected` が、引き続きバスを直接確認する手段です。 |

:::caution[RabbitMQ 以外のブローカーはそのまま置き換えられません]
コントロールプレーンは AMQP 0-9-1 クライアントの `amqprs` と、RabbitMQ の exchange／queue 宣言の
セマンティクスを使用します。他のブローカーはテストされていません。特に Azure Service Bus は AMQP 1.0 を
使用するため、互換性があると想定してはいけません。コントロールプレーンのメッセージングの一部または全部が
失敗する可能性があります。代替ブローカーをエンドツーエンドで検証できる場合を除き、RabbitMQ を使用してください。
:::

データストアにコンテナや Docker Compose は必須ではありません。公式の
[PostgreSQL ダウンロードページ](https://www.postgresql.org/download/)と
[RabbitMQ ダウンロードガイド](https://www.rabbitmq.com/docs/download)に従い、Redis はディストリビューションの
パッケージか公式の配布物を使うか、あるいはマネージドサービスまたは以下の Compose 例を使用してください。
どの方法でも、上記の要件を満たす必要があります。

### 認証情報

パスワードは**URL セーフ**な形式で生成してください。どちらも URI（`GURU_DATABASE_URL` と `AMQP_URI`）に
埋め込まれ、そこでは `@`、`:`、`/`、`%` が URI の意味を変えてしまいます:

```sh
openssl rand -hex 32          # once for PostgreSQL, once for RabbitMQ
```

16 進文字列であれば、クォートやパーセントエンコーディングの問題は一切起きません。どうしても記号を使いたい場合は、
両方の URI 内でパーセントエンコードしてください（`@` → `%40`、`:` → `%3A`、`/` → `%2F`、`%` → `%25`）。

接続用の認証情報を、コントロールプレーンが読み込むファイルに記録します。イメージデプロイ用の Compose 例も、
データストアの認証情報をこのファイルから読み込みます:

<Tabs syncKey="deployment">
<TabItem label="ネイティブデプロイ">

```sh
# /path/to/proxy-guru/.env   (chmod 600; gitignored)
GURU_DATABASE_URL=postgres://guru:<first hex string>@127.0.0.1:5432/guru
RABBIT_USER=guru
RABBIT_PASSWORD=<second hex string>
AMQP_URI=amqp://guru:<second hex string>@127.0.0.1:5672/
REDIS_URL=redis://127.0.0.1:6379/
```

systemd は後で `EnvironmentFile=` からこのファイルをそのまま読み込みます。systemd は `${…}` を
**展開しない**ため、`GURU_DATABASE_URL` と `AMQP_URI` は完全な形で書き出してください。

</TabItem>
<TabItem label="イメージデプロイ">

```sh
# /srv/guru/.env   (chmod 600)
POSTGRES_USER=guru
POSTGRES_PASSWORD=<first hex string>
POSTGRES_DB=guru

RABBIT_USER=guru
RABBIT_PASSWORD=<second hex string>
```

先に `/srv/guru` を作成してください（`sudo mkdir -p /srv/guru`）。以下の Compose ファイルはこの `.env` の
隣に置き、イメージガイドではここに `MASTER_VERSION`、`FRONTEND_VERSION`、`GURU_MASTER_KEY` を追記します。
`GURU_DATABASE_URL` と `AMQP_URI` もこのファイルには現れません。Compose が上記の変数から両方を組み立てます。
Redis に認証情報が要らないため Compose が URL をそのまま書いている（`redis://redis:6379/`）のと同じ考え方です。

</TabItem>
</Tabs>

### 起動する

<Tabs>
<TabItem label="ネイティブデプロイ">

3 つのサービスをインストールします。PostgreSQL と RabbitMQ は公式の
[PostgreSQL ダウンロードページ](https://www.postgresql.org/download/)と
[RabbitMQ ダウンロードガイド](https://www.rabbitmq.com/docs/download)に従い、Redis はディストリビューションの
パッケージか公式の配布物で構いません。PostgreSQL では `guru` ロールと、それが所有する `guru` データベースを
作成し、ポート `5432` のループバックリスナーを設定します。RabbitMQ は `.env` のユーザーとパスワード、
デフォルト vhost、永続ストレージ、ポート `5672` のループバックリスナーを設定し、Redis はポート `6379` の
ループバックリスナーだけを設定します
（保存するものがないので、AOF も RDB も無効にして構いません）。オペレーティングシステムのサービスマネージャーを
使って 3 つすべてを起動し、ブート時に有効化してください。

Docker Compose は任意の代替手段であり、デプロイ要件ではありません。使用する場合、リポジトリの
`docker-compose.yml` が同じループバック限定の構成を提供し、永続データを `./data/` 以下に保存します。

</TabItem>
<TabItem label="イメージデプロイ">

デプロイ用ディレクトリ（イメージガイドでは `/srv/guru`）を作成し、認証情報を持つ `.env` の隣にある Compose
ファイルに 3 つのデータストアを記述します:

```yaml
# /srv/guru/docker-compose.yml
name: guru

services:
  postgres:
    image: postgres:18.6-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
```

Compose 例で 1 つ説明しておくべき点があります。RabbitMQ はデータディレクトリをノード名
`rabbit@<hostname>` に基づいて命名するため、このサービスは `hostname:` を固定しています。これがないと、
コンテナを作り直すたびに空のブローカーで起動してしまいます。Redis だけは意図的に例外です: ボリュームも、
公開ポートも、healthcheck もありません — master は Compose ネットワーク経由で到達し、新しい空のサーバーは
置き換えた元のサーバーとまったく同じように役立ちます。

consumer がバインドするキューは自動的に作成されます。編集用の `guru_orchestration_canvas_dirty` に加え、
6 つの定期ジョブ用に `guru_orchestration_derive_stale_canvases`、`guru_orchestration_sweep_liveness`、
`guru_orchestration_trim_health_history`、`guru_orchestration_renew_certificates`、
`guru_orchestration_rotate_relay_certificates`、`guru_orchestration_resolve_server_countries` が
作成されます。

## 5. ホスト名と証明書

ホストを指す DNS 名 1 つと、それに対する TLS 証明書（`certbot`、自前の CA、何でも構いません）が必要です。
どちらのガイドもその名前でダッシュボードを終端し、ネイティブガイドでは同じ名前でワーカー API も終端します。

:::danger[HTTPS は必須です]
ダッシュボードのセッション Cookie（`guru_session`）は `Secure` 付きで発行されるため、`localhost` 以外では
ブラウザーが平文 HTTP 上でこれを破棄します。またアプリはリクエストごとに自身のオリジンを再構成し、ブラウザーの
`Origin` が一致しないログイン POST を拒否します。そのためプロキシは `X-Forwarded-Proto` と
`X-Forwarded-Host` を転送する必要があります。
:::

:::caution[ホスト名を Cloudflare のプロキシ経由にしないこと]
Cloudflare のプロキシは、データが 100 秒流れないストリーミングレスポンスを切断します。`WatchConfig` は
リビジョンの間は無音なので、オレンジクラウド越しではすべてのワーカーが数分おきに再接続することになります。
レコードは DNS のみ（DNS-only）にしてください。自前の nginx への TLS だけで、API キーの通信経路は十分に
保護されます。
:::
