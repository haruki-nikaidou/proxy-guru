スキーマはリポジトリ内の SQL マイグレーション群であり、コンパイル時にバイナリへ埋め込まれます。
`guru-master` は起動時に未適用のものをすべて適用するため、新規インストールでは空のデータベース以外に
ここで必要なものはありません — このページは、代わりに意図的なタイミングで適用したい場合のためのものです:
最初の master を起動する前、デプロイの直前、あるいはまだどの master も接続していないデータベースに対して。
2 つのデプロイガイド（[Docker](/ja/guides/deploy-with-docker/)、[ネイティブ](/ja/guides/deploy-natively/)）は
どちらもここを参照しており、以降のスキーマ変更もすべて同じ手順に従います。

リポジトリに含まれているもの:

| パス | 内容 |
|---|---|
| `migrations/*.sql` | マイグレーション。ファイル名順に適用され、一度適用したものは決して編集しません |

前提条件: 到達可能な PostgreSQL ≥ 16 と、その接続 URL —
いずれも[前提条件](/ja/guides/prerequisites/)を参照してください。

## 1. ツールを正しいデータベースに向ける

どちらのバイナリも接続情報を 1 本の URL として受け取ります: `--database-url`、または環境変数の
`GURU_DATABASE_URL` です。

```
postgres://guru:<password>@127.0.0.1:15432/guru
```

:::caution[接続情報は必ず明示的に渡す]
`GURU_DATABASE_URL` は、それを export したシェルから起動されたすべてのプロセスに引き継がれ、作業ディレクトリに
ある `.env` も同じように引き継がれます。別環境の認証情報も置かれているマシンでは、フラグを 1 つ忘れただけで
「ローカル向け」のコマンドが本番環境を書き換えてしまいます。
:::

`manage-tool` は同じチェックアウトからビルドする（`cargo build --release -p manage-tool`）か、
`master-v*` リリースが `manage-tool-<version>-x86_64-unknown-linux-gnu` として添付しているものを
ダウンロードして使います。

<Tabs syncKey="deployment">
<TabItem label="ネイティブデプロイ">

チェックアウト自身の `.env` に接続情報が入っているので、これを読み込みます:

```sh
cd /path/to/proxy-guru
set -a; . ./.env; set +a
```

</TabItem>
<TabItem label="イメージデプロイ">

デプロイ用の `.env` はチェックアウトではなく Compose ファイルの隣にあるため、別ディレクトリのファイルを
読み込むのではなく URL を手で渡します:

```sh
cd /path/to/proxy-guru
read -rs GURU_DATABASE_URL    # paste it; not echoed
export GURU_DATABASE_URL
```

</TabItem>
</Tabs>

データベースがリモートホストのループバックでしか待ち受けていない場合は、先にトンネルを張ってください:
`ssh -N -L 15432:127.0.0.1:5432 guru-host`。

## 2. スキーマを適用する

```sh
./target/release/manage-tool db migrate
# schema is up to date
```

手順はこれだけです。この操作は冪等で、すでに実行済みのマイグレーションは `_sqlx_migrations` テーブルに
記録されておりスキップされます。複数のプロセスが同時に実行しても構いません — マイグレーターは PostgreSQL の
アドバイザリロックを取得するため、master 群が一斉に起動しても各マイグレーションはちょうど一度だけ適用されます。

## 3. モジュール設定のシードを投入する

オペレーターが調整する設定値 — ヘルスのしきい値と保持期間、デフォルトの ACME ディレクトリ、更新ウィンドウ、
各定期ジョブの実行間隔 — は環境変数ではなくデータベースに、キーごとに 1 行の `app_config` レコードとして
格納されます。スキーマを適用したら、デフォルト値を一度書き込みます:

```sh
./target/release/manage-tool config seed
# seeded auth
# seeded orchestration
```

この操作は冪等で、編集済みの値を上書きすることはないため、スキーマ変更のたびに再実行して構いません。
`config list`、`config get <key>`、`config set <key> <json>` でこれらの値を確認・変更できます。master は
起動時に一度だけ読み込むので、変更を反映するには再デプロイではなく再起動が必要です。
[設定 → モジュール設定](/ja/reference/configuration/#モジュール設定)を参照してください。

シード投入を省略しても問題ありません — 未投入のインストールはデフォルト値で動作します — が、型に一致しない
ドキュメントが保存されている場合は、該当キー名を示して master の起動が失敗します。これは意図的な挙動です:
黙ってデフォルトにフォールバックすると、ACME がステージングから本番ディレクトリに切り替わってしまう
可能性があるためです。

## 4. その後のスキーマ変更

スキーマ変更とは `migrations/` に新しいファイルを追加することです。適用済みのマイグレーションを
編集することは決してありません。データベースが記録しているのは、どのマイグレーションを実行したかであって、
その内容ではないからです。

<Steps>

1. 新しいマイグレーションを適用します。新しいバイナリをデプロイする（各 master が起動時にマイグレートします）か、
   前倒しで済ませたい場合は新しいチェックアウトから `manage-tool db migrate` を実行します。

2. 対応するバイナリをデプロイし、動作を検証します。

</Steps>

:::caution[ローリングアップグレードでは 2 つのスキーマが同時に見える]
新しいバイナリが順次入れ替わっている間、古いバイナリはマイグレーション済みのデータベースに対してサービスを
提供し続けます。追加だけを行うマイグレーションは古いバイナリにとって安全ですが、古いバイナリがまだ読んでいる
カラムを削除・リネームするものは安全ではありません。そうした変更は 2 つに分けてください — 追加を行い旧来の形を
使うのをやめるリリースと、それを削除する後続のリリース — あるいは、その 2 つの間ですべての master を短時間
停止させることを受け入れてください。
:::

リポジトリの外に保管しておくべきものはありません: マイグレーションはコミットされており、どのデータベースが
何を適用済みかは、そのデータベース自身に記録されています。
