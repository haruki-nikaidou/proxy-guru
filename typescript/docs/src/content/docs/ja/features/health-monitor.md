title: ヘルスモニター
description: ワーカーが報告する内容、マスターがそれをサーバーとポッドのステータスに変える仕組み、そしてダッシュボードのヘルスページが表示するもの。
---

すべてのワーカーはコントロールプレーンへストリームを 1 本開いたままにし、一定の間隔でそこへレポートを
push します。そのストリームがヘルスモニターのすべてです。サーバーが `Online` かどうかを決め、
ダッシュボードがチャートに描くトラフィックカウンターを運び、その沈黙こそがサーバーを `Offline` として
マークするものです。

## ワーカーが報告する内容

`WorkerAgent` サービスのクライアントストリーミング RPC である `ReportHealth` 上で、間隔ごとに
`HealthReport` を 1 件。認証にはワーカーの現在のリフレッシュキーを使います:

| フィールド | 内容 |
|---|---|
| `running_revision` | ワーカーが実行していると認識している設定リビジョン。`0` は新規インストール、または state ディレクトリが消えた状態を意味します。 |
| `upload_bytes`、`download_bytes` | **前回のレポートからの**バイト数を、すべての forwarding について合計したもの。 |
| `current_connections` | **レポート時点で**開いている接続数 — 間隔あたりの量ではなく、ゲージです。 |
| `max_connections` | 前回のレポート以降のハイウォーターマーク。0 からではなく、まだ開いている接続数から数え直します。 |
| `pods` | 実行中の forwarding ごとに 1 エントリ。その tag（ポッドの id）と、任意のエラー。 |
| `reported_addresses` | アドレス検出の結果が変わったレポートにのみ含まれます。 |

間隔はマスターのものです。`Register` は保存された `orchestration` 設定の
`health_report_interval_secs`（デフォルトでは 15 秒）を返し、ワーカー自身の `--health-interval` は
マスターが `0` を送ってきた場合にのみ適用されます。最初のレポートは、ストリームが開いた時点で
すぐに送られます。

レポートタスクはセッションとまったく同じ寿命を持ちます。何らかの理由で終了すると、ワーカーは
セッションを破棄し、上限付きの指数バックオフで再接続します。つまり、新しい `Register`、新しい
リフレッシュキー、再交渉された間隔になります。カウンターはそれを生き延びません。失われた間隔の差分は
破棄され、接続のゲージは開いているものから数え直しになります。

## マスターが保存する内容

受理された各レポートは 1 つのトランザクションです。ワーカーのリフレッシュキーの generation で
フェンスされており — 置き換えられたセッションからのレポートは、記録されずに拒否されます — 次を
書き込みます:

- サーバー行の `last_health_report_at`、`last_seen_at`、そして現在の `health_status`;
- `server_health_record` 行 1 つ: ステータス、レポート時刻、4 つのカウンター;
- レポートが解決できたポッドごとに `pod_health_record` 行 1 つ。

報告された tag は、まずサーバーの `applied` スナップショット、次に `desired` スナップショットに対して
解決されます。どちらにもない tag はスキップされ、何も書き込みません。1 つのポッドが 2 つのリスナーで
保持されている場合 — 依存側が新しいポートへ切り替わっている間に起こります — 2 つのエントリは、
両者のうち**最も悪い**ステータスを持つ 1 行にまとめられます。

その書き込みがコミットされた後、サービスはそのレコードをライブバスに publish します — これは
トランザクションの一部ではない別のステップです — そしてこれをダッシュボードのストリームと、
キャンバスの `WatchGraph` の subscriber が読み取ります。

## サーバーのステータス

`Online`、`Degraded`、`Offline` です。新しいサーバーは `Offline` から始まります。まだ誰もそこから
何も聞いていないからです。受理されたレポートごとに、次の順で判定をやり直します:

1. サーバーの設定ビューに `apply_error` がある、またはいずれかのポッドが失敗として記録されている →
   `Degraded`;
2. `running_revision` が applied リビジョンと異なる → `Degraded`（`0` を報告するワーカーはここで
   捕まります）;
3. より新しいリビジョンが desired であり、その publish が `degraded_grace_secs`（60 秒）より前である →
   `Degraded`;
4. それ以外は `Online`。

`AckConfig` も `Online`/`Degraded` を直接書き込むため、適用の失敗は次のレポートを待たずに現れます。

`Offline` には強制ポイントが 2 つあり、どちらも `health_report_interval_secs ×
health_offline_after_intervals` — デフォルトでは **45 秒** — で駆動されます:

- マスターはその値をレポートごとのタイムアウトとしてストリームを読み、沈黙したストリームを
  `no health report within 45s` で終了します;
- `sweep_liveness` パスが、最後に受理されたレポートがしきい値より古い、offline でないサーバーすべてを
  反転させます。

`Offline` になると、サーバーのセッションリースもクリアされ、watch エポックが進みます。そのため設定
ストリームは終了し、ワーカーの次の `Register` は重複セッションとして拒否されるのではなく、すぐに
受理されます。ステータスの反転は、カウンターがすべて 0 の `server_health_record` 行を書き込み、
`last_health_report_at` は動かしません。

## ポッドのステータス

`Ready`、`Deploying`、`Failed` のいずれかで、文言ではなくスナップショットからレポートごとに
判定されます:

- **Failed** — レポートがそのポッドのエラーを運んできた、または最後の ack が失敗として記録した。
  そのエラーのテキストが行の message になります。
- **Deploying** — そのポッドのエントリが `desired` と `applied` で異なる、または `desired` にしか
  存在しない。
- **Ready** — 解決でき、失敗がなく、保留中のものが何もない。

`Deploying` は、導出がリビジョンを publish した瞬間に、forwarding が変わったすべてのポッドに対して
`revision <n> published` という message とともに書き込まれます — TOML がバイト単位で同一でも
ディスク上の材料が新しい証明書の更新も含みます。

## 定期パス

どちらも `--mode consumer` で動きます。`--mode cron` は一定の周期でそのシグナルを publish するだけで、
データベースは開きません。

| パス | シグナルの周期 | 設定キー（デフォルト） | 内容 |
|---|---|---|---|
| `sweep_liveness` | 30 秒 | `liveness_interval_secs`（30） | 沈黙したサーバーを `Offline` にし、登録しながら一度もレポートしていない、すでに offline のサーバーのセッションを revoke します。 |
| `trim_health_history` | 300 秒 | `health_retention_interval_secs`（300） | `server_health_ttl_secs` / `pod_health_ttl_secs`（それぞれ 7 日）より古いレコードを削除します。 |

各 consumer は作業の前にそのティックを `orchestration_job_run` 行 1 つで claim するため、consumer が
何台起動していても、パスは設定された間隔につき 1 回だけ実行されます。claim が比較するのは
スケジューリングのティックで、壁時計ではありません。シグナルの周期以下の間隔は「シグナルごとに実行
する」という意味になり、それより大きい間隔はフリート全体でパスを遅くします。

## 読み出す

保存された履歴を読む unary メソッドが 2 つ — `ListServerHealthHistory`（両端を含む時間範囲、古い順、
上限なし）と `ListPodHealthHistory`（新しい順、`limit` 0 は 500 を意味します）— そしてそれをライブで
追う server-streaming メソッドが 2 つあります。`WatchServerHealth` と `WatchPodHealth` は `since`
（空の場合は 1 時間前）からのスナップショットで開き、その後はコミットされたレコードごとに 1 イベントを
push し、`stream_keepalive_secs` ごとにキープアライブを送ります。どちらのストリームも履歴を読む前に
バスを subscribe するため、スナップショットと最初のイベントの間に落ちるものはありません。また、
見た中で最も新しいレポート時刻で重複を排除し、これが再接続時の再配信を防ぐ仕組みでもあります。

提供されるものはすべて保存された行です。ライブストリームは数値を再読み込みなしで届けますが、自分で
何かを測ることは決してないため、`Offline` のサーバーは最後に送った内容を表示し続けます。

## ヘルスページ

![キャンバスのヘルスページ: *ライブ* インジケーターと「直近 1 時間」のウィンドウセレクター、online・degraded・offline のサーバー数とレポートを持つサーバー数を数える 4 枚のサマリーカード、続いて Online バッジ、最後のレポート時点の接続数、ピーク値、そのレポートの時刻、レポート件数を示すサーバーカードと、その下のスループットと接続数のチャート](/img/features/health-page.avif)

`/canvas/<canvas-id>/health` はライブです。キャンバスのメンバーシップのための `WatchGraph` ストリームを
1 本と、サーバーごとに `WatchServerHealth` ストリームを 1 本開き、切れたストリームは最後に受け取った
レコードから開き直すため、再取得されるのは欠けた区間だけです。ウィンドウセレクターは 1 時間 / 6 時間 /
24 時間 / 7 日を選べます。

サマリーのストリップは、サーバーをステータスごとに数え、ウィンドウ内で少なくとも 1 件レコードを
生成したサーバーの数を数えます。各サーバーカードは、ステータスバッジ、ウィンドウ内の**最後のレポート
時点**の接続数、ハイウォーターマークのピーク、そのレポートの時刻、そこに含まれるレポート件数を表示し、
その下に同じ x 軸の 2 つのチャート — レポートごとのバイト差分を積み上げたスループットと、ゲージの
背後にハイウォーターマークを置いた接続数 — を並べます。

**Pod イベント**タブは、そのサーバーで動くすべてのポッドを新しい順に、ステータス・時刻・message と
ともに一覧します — `Failed` 行の `message` はワーカー自身のエラーテキストです。ポッドごとに 1 本の
ストリームを使うため、開いたときにのみマウントされます。

## 設定

`orchestration` 設定キーの下に保存され、マスターの起動時に一度だけ読まれます。そのため変更は再起動で
有効になります:

| キー | デフォルト | 効果 |
|---|---|---|
| `health_report_interval_secs` | 15 | ワーカーに渡される間隔。offline のしきい値の基準になります。 |
| `health_offline_after_intervals` | 3 | offline のしきい値の乗数（デフォルトでは 45 秒）。 |
| `degraded_grace_secs` | 60 | サーバーが `Degraded` になるまでに desired リビジョンに遅れていられる時間。 |
| `server_health_ttl_secs` | 604800（7 日） | サーバーレコードの保持期間。 |
| `pod_health_ttl_secs` | 604800（7 日） | ポッドレコードの保持期間。 |
| `liveness_interval_secs` | 30 | `sweep_liveness` の実行周期。 |
| `health_retention_interval_secs` | 300 | `trim_health_history` の実行周期。 |
| `stream_keepalive_secs` | 15 | `Watch*` ストリームのキープアライブ。 |

ワーカー側の `--health-interval` / `GURU_HEALTH_INTERVAL_SECS`（デフォルト 15、最小 1）は、間隔を
送ってこないマスターに対するフォールバックです。ドキュメント全体については
[設定](/ja/reference/configuration/)を、そもそもリビジョンがどうワーカーへ届くのかについては
[ロールアウト](/ja/reference/rollout/)を参照してください。
