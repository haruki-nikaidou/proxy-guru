---
title: DNS を使った ACME
description: TLS ポッドが DNS-01 チャレンジを通じて公的に信頼された証明書を得るまでと、それとは別の内部 CA がリレーのホップを保護する仕組み。
---

TLS を終端するクライアントポッドには、クライアントが接続してくる名前に対する、公的に信頼された証明書が
必要です。コントロールプレーンは DNS-01 チャレンジを使った ACME でそれを自分で取得するため、ポート 80 で
何かに到達できる必要はなく、まだトラフィックが流れ始めていない名前に対しても証明書を発行できます。
自分のサーバー同士のリレーのホップは、別の内部 CA を使います — このページの後半です。

## ポッドが宣言する内容

TLS クライアントポッドは、[ポッドのパネル](/ja/reference/nodes/#ポッドのパネルとルート)で編集する
4 つの設定を持ちます:

| 設定 | 内容 |
|---|---|
| `sni` | クライアントが提示するホスト名。小文字に正規化して保存され、証明書はその正規形をキーにします。 |
| DNS プロバイダー | 設定済みのどのプロバイダーがチャレンジに応答するか。 |
| `domain_id` | Cloudflare: ゾーン ID。Vercel: 登録済みのドメイン、例えば `example.com`。 |
| ACME ディレクトリ | 空の場合は保存された `default_acme_directory`（Let's Encrypt の本番）。 |

この組み合わせは 3 つのグラフ検査で守られており、いずれかに触れる編集は拒否されます:

- `invalid_sni` — その名前が、ASCII の英字・数字・ハイフンからなるラベル 2 つ以上のホスト名では
  ありません。ワイルドカードは受け付けられません。
- `unknown_dns_provider` — ポッドが、存在しないプロバイダーを指定しています。
- `certificate_issued_elsewhere` — 同じ SNI とディレクトリの証明書が、別のプロバイダーまたは別の
  domain id で既に存在します。証明書は `(sni, directory)` だけをキーにするため、SNI を共有する
  すべてのポッドは、どちらか一方の設定が黙って無視されるのではなく、発行方法について一致していなければ
  なりません。

## 名前とディレクトリごとに 1 行

それぞれ異なる `(sni, acme_directory)` は、1 つの `certificate` 行に解決されます。最初に要求した
ポッドがそのプロバイダーと domain id を確定させ、後から来たポッドはそれを共有します。行は、ACME
アカウントの資格情報と秘密鍵を `GURU_MASTER_KEY` で**暗号化**して（XChaCha20-Poly1305）保持し、
チェーンは平文で、さらに有効期間、`version`、直近の試行からの `last_error` と `last_attempt_at` を
持ちます。

そのステータスは `pending`、`issued`、`failed` のいずれかで、ポッドが設定へコンパイルされるのは、
行が issued であり*かつ*実際に鍵とチェーンを保持している場合だけです。更新の失敗が、生きている証明書を
格下げすることはありません。失敗は行に記録され、ステータスは `issued` のままです。

## 発行パス

`renew_certificates` は 60 秒ごとに publish され、`--mode consumer` で消費されます。そこでティックが
`orchestration_job_run` で claim されるため、パスは `acme_interval_secs` につきフリート全体で 1 回だけ
実行されます。1 回のパスは:

1. すべての `client_tls` ポッドを読み、そのディレクトリを解決し、足りない証明書行を作成します;
2. 期限が来た行を列挙します — 一度も試行されていない、または `acme_retry_after_secs`（1 時間）より前に
   試行され、かつまだ issued でないか `acme_renew_before_secs`（30 日）以内に失効するもの;
3. たった今観測した `last_attempt_at` の値に対する compare-and-set で各行を claim します。これが
   2 台のマスターが同じ証明書を注文することを防ぎ、マスターが注文の途中でクラッシュした場合に行を
   1 時間押し留めるものでもあります;
4. 注文は 1 件ずつ実行します。DNS-01 の注文は数分かかり、プロバイダーの API にはレート制限が
   あるためです。

注文自体は、保存された ACME アカウントを復元するか新しく登録し、その SNI で注文を開き、保留中の各
authorization の `dns-01` チャレンジに対してプロバイダーの API 経由で `_acme-challenge.<name>` に
TTL 60 の TXT レコードを作成して応答し、伝播を待ち、CA にチャレンジの準備ができたと伝え、その後
ポーリングして finalize し、保存します。TXT レコードは、注文が成功したかどうかにかかわらず、あとで
削除されます。

伝播は Cloudflare と Google のパブリックリゾルバーに対して確認され、その両方が正確なチャレンジ値を
返さなければならず、5 秒ごと、最大 120 秒までポーリングされます。注文と証明書のポーリングにも、
それぞれ 120 秒の上限があります。この 4 つの値はコンパイル時に埋め込まれており、設定キーではありません。
タイムアウトは `TXT record _acme-challenge.<name> did not propagate within 120s` として報告されます。

証明書の保存は、その `version` を進め、`last_error` をクリアし、その SNI のポッドを持つすべての
キャンバスを touch して導出を走らせます。恒久的に諦められるものは何もありません。どの失敗も記録され、
試行のカウンターや追加のバックオフなしに、再試行の窓を過ぎた後のパスで再試行されます。

## 証明書がまだない間

そのポッドはコンパイルされません。forwarding には何も寄与せず、そのサーバーの残りは通常どおり導出・
publish され、ポッドは次の 3 つのメッセージのいずれかとともにサーバービューの `invalid_pods` に
現れます:

| メッセージ | 内容 |
|---|---|
| `certificate for <sni> is pending (not requested yet)` | 行がまだ存在しません — 発行側のより厳しい検証が拒否する SNI、つまり行がまったく作られないケースも含みます。 |
| `certificate for <sni> is pending` | 行は存在しますが、まだ発行されていません。 |
| `certificate for <sni> is failed: <error>` | 直近の試行が失敗しました。チャレンジがうまくいかないときに読むべきメッセージです。 |

保留中の証明書があっても、サーバーが `Degraded` になることは**ありません**。`invalid_pods` は
[ステータスの判定](/ja/features/health-monitor/#サーバーのステータス)の一部ではないからです。すでに
提供していたポッドは、後からコンパイルされなくなっても、そのリスナーを維持します。

## 更新

issued の行は、`not_after` が `acme_renew_before_secs`（30 日）の内側に入った時点で更新されます。更新は
材料をその場で書き換え — 同じ行、同じ id なので、どのワーカー上でもファイルパスは変わりません —
`version` を 1 つ進めます。新しい材料を配るのはその version です。スナップショットは自身の TOML が
参照するバージョンをピン留めするため、TOML のバイト列が同一でもスナップショットは異なり、その証明書を
提供するすべてのサーバーは新しいリビジョンを受け取ります。ワーカーは新しいファイルをアトミックに
書き出し、秘密鍵はモード 0600 です。

## DNS プロバイダー

サポートされるプロバイダーは 2 つです。プロバイダー行は、名前、種別、任意の `account_id`、そして API
トークンからなり、トークンは暗号化して保存され、どの API からも**決して返されません** — すべての
読み取り経路は、それを省いたサマリーを返します。

| プロバイダー | ポッドの `domain_id` | プロバイダーの `account_id` |
|---|---|---|
| Cloudflare | ゾーン ID | 未使用 |
| Vercel | 登録済みのドメイン | チーム ID。空の場合は個人アカウント |

`CreateDnsProvider`、`UpdateDnsProvider`、`DeleteDnsProvider` は Admin 専用です。トークンを空にした
更新は、保存済みのものを維持します。ポッドからまだ参照されているプロバイダーは削除できません:
`dns provider is still used by <n> pod(s)`。

## TLS ページ

`/tls` はダッシュボードでは Admin 専用で、タブが 2 つあります。**DNS プロバイダー**はプロバイダーの
作成・編集・削除を行います。種別は作成後に変更できず、編集でトークンを空欄のままにすると保存済みの
ものが維持されます。**証明書**はすべての行を、その SNI、ステータス、解決されたプロバイダー、domain id、
ACME ディレクトリ、失効のヒント付きの有効期間、直近の試行とともに一覧し、失敗した行は展開すると
`last_error` を表示します。

行ごとにアクションが 2 つあり、どちらも同期的に何かを発行するものではありません:

- **Retry now** は `last_error` と `last_attempt_at` をクリアし、次のパスでその行を期限切れにします —
  issued の証明書に対しては、強制的な更新になります。
- **Delete** は、いずれかのポッドがまだその証明書に解決される間は拒否されます。

このページが行を作成することはありません。行は、次の `renew_certificates` パスが TLS ポッドの
証明書設定を読んだ時点で現れ、その設定はキャンバス上で編集します。導出は行を観測するだけで、
発行されるまでそのポッドを invalid として報告します。

## 内部リレー CA

TLS または QUIC を使うリレーのホップは自分のサーバー同士のトラフィックなので、ACME はまったく使いません。
`manage-tool orchestration init-ca` が自己署名のルートを 1 つ作成し — CN は `guru internal relay CA`、
有効期間 10 年、その鍵は `GURU_MASTER_KEY` で暗号化 — 証明書を標準出力に出力します。ルートに対する
上書きやローテーションの経路は、意図的に存在しません。

それ以降は、導出パスがリレーポッドごとにリーフを 1 枚、有効期間 `relay_cert_valid_secs`（30 日）、
CN と SAN を `<pod-key>.relay.guru.internal` として発行します。`rotate_relay_certificates` パスは
1 時間ごとに走り、`relay_cert_renew_before_secs`（10 日）以内に失効するリーフをすべてローテーションし、
新しい材料がリビジョンとして配られるように、影響を受けたキャンバスを touch します。ワーカーはルートを
`certs/ca.pem`（TOML の `relay_ca`）として受け取り、リレーの対向をそれに対して検証します。

リレーの TLS または QUIC ポッドは、CA が存在しないうちはコンパイルできません — 編集は受理されますが
ポッドは invalid として報告され、直し方は `manage-tool orchestration init-ca` です。素の TCP による
リレーポッドは、どちらの CA も必要としません。

## 設定

`orchestration` 設定キーの下に保存され、マスターの起動時に一度だけ読まれます:

| キー | デフォルト |
|---|---|
| `default_acme_directory` | `https://acme-v02.api.letsencrypt.org/directory` |
| `acme_renew_before_secs` | 2592000（30 日） |
| `acme_retry_after_secs` | 3600（1 時間） |
| `acme_interval_secs` | 60 |
| `relay_cert_valid_secs` | 2592000（30 日） |
| `relay_cert_renew_before_secs` | 864000（10 日） |
| `relay_rotation_interval_secs` | 3600 |

consumer には、ACME ディレクトリと DNS プロバイダーの API への外向き HTTPS、そして伝播を確認する
パブリックリゾルバーへの DNS が必要です。ドキュメント全体については
[設定](/ja/reference/configuration/)を参照してください。
