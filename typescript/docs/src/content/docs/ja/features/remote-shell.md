リモートシェルを使うと、Admin がダッシュボードから `guru-worker` のホストでコマンドを実行し、その出力を
生成されたそばから確認できます。この機能はデフォルトでは一切有効になっていません。ワーカーは、
**それが動いているホスト**がオプトインしない限りシェルを起動せず、ダッシュボードやマスターのどの設定も
それを変えられません。

## セッションとは

セッションとは、ワーカーホスト上の 1 つの `bash` プロセスです。セッションのために起動され、セッションが
終わるまで残ります。セッションのコマンドはすべて同じプロセスに送られるので、ターミナルと同じように状態が
引き継がれます。`cd /tmp` の後に `pwd` を実行すれば `/tmp` が表示され、`export` やシェル変数は後続の
コマンドでも設定されたままです。新しいセッションは、`$HOME` が存在するディレクトリならそこで、
そうでなければ `/` で始まります。

- **一度に 1 コマンド。** 別のコマンドの実行中に送られたコマンドは拒否されます。キューには入りません。
  ダッシュボードは、実行中のコマンドが終わるまで入力欄を無効にします。
- **終了コード。** 終了したコマンドはそれぞれ終了ステータスを報告します（シグナル `n` で終了した
  コマンドは `128 + n`）。
- **ライブ出力。** stdout と stderr は書き込まれたそばからストリーミングされ、各チャンクにはどちらの
  ストリームから来たかのタグが付きます。
- **誰も見ていなくても動き続けます。** シェルはワーカープロセスのもので、どの接続のものでもありません。
  ブラウザのタブを閉じても、フロントエンドやマスターが再起動しても、ワーカーとマスターの間の接続が
  切れても、コマンドは止まりません。
- **再開。** ワーカーは各セッションのトランスクリプト — コマンド、出力、終了コード — を
  `--remote-shell-buffer-bytes`（デフォルト 1 MiB）のリングバッファに保持します。各エントリには位置があり、
  再接続したビューアーは最後に見た位置より後のすべてを要求します。バッファがその位置を越えて一周して
  いた場合、トランスクリプトは捨てられたバイト数を示す切り詰めのマーカーの後、まだ保持されている
  最も古いエントリから続きます。バッファが捨てるのは常に最も古いエントリだけです。書き込みは遅い
  ビューアーを決して待たないので、止まったブラウザがシェルを止めることはありません。
- **複数のビューアー。** 何人の Admin でも、それぞれ自分の位置から同じセッションを同時に見られ、誰でも
  次のコマンドを送れます。

1 つのワーカーで同時に動くセッションは最大 `--remote-shell-max-sessions`（デフォルト 4）個です。それを
超えて開こうとすると、どれかが終わるまで拒否されます。

## できないこと

- **ターミナルではありません。** PTY はありません。`top`、エディター、ページャー、パスワード入力、
  ターミナルのリサイズは使えません。コマンドの stdin は `/dev/null` なので、入力を読むプログラムは
  入力を待たずにすぐ EOF を受け取ります。非対話的な形を使ってください（`systemctl --no-pager`、
  `journalctl --no-pager -n 100`、`apt-get -y`）。
- **中断できません。** 実行中のコマンドだけを止めることはできません。止める唯一の方法はセッションを
  閉じることで、そうするとセッションが起動したものがすべて kill されます。
- **監査ログはありません。** Proxy Guru は、誰がどのコマンドを実行したかを記録しません。
- **トランスクリプトは保存されません。** 出力はワーカーのリングバッファの中にしかありません。
  マスターは中継するだけで何も保持せず、PostgreSQL にも何も書き込まれません。
- **ワーカーの再起動をまたいで生き残りません。** ワーカーを停止または再起動するとすべてのセッションが
  終わります。再起動である[セルフアップデート](/ja/guides/agent-install/#3-update-a-running-worker)も
  同じです。

## 誰が有効にできるか

4 つのゲートがあり、すべてが開いている必要があります。

1. **ビルド。** ワーカーの Cargo フィーチャー `remote-shell` はデフォルトフィーチャーに含まれるので、
   公式リリースビルドと素の `cargo build -p guru-worker` には入っています。`--no-default-features` で
   ビルドしたバイナリには入っていません。シェルのコードを一切含まず、ホストがそれでもオプトインすると、
   設定を黙って無視するのではなく起動を拒否します。
2. **ホスト。** オプトインはワーカープロセスのローカル設定 — ホスト上のフラグまたは環境変数 — で、
   `--no-self-update` と同じように読まれます。マスターがワーカーへプッシュする設定には含まれないため、
   ダッシュボードも、乗っ取られたマスターも、これを有効にできません。有効にできるのは、そのホストで
   すでにワーカーのユニットを変更できる人だけです。
3. **ケイパビリティ。** オプトインしたワーカーは、マスターへの登録時にケイパビリティ `remote_shell` を
   通知します。マスターは、ワーカーがこれを通知していないサーバーへのリモートシェルの要求をすべて拒否し、
   ダッシュボードはそのサーバーに入口を表示しません。
4. **アカウント。** リモートシェルの呼び出しにはすべて `RemoteShell` 権限が必要で、これを持つのは
   Admin ロールだけです。それもサインインしたダッシュボードのセッションからに限られ、API キーでは
   使えません。

### 設定

すべてワーカーホストのローカル設定で、フィーチャーの有無にかかわらずどのビルドにも存在します。

| フラグ | 環境変数 | デフォルト |
|---|---|---|
| `--remote-shell` | `GURU_REMOTE_SHELL` | オフ（オプトイン。エージェントモードのみ） |
| `--remote-shell-buffer-bytes` | `GURU_REMOTE_SHELL_BUFFER_BYTES` | `1048576`（1 MiB。セッションごとに保持するトランスクリプトで、出力、コマンド、エントリごとの小さなオーバーヘッドを数えます。`4096` 以上） |
| `--remote-shell-idle-timeout` | `GURU_REMOTE_SHELL_IDLE_TIMEOUT_SECS` | `1800`（コマンドが実行されておらず、誰も見ていない状態のセッションを残しておく秒数。`1` 以上） |
| `--remote-shell-max-sessions` | `GURU_REMOTE_SHELL_MAX_SESSIONS` | `4`（このワーカーで同時に動くセッション数。`1` 以上） |
| `--remote-shell-allow-plaintext` | `GURU_REMOTE_SHELL_ALLOW_PLAINTEXT` | オフ（`http://` のマスターでもオプトインを許可します。[セキュリティ](#セキュリティ)を参照） |

オプトインが設定されていると、ワーカーは次の場合に起動を拒否します — 理由を書いた `fatal:` 行を出して
終了します。

- バイナリが `remote-shell` フィーチャーなしでビルドされている。
- スタンドアロン（`--config`、`--master` なし）で動いている。シェルにはマスター経由で到達するので、
  スタンドアロンのワーカーには使い道がありません。
- `--master` が `http://` の URL で、`--remote-shell-allow-plaintext` が設定されていない。
- ワーカーの `PATH` に `bash` が見つからない。`/bin/bash` ではなく `PATH` から探します。systemd の
  デフォルトの `PATH` は通常の場所を含みますが、NixOS ではユニットにそれを含む `PATH` が必要です
  （例: `Environment=PATH=/run/current-system/sw/bin`）。

## ホストで有効にする

ダッシュボードのインストールコマンドでインストールしたワーカー（[エージェントのインストールと更新](/ja/guides/agent-install/)
を参照）では、インスタンスの環境ファイルにオプトインを追加して、インスタンスを再起動します。

```sh
echo 'GURU_REMOTE_SHELL=1' | sudo tee -a /etc/guru-worker/hk-1.env
sudo systemctl restart guru-worker@hk-1
```

デフォルトが合わない場合は、ほかの設定も同じファイルに書きます。たとえば
`GURU_REMOTE_SHELL_IDLE_TIMEOUT_SECS=600` です。インストールコマンドを再実行するとこのファイルは
書き直されるので、その後でもう一度行を追加してください。

自分で書いたユニット — たとえば[スタンドアロンモードから取り込んだ](/ja/guides/independent-worker/#9-後からノードを取り込む)
もの — では、コマンドラインにフラグを、または環境に変数を渡します。

```ini
ExecStart=/usr/local/bin/guru-worker --master https://guru.example.com --server <key> --remote-shell
```

ワーカーが再登録すると、ダッシュボードのサーバーの**エージェント**セクションに**リモートシェル**ボタンが
表示されます。シェルを無効にするには、設定を削除して再起動します。ワーカーはケイパビリティなしで登録し、
ボタンは消え、再起動の時点ですべてのセッションは終わっています。

## ダッシュボードから使う

キャンバスを開いてサーバーをクリックし、パネルの**エージェント**セクションを探します。Admin には、
ワーカーがケイパビリティを通知しているすべてのサーバーで、そこに**リモートシェル**ボタンが表示されます。
押すと *リモートシェル · &lt;サーバー名&gt;* が開きます。

- **セッション**には、そのワーカーで動いているセッションが並びます。**新しいセッション**で 1 つ始め、
  **アタッチ**ですでに動いているもの — 以前に開いた自分のもの、あるいは別の Admin のもの — に参加します。
  アタッチすると、バッファがまだ保持している範囲のトランスクリプトが再生されます。
- コマンドを入力欄に入力して**実行**を押します。各コマンドはその出力と一緒に表示され、終わると
  `exit <code>` が続きます。実行中は入力欄が無効のままです。
- **セッションを閉じる**は、確認の後、セッションとそれが起動したものすべてを kill します。

ダイアログやタブを閉じてもデタッチするだけです。セッションも実行中のコマンドも続き、もう一度アタッチ
すれば今のトランスクリプトから再開します。切れた接続は、ブラウザが最後に受け取った位置から自動的に
再開します。

セッションが終わると、トランスクリプトに理由が表示されます。オペレーターによるクローズ、アイドル
タイムアウト、シェルの終了（たとえば `exit` の後）、ワーカーの停止のいずれかです。

## ライフタイム

セッションは、次のいずれか 1 つの形で終わります。

| 終わり方 | いつ |
|---|---|
| クローズ | 誰かが**セッションを閉じる**を押したとき。ワーカーはセッションのプロセスグループ全体に `SIGKILL` を送るので、シェルとそれがそのグループで起動したすべてのプロセスが一度に消えます。 |
| アイドルタイムアウト | コマンドが実行されておらず、**かつ**ビューアーが 1 つもアタッチしていない状態が `--remote-shell-idle-timeout`（デフォルト 30 分）続いたとき。実行中のコマンドか、開いているビューアーが 1 つあればセッションは生き続けます。 |
| シェルの終了 | シェルが自分で終わったとき（たとえば `exit` の後）。実行中だったコマンドがあれば、先にその終了ステータスを報告します。 |
| ワーカーの停止 | ワーカーが停止または再起動したとき（セルフアップデートを含む）。すべてのセッションが kill され、復元されるものはありません。 |

コマンドが独自のプロセスグループへ移したプロセス — `setsid`、自分でデタッチするデーモン — は
セッションのグループに属さないため、クローズ後も生き残ります。ただしインストーラーのユニットでは、
ワーカーとともに終わります。`guru-worker@<unit>` を停止または再起動すると、systemd がユニットの
コントロールグループ内のすべてを kill するからです。

## 通信経路

ダイヤルするのは常にワーカーで、マスターがワーカーに接続することはありません。オプトインしたワーカーは、
登録後にマスターへのストリームを 1 本追加で開きます。これはセッションのリフレッシュキーで認証され、
設定ストリームと同じように次の登録で置き換えられます。切れたときはワーカーが自分で開き直します。
マスターはこのストリームとダッシュボードの呼び出しの間で、レプリカをまたいで要求とトランスクリプトの
エントリを中継し、何も保存しません。ブラウザはトランスクリプトを Server-Sent Events として受け取り、
その id はトランスクリプトの位置です。再接続が取りこぼした分だけを正確に要求できるのはこのためです。

## セキュリティ

リモートシェルを有効にすると、ダッシュボードがホストへの入口になります。ホストごとに判断し、必要な
ホストでだけ有効にしてください。

- **ワーカーのユーザーとして、そのユーザーの権限で動きます。** コマンドはワーカーが動いているユーザーで、
  同じ環境、制限、サンドボックスのもとで実行されます。インストーラーのユニットでは `guru-worker`
  システムユーザーで、ユニットの `ProtectSystem=strict`、`ProtectHome=yes`、`PrivateTmp=yes`、
  `NoNewPrivileges=yes` に閉じ込められます。つまり `sudo` や setuid プログラムでは昇格できず、`/tmp` は
  ユニット専用のもので、書き込めるのは状態ディレクトリとインスタンス自身の `bin/` だけです。ユニットの
  `CAP_NET_BIND_SERVICE` も引き継がれるので、コマンドは 1024 未満のポートを bind できます。自分で書いた
  ユニットでワーカーを root で動かしていれば、すべての Admin に root シェルを渡すことになります。
- **Admin アカウントは、オプトインしたすべてのホストのシェルです。** Admin としてサインインした人 —
  あるいは Admin のセッションを盗んだ人 — は、オプトインしたすべてのホストでコマンドを実行できます。
  Admin の数は少なく、パスワードは強く保ってください。Maintainer と Observer のアカウントはシェルを
  使えません。
- **キーは環境からは消えますが、手の届かない場所にあるわけではありません。** `GURU_API_KEY` はシェルの
  環境から取り除かれますが、ワーカーのユーザーが読めるファイルはすべてシェルから読めます。
  インストーラーのレイアウトでは `/etc/guru-worker/<unit>.env` もその 1 つで、そのインスタンスの
  キーだけでなく、同じホストの他のすべてのインスタンスのキーも含まれます。どれも `guru-worker`
  グループから読めるからです。シェルを持つ人は、インスタンスの書き込み可能な `bin/` にあるバイナリを
  置き換えることもでき、ユニットは次の起動時にそれを実行します。リモートシェルは読み取り専用の
  ビューではなく、そのホスト上でのワーカーの全権限だと考えてください。
- **デフォルトでは平文を拒否します。** コマンドとその出力はワーカー ↔ マスター間のリンクを通るので、
  `--master` が `http://`（h2c）のワーカーは、オプトインが設定されていると起動を拒否します。代わりに
  `https://` のマスターを指定してください。`--remote-shell-allow-plaintext` はこの拒否を解除します。
  設定するのは、リンクが下のレイヤーですでに暗号化されている場合 — WireGuard や SSH のトンネル、
  TLS と同じくらい信頼できるプライベートネットワーク — だけにしてください。このチェックが対象と
  するのはワーカー自身のリンクです。すべてのコマンドとその出力はブラウザの接続も通るので、
  ダッシュボードも HTTPS で配信してください。
- **何も記録されません。** 誰が何を実行したかの監査証跡はなく、トランスクリプトも残らないので、
  コマンドが何をしたかの記録はホスト自身のログだけです。
