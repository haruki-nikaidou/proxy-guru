title: 通知
description: サーバーやポッドのヘルス変化がどのようにメールや Telegram メッセージになるのか、誰がそれを受け取るのか、そして notifier モードが何をするのか。
---

ヘルスモニターは、フリートのステータスが*何*であるかを決めます。通知が決めるのは*誰がそれを知るか*です。
マスターが記録したすべてのステータス変化は、受信者が選んだ言語のメールや Telegram メッセージになり得ます。

オペレーターが自分で有効にするまで、何も送信されません。新規インストールには通知の行が 1 つもなく、行が
存在しないことは「イベントなし」を意味するため、この機能をデプロイしても誰にも通知は届きません。

## 2 つのスコープ

どちらもキャンバス — 通知が対象とするワークスペース — をキーにします。

| スコープ | 行 | 編集できる人 | 宛先 |
|---|---|---|---|
| ワークスペース | `notify_canvas_setting` | 読み取りは `ViewWorkspace`、置き換えは `EditWorkspace` | メールアドレスのリストと Telegram チャット id のリスト。そのキャンバスを見る全員で共有します |
| 個人 | `notify_account_setting` | アカウント自身（人間のセッションのみで、API キーでは決してできません） | そのアカウント自身のメールアドレスと、Telegram チャット id 1 つ |
| 個人のデフォルト | `notify_account_default` | アカウント自身 | 同じもので、そのアカウントの行がないすべてのキャンバスに使われます |

各行は言語と、イベント種別の集合を持ちます。ワークスペース行の宛先は、アカウントへのファンアウト
*ではありません*。素のアドレスとチャット id なので、オンコール用のエイリアスやチームのチャンネルには、
このインストールにアカウントが存在する必要はありません。

個人設定の解決はキャンバス単位です。そのキャンバスの行を持つアカウントはその行で処理され、持たない
アカウントはそのデフォルト行で処理されます — 両方が使われることは決してありません。これが、「デフォルトでは
すべて、ただしこのワークスペースだけは日本語で」を、すべてのキャンバスに触らずに表現できる理由です。

ダッシュボードでは、キャンバスのサイドバーの**通知**で両方を編集します。**ワークスペース**カードは Observer には
読み取り専用で、**自分の設定**カードは常に編集できます。呼び出し元自身の行しか書き込まないからです —
アカウント id はセッションから取られ、リクエストから取られることは決してありません。

## 6 つのイベント種別

| 種別 | 送信されるタイミング |
|---|---|
| `server_online` | サーバーのステータスが `Online` になった |
| `server_degraded` | サーバーのステータスが `Degraded` になった |
| `server_offline` | サーバーのステータスが `Offline` になった（レポートが途絶えた、ストリームが閉じた、または死活監視のスイープ） |
| `pod_ready` | ポッドのステータスが `Ready` になった |
| `pod_deploying` | ポッドのステータスが `Deploying` になった（そのポッドに新しいリビジョンが publish された） |
| `pod_failed` | ポッドのステータスが `Failed` になった。ワーカーの message が通知の詳細として運ばれます |

綴りは、データベースの `CHECK`、API、設定ドキュメントのいずれでも同一です。

## 変化だけが通知される

ワーカーはデフォルトで 15 秒ごとに報告し、レポートごとにポッド 1 つあたり 1 行を書き込みます。行を単位に
通知すれば、間隔ごと・ポッドごとにメッセージが 1 通になってしまうため、ファンアウトは対象ごとに最後に
通知した内容を自分で覚えておき — `notify_server_state` と `notify_pod_state` に、サーバーごと・ポッドごとに
1 行 — 動いていないものはすべて捨てます:

- 保存されたステータスが新しいものと同じ → 何も送らず、行の `changed_at` もそのままです;
- 保存されたステータスがまったくない（その対象を初めて見たとき）→ ステータスを記録し、**何も送りません**。
  そうしなければ、この機能を導入したときや、サーバーを追加したときに、フリート全体を一斉に通知して
  しまいます;
- 保存されたステータスが異なる → 受信者の集まりごとに通知を 1 件送り、行を進めます。

サーバーやポッドを削除すると、その行は外部キーによって消えます。書き込みとファンアウトの間に消えた対象は、
リトライされるのではなく捨てられます。

## 通知が届くまで

```text
ヘルスの書き込み ──▶ orchestration が `health_changed` を publish（facts + ラベル）
                        │
                        ▼
              --mode consumer: ファンアウト
                 · 変化ではない fact を捨てる
                 · 設定を読み、受信者を解決する
                 · 受信者の集まりごとに通知を 1 件 publish する
                        │
                        ▼
              --mode notifier（ちょうど 1 つ）: 配信
                 · 通知の言語で subject と body を一度だけレンダリングする
                 · 通知が運ぶすべての宛先へ送る
```

fact は自分のラベル — サーバーやポッドの名前、キャンバスとその名前 — を一緒に運ぶため、notifier は
データベースを一切開きません。そのため、その後に名前が変わったサーバーについての通知も、発生した当時の
ままに読めます。

この分割は意図的です。ファンアウトはデータベースの読み手であり、他の consumer と同じようにスケールします。
一方、配信側は SMTP リレーと Telegram と話すため、2 つ動かしてはいけません。

## `--mode notifier`

`guru-master` の 5 つ目の実行モードであり、このワークスペースで唯一、単一インスタンスであることを要求される
モードです:

```sh
guru-master --mode notifier \
  --database-url "$GURU_DATABASE_URL" \
  --amqp-uri 'amqp://guru:guru@127.0.0.1:5672/'
```

- **インスタンスはちょうど 1 つ。** キューをバインドする前に、セッションスコープの PostgreSQL アドバイザリ
  ロックを取得します。2 つ目のインスタンスは `another notifier already holds the advisory lock; run
  exactly one` を出力して非ゼロで終了します。ロックは接続が切れることで解放されるため、kill された
  notifier が後続を塞ぐことはなく、前任と重なった再起動はメッセージを二重に送る代わりに即座に失敗します。
- **master キーも Redis も不要。** 何も復号せず、何も publish しないため、`GURU_MASTER_KEY` も `REDIS_URL` も
  受け取りません。必要なのはデータベース（上記のロックと、起動時に読む `notify` 設定のため）と
  ブローカーだけです。
- 最終的にどのチャンネルが使えるようになったかをログするため、シークレットが届いたかどうかを最も手早く
  確認できます:

```text
INFO guru_master: notification channel channel="email: configured"
INFO guru_master: notification channel channel="telegram: disabled (no GURU_TELEGRAM_BOT_TOKEN)"
```

notifier が停止していても通知は失われません。復帰するまで `guru_notify_health_notify_group` と
`guru_notify_health_notify_personal` のキューで待ちます。

## チャンネルとそのシークレット

2 つのシークレットは**環境変数のみ**で、設定ドキュメントの一部になることは決してありません。Admin は
ダッシュボードでそのドキュメントを読めますし、ボットトークンは設定ではありません:

| 変数 | チャンネル | 未設定の場合 |
|---|---|---|
| `GURU_SMTP_PASSWORD` | メール | リレーを認証なしで使います（localhost のリレーが期待する形です） |
| `GURU_TELEGRAM_BOT_TOKEN` | Telegram | Telegram は無効になります。チャット id を指す通知はログされ、スキップされます |

メールはプールされた SMTP 接続 1 本で送られ、`smtp_starttls` を無効にしていなければ STARTTLS で
アップグレードされます（無効にするとプレーンな SMTP で話すため、localhost のリレーやテスト用のシンクに
だけ使います）。Telegram は `telegram_api_base` に対して、チャットごとに `sendMessage` 呼び出し 1 回です。
トークンは URL のパスに入るため、リクエスト URL がログされることは決してありません。

どちらのチャンネルも、失敗した送信を `delivery_retry_delay_secs` 間隔で `delivery_attempts` 回まで
リトライします。

## 配信はベストエフォート

対象の状態行は、通知が publish された時点で — 送信される前に — 進みます。そのため、SMTP や Telegram の
障害で失われた通知が、`delivery_attempts` を超えてリトライされることは**ありません**。失敗した送信はログされ、
残りの宛先には引き続き送信が試みられます。配信を再キューしても、いまは変化なしに見える対象に対して
ファンアウトをやり直すことになり、その対象についての次のメッセージは、次の本当の変化になってしまいます。

`consumer` のレプリカが 2 つあると、狭いウィンドウで両方が同じ遷移を観測し、重複した通知を publish する
こともあり得ます。これは受け入れています。通知のために対象ごとのロックを置く価値はなく、重複は同じ本当の
ことを 2 回言うだけです。

通知は便利な機能であって、コントロールプレーンの記録ではありません。フリートが何を動かすかは、publisher が
すでにコミットした行が決めますし、ヘルスページは常に現在の真実を表示します。

## 設定

`app_config` のキーは `notify` 1 つで、他のすべてと同じく起動時に一度だけ読まれます:

```sh
manage-tool config set notify '{
  "smtp_host": "smtp.example.com",
  "smtp_port": 587,
  "smtp_starttls": true,
  "smtp_username": "guru@example.com",
  "smtp_from": "guru <noreply@example.com>",
  "default_language": "en"
}'
```

`smtp_host` が空 — これがデフォルトです — ならメールは完全に無効になります。フィールドの一覧は
[設定リファレンス](/ja/reference/configuration/#モジュール設定)にあります。保存（CLI から、あるいは
ダッシュボードの**管理 → 設定**から）した内容はマスターの再起動で有効になります。notifier はトランスポートを
起動時に一度だけ構築します。

## テスト通知を送る

通知ページの**テスト通知を送信**ボタンは、呼び出し元自身のチャンネルへ、そのキャンバスで有効な設定のまま
通知を 1 件 publish します。どの種別を購読しているかは無視します — 要点は購読ではなく、チャンネルだから
です。publish → notifier → 送信という経路のすべてを通るため、メッセージが届けば、notifier とそのシークレット、
そしてリレーがすべて動いていることの証明になります。

呼び出し元にチャンネルが 1 つも設定されていない場合は `FAILED_PRECONDITION` を返します。まずメールを
有効にするか、Telegram チャット id を設定して、保存してください。
