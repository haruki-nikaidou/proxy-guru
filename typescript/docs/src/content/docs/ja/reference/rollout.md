## 編集から適用済み設定まで

編集はグラフ変更の検査済みバッチ 1 つです（`ApplyGraph`、[キャンバス](/ja/reference/canvas/)を参照）。ルートキャンバスの
generation を進め、`CanvasDirty` を publish します。ワーカーの ack・登録・アドレス
変更は、代わりに自分のサーバーの設定ビュー上のカウンターだけを進めるので、多数のワーカーが同時に ack しても
キャンバス行で衝突しません。導出フックはキャンバスツリー全体を再導出し、定期的な `derive_stale_canvases` シグナル
（消費するのは同じフックです）が、この 2 つのカウンターを前回の導出が記録した値と比べて、メッセージの喪失で
取りこぼされたものを拾います。どちらのトリガーもブローカーのメッセージなので、このバックストップは
ブローカーから独立ではありません。`CanvasDirty` を失ったキャンバスは配信が回復するまで待ち、ブローカーに
到達できないマスターは何も導出しません。

すべてのサーバーは**単一の設定ビュー**を持ち、そこに `desired`、`in_flight`、`applied` の 3 つのスナップショットが
入ります。ワーカーのストリームが `desired` → `in_flight` を昇格させ、その `AckConfig` が `in_flight` → `applied` を
昇格させます。

```text
graph edit ───────▶ CanvasDirty ──┐
                                  ├──▶ derivation hook (--mode consumer)
cron: derive_stale_canvases ──────┘
                                       │
                                       ▼
                             config view: desired
                                       │ worker stream
                                       ▼
                                   in_flight
                                       │ AckConfig
                                       ▼
                                    applied
```

## 収束

導出は収束的です。サーバーは、ターゲットが実際にそれを提供し始めてからでないと宛先を切り替えないため、
ロールアウトの途中でトラフィックを落とすリビジョンはありません。単一の「現在の設定」フィールドではなく
3 スナップショットのビューが存在するのは、この性質のためです — マスターは、ワーカーが実際に適用した
ものを常に把握しています。

リビジョンは **pod 単位**で適用されます。ワーカーは準備とバインドに成功したすべての `[[forwarding]]` を
コミットし、失敗したものは以前のリスナーを維持し、それぞれの結果を ack します。マスターはその混在状態の
スナップショットを `applied` として保存し（適用できた pod は新しい形、失敗した pod は以前の形）、失敗した pod を
サーバーのビューに記録し、サーバーを `Degraded`、失敗した各 pod を `Failed` としてワーカーのメッセージ付きで
マークします。まったく適用できないリビジョン（パースできない TOML、書き込めない証明書ファイル）はワーカー上で
何も変えず、`apply_error` として記録されます。

## ヘルス

すべてのワーカーは `--health-interval`（デフォルト 15 秒）ごとに `ReportHealth` 経由で `HealthReport` を 1 件
ストリーミングします。内容は、実行中のリビジョン、前回のレポートからのアップロード/ダウンロードのバイト数と
接続数（max はハイウォーターマーク）、そして実行中の forwarding ごとに 1 つの `PodStatus` です。各レポートは
1 つの `server_health_record` 行と、pod ごとに 1 つの `pod_health_record` 行になります（forwarding の tag は
その pod の id です。依存側の切り替え中に 2 つのリスナーで保持される pod は、最も悪いステータスになります）。
pod のステータス: `Ready`（pod は `desired` が求めるものを実行しています）、`Deploying`（その pod を含む新しい
リビジョンが導出済みでまだ適用されていません — 導出が publish された時点で書き込まれます）、`Failed`（pod の
適用または実行に 失敗しました）。サーバーのステータス: `Online`、`Degraded`（猶予期間を超えて `desired` に遅れている、または
最後に ack されたリビジョンがいずれかの pod で失敗した）、`Offline`（ヘルスストリームが閉じた、または
3 間隔分レポートがない — `sweep_liveness` パス）。どちらの履歴も生のまま保持され、`trim_health_history` パスで
切り詰められます。`ListServerHealthHistory` / `ListPodHealthHistory` は時間範囲を読み取ります。

どちらのパスも `--mode consumer` で、ジョブの期限が来たときに `cron` スケジューラーが publish するシグナルに
応じて実行されます。スケジューラーは自身の時計以外の状態を持たず、consumer は各実行を 1 つの
`orchestration_job_run` 行で claim するため、consumer が何台起動していても、パスは設定された間隔につき
1 回だけ実行されます。

ダッシュボードでは、キャンバスの**ヘルス**ページが選択したウィンドウ（1 時間 / 6 時間 / 24 時間 / 7 日）で
両方の履歴を読み取ります。サーバーごとに 1 枚のカードがあり、そのステータス、ウィンドウ内の*最後のレポート
時点*の接続数とピーク値、さらに 2 つのチャート — レポートごとのアップロード/ダウンロードの差分から得た
スループットと、ハイウォーターマークと並べた接続数 — を表示します。このページはコントロールプレーンの
ストリームを追従し、再読み込みせずにその場で更新されます。サーバーのステータスバッジとサマリーの台数は、
ステータスの変化に即座に追従します。新しいレポートのデータポイントは、1 時間のウィンドウでは 2 秒ごと、
6 時間では 10 秒ごと、24 時間では 30 秒ごと、7 日では 2 分ごとにチャートに反映されます（ウィンドウが長いほど
再描画の頻度は下がります）。選択したウィンドウから外れたデータポイントは、サーバーがレポートを
送らなくなっていても消えていきます。すべての数値は引き続き保存されたレポートなので、
`Offline` のサーバーは最後に送った内容を、それが古くなってウィンドウから外れるまで表示し続けます。各カードの
*Pod イベント*タブは、そのサーバーのすべての pod のイベントを一覧し、`Failed` 行が持つ `message` も含みます。
タブを開いている間だけストリーミングされ、pod ごとに最新の 500 件までのイベントを表示し、新しいイベントは
およそ 2 秒以内に現れます。

## 証明書

TLS クライアントポッド（`sni`、DNS プロバイダー、`domain_id`、任意の ACME ディレクトリ — 空の場合は保存された
`orchestration` 設定の `default_acme_directory`、つまり Let's Encrypt）は、
`(sni, acme_directory)` ごとに 1 つの
`certificate` 行へ解決されます。ACME パスはその行を作成し、DNS プロバイダー経由で DNS-01 チャレンジを実行し
（Cloudflare: `domain_id` はゾーン ID、Vercel: `domain_id` はドメインで、プロバイダーの `account_id` がチーム ID）、
TXT レコードがパブリックリゾルバーから見えるようになるのを待って、チェーンと暗号化された鍵を保存します。
それまで、その pod は `invalid_pods` のエントリ（「certificate for <sni> is pending」）であり、
サーバーの障害になることはありません。更新は有効期限の 30 日前に行われます。更新は行の version を進め、
すべてのスナップショットは自身の TOML が参照するバージョンをピン留めしているため、その証明書を提供する
すべてのサーバーは、同じファイルパスと新しい鍵・証明書を持つ新しいリビジョンを受け取ります。

TLS または QUIC を使うリレーリスナーは、代わりに**内部 CA** を使います。`manage-tool orchestration init-ca` が
一度だけこれを作成し、導出フックがリレー pod ごとに有効期間 30 日のリーフ証明書を発行し（SAN は
`<pod-key>.relay.guru.internal`）、`rotate_relay_certificates` パスが有効期限の 10 日前にリーフをローテーションし、
ワーカーはリレーの対向を `certs/ca.pem`（TOML の `relay_ca`）だけで検証します。DNS プロバイダー、証明書、
CA はオペレーター API（`CreateDnsProvider`、`ListCertificates`、`RetryCertificate` など）を通じて Admin が管理します。
シークレットは `GURU_MASTER_KEY` で暗号化され、決して返されません。

ダッシュボードの **TLS** ページは、これの Admin 向けの側面です。DNS プロバイダーはここで作成・編集
（API トークンを空にすると保存済みのものが維持されます）・削除でき、証明書テーブルは各行のステータス、
解決されたプロバイダー、有効期限のヒント付きの有効期間、失敗時の `last_error` を表示し、行ごとに
*Retry*（失敗のクリア、または更新の強制）と*Delete* を備えます。このページが証明書を発行することは
ありません。行は、導出パスが TLS クライアントポッドの証明書設定を読んだ時点で現れ、その設定はキャンバス上の
ポッドのパネルで編集します。

## 導出された設定を確認する

`manage-tool` は、マスターが 1 つのサーバー向けに導出した TOML をそのまま出力します:

```sh
cargo run -p manage-tool -- --database-url "$GURU_DATABASE_URL" \
  orchestration export-config --server <orchestration_server id>
```

同じモデルがスタンドアロンワーカーも支えています。出力されたファイルはそのまま
`guru-worker --config` に渡せます。

ダッシュボードも同じ TOML を表示します — サーバーパネルの*ワーカー設定* — それを読み取るロールアウトの
情報の隣に、です: desired、in-flight、applied の各リビジョンとそのタイムスタンプ、`derive_error` と
`apply_error`、このサーバーが待っているサーバー（名前に解決済み）、そして pod・listen アドレス・エラーの
テーブルとしての `invalid_pods`。`ForgetServerApplied` もそこにあり、Admin 限定で確認ダイアログの後ろに
置かれています。まだサービスを提供している可能性のあるサーバーを、死んだと宣言する操作だからです。

## リスナーの同一性

収束はリスナーを `(server, port, protocol)` で照合し、アドレスでは決して照合しません。サーバーのアドレスは
そのワーカーから学習される（またはオペレーターが固定する）もので、リレーが*ダイアル*する先だけを決めます。
アドレスを変更すると、そのサーバーを指すすべての宛先が再導出されますが、シームレス切り替えのプロトコルには
影響しません。依存側が参照しているリスナーは変わっていないからです。pod 単位の導出失敗では、その pod の
リスナーが `bind:port` として（ワイルドカードバインドでは `[::]:port`）示され、ターゲットのサーバーにまだ既知の
アドレスがないリレーは、そこで `server … has no address yet` として報告されます。

リスナーが移動した pod（ポートの変更）は、すべての依存側が切り替え終わるまで新旧両方のリスナーを提供します。
ワーカーはリスナーを tag で区別し、pod の tag はその id なので、保持される旧リスナーは TOML 上ではそのソケットに
基づく名前 `<pod id> (9443/relay_tcp)` で現れ、どこからも参照されなくなった時点でその tag ごと外されます。
いずれかのサーバーがまだダイアルしているポートのプロトコル変更にはシームレスな道がないため、その編集は拒否され、
pod には新しいポートが必要です。

## 転送の形

各 pod は 1 つの `[[forwarding]]` になります: そのリスナー（`raw`、`tls`、または受信側のリレー）とルートです。
`route_table` 機能を報告するワーカーはルートをグループとアップストリームのテーブルとして受け取り、古いワーカーは
インラインのツリー（重みはメンバーの繰り返し、フェイルオーバーは `fallback`、スティッキーなバランスは `ip_hash`）
として受け取ります。PROXY プロトコルの v1 と v2 は、どちらの端でもサポートされます。
[設定リファレンス](/ja/reference/configuration/#ルートテーブル)を参照してください。
