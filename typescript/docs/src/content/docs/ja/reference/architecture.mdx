## クレート

| クレート | 役割 |
|---|---|
| `bin/guru-master` | コントロールプレーン。1 つのバイナリに 5 つのモード（`--mode`）: `dashboard_grpc`（オペレーター API）、`workers_grpc`（ワーカー API + config view ポーラー）、`consumer`（Iggy のイベントハンドラー — キャンバスの導出と通知のファンアウト）、`notifier`（通知の配信、インスタンスは 1 つ）、`cron`（6 つの定期ジョブをプロセス内で実行）。配線には wakuwaku の `ServiceBuilder`（`grpc_service`、`iggy_consumer`、`cron_job`）を使います。 |
| `bin/guru-worker` | データプレーン。リスナーを終端しトラフィックを転送します。TOML ファイルから単独で動作する（`SIGHUP` で再読み込み）か、エージェントモードで master から設定をストリーミング受信します。 |
| `bin/manage-tool` | 管理 CLI: `create-admin` によるブートストラップ、`orchestration export-config`。 |
| `lib/guru_topology` | ポッドのグラフとしての転送トポロジー。グラフを検査し、各サーバーの転送設定にコンパイルします。純粋な計算で I/O はありません。 |
| `lib/guru_worker_config` | 両プレーンで共有されるワーカー設定モデル。 |
| `lib/rpguru_sdk` | `proto/` から生成された gRPC/protobuf 型（Rust）。 |
| `lib/db_types` | `table_record!` と `text_enum!`: 型付きの行 ID と、テキストで保存する enum。 |
| `modules/auth` | アカウント、セッション、API キー、RBAC。 |
| `modules/orchestration` | キャンバス、サーバー、ポッドグラフ。グラフの検査、設定導出、ワーカーへのロールアウト。 |
| `modules/notify` | 通知モジュール — `base` から雛形を作成しただけで、まだ未実装です。 |
| `modules/base` | 共通基盤と、すべてのモジュールが踏襲するレイアウト。 |

## すべては Processor

`kanau::processor::Processor` は **状態 + 非同期関数** です:

```text
Processor = State + async fn(Input) -> Result<Output, Error>
```

`Processor` は自身の依存関係を保持する `Clone` 可能な構造体で、操作ごとに 1 回 `Processor<Input>` を実装します。ビジネス操作、イベントハンドラー、定期ジョブはいずれも入力 1 つと `Processor` 実装 1 つとしてモデル化されます。データベースクエリも入力構造体 1 つですが、こちらは wakuwaku-entity の `Query` と `Execute` を実装し、`base::db::Db` がそれを `Processor` として実行します。

## モジュールの構造

すべてのモジュールクレートは `modules/base` を踏襲します:

<FileTree>

- src/
  - lib.rs declares the modules below; sets crate-wide lints
  - config.rs typed configuration (one `app_config` row, JSON document)
  - utils/ small, dependency-light helpers
  - entities/ persistence layer
    - db/ PostgreSQL row types + wakuwaku-entity queries (table markers in tables.rs)
    - redis/ Redis key/value types (rkyv-encoded)
  - services/ business logic (stateful Processors)
  - events/ Iggy event payloads + topics
  - hooks/ background reactors (Iggy event handlers, cron jobs, loggers)
  - rpc/ gRPC service implementations (transport edge)

</FileTree>

| 書こうとしているもの | 置き場所 |
|---|---|
| PostgreSQL クエリ、またはテーブル行の型 | `entities/db` |
| Redis にキャッシュされる値、または一時トークン | `entities/redis` |
| クエリとルールを組み合わせたユースケース | `services` |
| 他のモジュールが反応するメッセージ | `events` |
| イベントへの反応 / 定期ジョブ / 監査ログ | `hooks` |
| gRPC エンドポイントの実装 | `rpc` |
| オペレーターが変更できる型付き設定 | `config` |
| ランタイム依存のない純粋なヘルパー | `utils` |

## レイヤールール

- **依存の向き:** `rpc → services → entities/events/config`。機能モジュールは `base` に依存してよいですが、`base` が機能モジュールに依存してはならず、モジュール同士が互いの内部に手を伸ばしてもいけません。モジュール間の通信は gRPC か Iggy イベント経由です。
- **`entities/db`:** テーブルまたは集約ごとに 1 サブモジュール。行構造体を定義し、ID は `table_record!(NameId, "table")` でラップします。テキストとして保存する enum は `text_enum!` で一度だけ書きます。クエリごとに入力構造体を 1 つ用意し、wakuwaku-entity の `Query`（その `Effect` は、`entities/db/tables.rs` にあるクレートごとのテーブルマーカーに対する `Read<tables::X>` / `Write<tables::X>`）と `Execute<PgSource>` を実装します。実行するのは `base::db::Db`（= `wakuwaku::entity::Db<PgSource, ReadWrite>`）で、`Execute` は `base::db::Error` を返します。複数ステートメントのトランザクションはすべて公開の `TxFlow` ステートマシン（`XFlow::new(input)`）で、各ステップは通常のクエリやヘルパークエリを順に `tx.run` し、`base::db::commit` か `base::db::rollback`（フェンスに負けたとき: `Error::Conflict`）で終えます。何にも一致しなかった条件付き書き込みは、その空の結果をコミットします。フローはクエリではありません。呼び出し側が `db.process(Transaction(XFlow::new(..)))` を実行し、`TxOutput::Committed` / `RolledBack` を自分で処理します。`COMMIT` の応答が失われた場合は `OrchestrationError::CommitUnknown`（gRPC `UNKNOWN`）になります。スナップショット読み取りは `RepeatableRead` の読み取り専用フローです。すべてのステートメントは sqlx の `query!` ファミリーを通るため、SQL はクレートのコンパイル時にスキーマに対して検査されます。振る舞いは引き続き実データベースに対する結合テスト（`#[sqlx::test]`）でカバーします。
- **`services`:** 依存関係を保持する `Clone` 構造体。操作ごとに `Processor` 実装を 1 つ持ち、ドメイン型を返します — protobuf 型は返しません。
- **`events`:** Iggy イベントのペイロードとトピック。イベントは rkyv と `RkyvMessageSer/De` を derive し、`EventBody` と `Event`（`TYPE_TAG`、`SUPER_PARTITION_NAME` がトピックとなる `Key: PartitionKey`、`Algebra`、`atomic_ordering`）を実装します。契約のドキュメントには publisher、consumer、トピック、タグを書きます。共有のストリームとトポロジー（`STREAM`、`PARTITIONS`、`ensure_topology`）は `base::events` にあります。モジュール間で唯一認められた非同期チャネルです。
- **`hooks`:** イベントへの反応は Iggy の `EventHandler<E>` 実装（と `ServiceCreation`）で、`--mode consumer` と `--mode notifier` で動きます。定期処理は `CronJob` 実装（固定の `INTERVAL` を持つ `Processor<CronTick>`）で、`--mode cron` のプロセス内で動きます。各ジョブは作業を始める前に `ClaimJobRun` で実行を claim する（`orchestration_job_run` 行 1 件の compare-and-set）ため、`cron` プロセスを多重化しても同じパスが設定された間隔に 2 回走ることはありません。
- **`rpc`:** 薄いアダプター — リクエストをデコードし、サービスを呼び、レスポンスをエンコードするだけ。ビジネスロジックは持ちません。
- **エラー:** `wakuwaku::Error` はもうありません。各モジュールが自身のエラー enum（`AuthError`、`OrchestrationError`、`NotifyError`）を持ち、それは `tonic::Status` に、ハンドラーでは Iggy の `HandleError` の分類に変換されます。`entities/db` の内部では `base::db::Error` を使い、サービス層で `?` によって変換します。この型は、データベースが応答しなかった場合（`UNAVAILABLE`）と拒否された場合を区別し、さらに `Error::Conflict` — 確実にコミットされなかったトランザクション — をその両方から区別します。
- **Lint:** クレートレベルで `deny(clippy::unwrap_used)`、`expect_used`、`panic`。リクエストパス上で panic させません。
- **トレーシング:** `tracing` と `tracing-subscriber` のみ（OpenTelemetry は使いません）。`#[tracing::instrument(skip_all, err)]` に明示的なスパン `name` を付けます — entities は `Query:<Input>`（フローの `step` には `Transaction:<Input>`）、services は `Service:<Input>`、フックとジョブは `Hook:<Input>`。gRPC ハンドラーには不要です。トレイトメソッド名がそのままスパンのラベルになります。

## PostgreSQL に関する注意

- NULL を許容するカラムの比較には `<>` ではなく `IS DISTINCT FROM` を使ってください。`NULL` に対する `<>` の結果は `NULL` であって `true` ではないため、`<>` で書いたフェンスは黙ってまったく一致しなくなります。
- `jsonb` ドキュメント内の JSON の `null` は SQL の `NULL` ではありません。両者は `jsonb_typeof` で区別できます。
- ステートメントはコンパイル時に検査されます。カラムは明示的に列挙し（`SELECT *` は使いません）、Rust 側の型が `table_record!` の ID、`text_enum!`、`Json<T>` であるカラムには型を併記したエイリアス（`id AS "id: CanvasId"`）を付け、同じ型のパラメーターは `input.id as _` として渡します。5 行を超える SQL は `<crate>/sql/*.sql` に置き、`query_file!` から呼びます。実行時に SQL を組み立てる箇所はありません。
- オフラインクエリデータは `.sqlx/` にコミットされているため、ビルドにデータベースは不要です（イメージのビルドは `SQLX_OFFLINE=true`）。ステートメントやスキーマを変更したら、マイグレーション済みのデータベースに対して `cargo sqlx prepare --workspace -- --all-targets` を実行して再生成します（`-- --all-targets` はテスト自身のステートメントも含めるために必要です）。
- スキーマは常にマイグレーションであり、編集ではありません。`guru-master` が起動時にアドバイザリロックの下で未適用のものを適用するため、フリートが一斉に起動しても各マイグレーションはちょうど一度だけ適用されます。
